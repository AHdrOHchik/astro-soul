# apps/web — Mini App «Разбор личности»

Клиент Telegram Mini App. Закрывает экраны 1–7 и 9 из `SPEC.md` и экран
согласия на обработку персональных данных: Welcome → согласие → BirthDate →
BirthTime → BirthPlace → Chart (колесо, три карточки, блок полного разбора,
«Поделиться»), дальше Paywall (покупка разбора и подписки), Report (заказ
разбора и сам разбор) и Settings (подписка, лимиты, документы, поддержка,
удаление данных). Тот, у кого карта уже есть, попадает сразу на неё. По пути
приложение отправляет продуктовые события. Экран прогноза и «спроси карту»
(экран 8) — в следующей итерации. Приложение написано под контракт
`api.openapi.yaml` версии 1.5.1.

Код живёт в двух пакетах:

| Пакет | Что внутри |
| --- | --- |
| `apps/web` (`@astro-soul/web`) | Приложение: экраны, клиент API, обёртка над Telegram, тексты, токены темы, мок API для разработки |
| `packages/ui` (`@astro-soul/ui`) | UI-кит без текстов и без сети: кнопки, поля, карточки, каркас экрана, состояния. Здесь же базовый `tsconfig` фронтенда и его слой правил ESLint (`eslint.frontend.mjs`) |

Из остального монорепо приложение берёт `@astro-soul/shared` (цены планов,
границы длины запроса в поиске места), `api.openapi.yaml` (типы API) и
`legal-texts-<версия>.md` (юридические тексты, с ними сверяется тест).

## Запуск

Нужны pnpm 9 (`packageManager` в корневом `package.json`) и Node 22 не ниже
22.22.2: нижнюю границу задаёт jsdom 31, на котором идут тесты, верхнюю (`<23`) —
`engines` корневого `package.json`.

```sh
pnpm install
pnpm --filter @astro-soul/shared build   # один раз и после правок в packages/shared

# с моком вместо бэкенда, в обычном браузере
API_MOCK=1 VITE_DEV_INIT_DATA=mock-init-data pnpm --filter @astro-soul/web dev

# то же, но с «оплатой» без Telegram: весь путь от цены до готового разбора в браузере
API_MOCK=1 VITE_DEV_INIT_DATA=mock-init-data VITE_DEV_INVOICE=paid pnpm --filter @astro-soul/web dev

# с настоящим API (по умолчанию проксируется http://localhost:8080)
API_PROXY_TARGET=http://localhost:8080 VITE_DEV_INIT_DATA='<initData>' pnpm --filter @astro-soul/web dev
```

`@astro-soul/shared` подключается собранным, из своего `dist/`. Пока он не
собран, не работают ни `dev`, ни `typecheck`, ни `test`, ни корневой `pnpm lint`.
Dev-сервер кладёт пакет в свой кеш зависимостей и изменений в нём не замечает
даже после обычного перезапуска: после пересборки `packages/shared` запускайте
`pnpm dev --force`.

Те же переменные можно положить в `apps/web/.env` (шаблон — `.env.example`,
сам `.env` в git не попадает). `initData` — это учётные данные: строка входит
от имени своего пользователя, поэтому берите её только от тестового аккаунта.
API принимает только строку, подписанную токеном того бота, с которым он запущен
(`TELEGRAM_BOT_TOKEN`), и не старше 24 часов.

Приложение вызывает `GET /me`, `DELETE /me`, `GET /charts/current`,
`POST /geo/resolve`, `POST /charts`, `POST /billing/invoice`, `POST /reports`,
`GET /reports/{id}` и `POST /events`; колесо показывает по `wheel_url` из
ответа, а делится картинкой по `wheel_png_url`. Чтобы API построил карту, рядом
с ним должен работать астро-движок (`pnpm dev:astro` из корня); как поднять
API, движок и базу — в корневом `README.md`.

В `main` контракт (1.5.1) новее кода `apps/api`: `POST /reports` и
`GET /reports/{id}` сервер из `main` не знает, а события принимает только с
полем `at` (контракт называет его `occurred_at`), так что с ним не работают ни
разбор, ни события. Всё это есть в бэкенд-PR #20; с его сервером приложение и
проверялось (раздел «Проверка на устройстве»).

| Команда (из `apps/web`) | Что делает |
| --- | --- |
| `pnpm dev` | Dev-сервер Vite |
| `pnpm build` | Проверка типов, продакшен-сборка в `dist/`, затем `scripts/check-bundle.mjs` |
| `pnpm preview` | Раздать собранный `dist/` |
| `pnpm clean` | Удалить `dist/` (его же вызывает корневой `pnpm clean`) |
| `pnpm typecheck` | Сверка типов API с контрактом и `tsc` отдельно для кода приложения и для Node-части (конфиг Vite, мок, тесты-охранники) |
| `pnpm test` | Vitest: компонентные и модульные тесты |
| `pnpm size` | Только проверка собранного `dist/` |
| `pnpm gen:api` | Перегенерировать `src/api/schema.gen.d.ts` из `api.openapi.yaml` |

Из корня репозитория `pnpm build | typecheck | test` запускают одноимённые
скрипты во всех пакетах; корневому `pnpm test` нужна ещё и тестовая база для
`apps/api` (см. корневой `README.md`).

Линт один на весь монорепо: `pnpm lint` из корня. Своего конфига ESLint у
фронтенда нет. Корневой `eslint.config.mjs` подключает слой
`packages/ui/eslint.frontend.mjs`, который добавляет к общим правилам
`strictTypeChecked` из typescript-eslint и правила React Hooks — только для
`apps/web` и `packages/ui`. `eslint` в `devDependencies` пакета `packages/ui`
закрывает peer-зависимость `eslint-plugin-react-hooks`. Диапазон версий там
должен совпадать с корневым: с другим диапазоном pnpm ставит в репозиторий
вторую копию ESLint.

## Переменные окружения

| Переменная | Где действует | Назначение |
| --- | --- | --- |
| `VITE_API_BASE_URL` | бандл | Origin API без `/api/v1`. Пусто — тот же origin, что у страницы |
| `VITE_BOT_USERNAME` | бандл | Имя бота, с `@` или без. С ним «Поделиться картой» добавляет к сообщению ссылку `https://t.me/<имя>?startapp=chart_<chart_id>`. Пусто — уходят только картинка и текст. Значение, которое не является именем (например, ссылка на бота), останавливает сборку |
| `VITE_SUPPORT_CONTACT` | бандл | Куда ведёт «Написать в поддержку»: имя в Telegram (с `@` или без) или ссылка `https://…`. Пусто — кнопка есть, но неактивна и называется «Поддержка скоро появится». Любое другое значение останавливает сборку |
| `VITE_DEV_INIT_DATA` | только dev-сборка | Строка `initData` для запуска вне Telegram. В продакшен-бандл не попадает: `pnpm build` падает, если попала |
| `VITE_DEV_INVOICE` | только dev-сборка | Чем заканчивается «оплата» вне Telegram: `paid`, `cancelled`, `failed` или `pending`. При `paid` dev-сборка ещё и сообщает моку, что счёт оплачен. Пусто — пейволл говорит «Оплата доступна в Telegram». В продакшен-бандл не попадает |
| `API_PROXY_TARGET` | dev-сервер | Куда проксировать `/api`, когда мок выключен |
| `API_MOCK` | dev-сервер, `vite preview` | `1` — отвечать моком из `mock/` |
| `API_MOCK_DELAY` | мок | Задержка ответа в мс (по умолчанию 400), чтобы были видны состояния загрузки |
| `API_MOCK_ME` | мок | Кто пользователь мока, слова через запятую: `401`, `500` (`GET /me` падает), `returning` (карта уже есть), `paid` (карта и купленный для неё разбор), `subscriber` (карта и подписка на месяц); пусто — новый пользователь |
| `API_MOCK_REPORT` | мок | Чем заканчивается каждый разбор: `ready` (по умолчанию), `failed`, `refunded`, `stuck` (застрял на двух главах) |
| `API_MOCK_REPORT_CHAPTER_MS` | мок | Сколько длится одна глава разбора, мс (по умолчанию 2500) |
| `API_MOCK_INVOICE` | мок | `POST /billing/invoice`: `422` (без `field_errors`), `500`, `price` (счёт на 50 ⭐ дороже ожидаемого) |
| `API_MOCK_DELETE` | мок | `DELETE /me`: `409` (с текстом сервера и `details.reason: refund_failed`), `401`, `500`; пусто — всё удаляется |
| `API_MOCK_PDF` | мок | `1` — у готового разбора есть PDF (в `apps/api` его пока нет) |
| `API_MOCK_CONSENT_VERSION` | мок | Версия согласия, которую мок принимает в `POST /charts` (по умолчанию — версия текстов приложения). Другая дата — «сервер с более новыми текстами»: любой запрос карты получит отказ по `consent.version` |

Секретов у клиента нет. Вход — только по `initData`: приложение держит строку
в памяти и отправляет заголовком `X-Telegram-Init-Data`, токенов не получает и
ничего не кладёт в `localStorage` и cookie. В `sessionStorage` приложение пишет
два ключа. `astro-soul.consent-refused` — версия согласия, которую отклонил
сервер, на время перезагрузки (раздел «Согласие и юридические тексты»).
`astro-soul.report-key.full.<chart_id>` — ключ идемпотентности заказа разбора
и время его создания (раздел «Оплата и разбор»): случайный идентификатор под
идентификатором карты. Данные рождения, текст разбора и ссылка на PDF туда не
попадают. Сам SDK Telegram сохраняет там же копию
параметров запуска (в них есть `initData`), чтобы пережить перезагрузку
страницы; она исчезает вместе с окном Mini App.

## Мок API

`mock/` — middleware dev-сервера, которое отвечает на `/api/v1/*` данными,
типизированными по `src/api/schema.gen.d.ts`: поле, которого нет в контракте,
не пройдёт `pnpm typecheck`. Мок ничего не считает: позиции планет в нём
условные, на колесе написано MOCK, а текст разбора прямо говорит, что он не
разбор. Тексты ошибок и строки короткого разбора — те же, что отдаёт
`apps/api`; для разборов, счетов и удаления — те, что написаны в бэкенд-PR #20.
В продакшен-бандл мок не входит.

Мок помнит своего пользователя, пока его не перезапустили: построенную карту
(после неё `GET /me` отвечает `has_chart: true`, `GET /charts/current` отдаёт
эту карту, а `POST /charts` с теми же данными — её же с кодом `200` и
`is_restored: true`), купленное, заказанные разборы. Поэтому перезагрузка
страницы после построения карты открывает сразу карту.

Начать заново с другим сценарием можно без перезапуска: открыть в браузере
`/api/v1/__mock/reset?me=paid&report=failed` и перезагрузить приложение.
Параметры — те же, что в переменных: `me`, `report`, `invoice`, `delete`,
`pdf=1`, `chapter_ms`. Без параметров — новый пользователь и разбор, который
удаётся.

Сценарии включаются вводом на экранах:

| Где | Что ввести | Что произойдёт |
| --- | --- | --- |
| Поиск места | `Мо`, `Ка`, `Но`, `Са`, `Ек`, `Вл`, `Ал`, `Ми`, `Ам` | Обычная выдача (поиск по началу названия, с двух символов) |
| Поиск места | любое другое, например `Ъъъ` | `200` с пустым списком → «Ничего не нашли» |
| Поиск места | `ошибка…` | `500` → ошибка с повтором |
| Поиск места | `лимит…` | `429 RATE_LIMITED` |
| Поиск места | `провайдер…` | `503 GEO_NOT_FOUND` с `details.reason: provider_timeout`: справочник мест недоступен → ошибка с повтором |
| Выбор места | `Ошибинск` | `POST /charts` → `500` |
| Выбор места | `Датино` | `422`, отклонено поле `birth_date` → шаг «Дата рождения» с текстом сервера |
| Выбор места | `Времянск` | `422`, отклонено поле `birth_time` → шаг «Время рождения» |
| Выбор места | `Отказово` | `422`, отклонено поле `birth_place` → шаг «Место рождения» |
| Выбор места | `Согласово` | `422`, отклонено поле `consent` → экран согласия |
| Выбор места | `Версионово` | `422`, отклонено поле `consent.version` → приложение перезагружается; сборка та же, поэтому дальше экран «Условия обновились» с кнопкой «Обновить приложение» |
| Выбор места | `Пустошь` | `201` с пустой картой → пустое состояние |
| Выбор места | `Безколёсово` | Карта есть, картинка колеса не грузится |
| Выбор места | `Примерново` | Карта с предупреждением `approximate_place` и ещё одним кодом, которого нет в контракте: приложение показывает первое и пропускает второй |
| Время | «Не знаю» | Карта без Асцендента и домов, предупреждение `no_birth_time` |
| Время | «Знаю примерно» | Предупреждение `approximate_time` |
| Запуск | `API_MOCK_ME=returning` | Карта уже есть: приложение открывается на ней |

Разбор, оплата и удаление — сценарии запуска (переменные или `__mock/reset`):

| Сценарий | Что произойдёт |
| --- | --- |
| `me=paid` | На карте «Получить разбор»: заказ принимается, разбор пишется по главе за `chapter_ms` |
| `me=returning` | На карте цена: `POST /reports` без покупки — `402` |
| `me=subscriber` | Подписка на месяц: в настройках план и срок, пейволл продаёт только разбор |
| `report=failed` | Разбор падает после двух глав: экран «Не получилось» |
| `report=refunded` | То же, а через 4 секунды разбор становится `refunded`, покупка отзывается |
| `report=stuck` | Разбор останавливается на двух главах: через минуту — «Это дольше обычного…» |
| `invoice=422`, `invoice=500`, `invoice=price` | Отказ в счёте без `field_errors`; ошибка сервера; счёт дороже, чем ждёт приложение |
| четвёртый счёт подряд | `429`, как в `apps/api` (не больше трёх счетов в час) |
| `delete=409`, `delete=401`, `delete=500` | Отказы `DELETE /me` |
| `pdf=1` | У готового разбора есть ссылка на PDF |

Оплату мок сам не проводит: счёт становится оплаченным, когда об этом сообщит
«Telegram» — запрос `POST /api/v1/__mock/payments {invoice_link, delay_ms}`. Его
отправляет dev-сборка с `VITE_DEV_INVOICE=paid`; `delay_ms` играет вебхук,
который опаздывает. `POST /api/v1/__mock/revoke` отзывает покупку разбора, как
возврат через поддержку: от разбора остаётся то, что сервер показывает
неоплаченным, — тизер. Оба адреса — не часть API.

Мок проверяет форму тела `POST /charts`: без `consent`, без `time_precision`
или со временем при `unknown` он отвечает `422` с `details.field_errors`; версию
согласия он сверяет со своей (`API_MOCK_CONSENT_VERSION`). Возраст и часовой
пояс он не проверяет — эти отказы сервера показывают сценарии из таблицы.

`POST /events` мок разбирает по правилам контракта: неизвестное имя или
неверная форма события — `422` на всю пачку; событие с запрещённым ключом в
`props`, старше суток или из будущего молча отбрасывается; в ответе `202` с
числом принятых. `GET …/wheel.png` отдаёт настоящий PNG с условным колесом; `size`
— только 1080 или 1600, иначе `422`, как в контракте. `limit` в поиске места вне
1…10 — тоже `422`.

Без заголовка `X-Telegram-Init-Data` мок отвечает `401`, как требует контракт.
Поэтому продакшен-сборка, открытая через `API_MOCK=1 pnpm preview` в обычном
браузере, показывает экран «Открой приложение в Telegram» — так и должно быть.

### Правила, за которыми следят тесты и сборка

- **Токены.** Цвета, размеры, длительности и градиенты задаются только в
  `src/theme.css`; в остальных CSS — только `var(--…)`. Инлайновых `style` нет.
- **Тексты.** Вся кириллица — в `src/i18n/`. В остальном коде приложения и
  UI-кита её нет даже в комментариях (в тестах можно).
- **Старые движки.** В CSS не используются flex-`gap`, `aspect-ratio`, `inset`,
  `:has()`, `:is()`/`:where()`, `@layer`, `@container`, вложенность.
- Всё это проверяет `tests/design-system.test.ts`; он же ловит неопределённые и
  неиспользуемые токены.
- **Контракт.** `pnpm typecheck` (а значит и `pnpm build`) падает, если
  `src/api/schema.gen.d.ts` разошёлся с `api.openapi.yaml`. После изменения
  контракта — `pnpm gen:api`.
- **Юридические тексты.** Тексты Welcome (дисклеймер и строка под кнопкой),
  экрана согласия и экранов документов дословно совпадают с
  `legal-texts-<версия>.md`, а версия согласия меняется вместе с ними — это
  проверяет `tests/legal-texts.test.ts` (подробнее — в разделе «Согласие и
  юридические тексты»).
- **События.** Имена событий в приложении — ровно список `x-analytics-events`
  контракта, а среди ключей `props` нет ни одного из
  `x-events-forbidden-prop-keys` — это проверяет `tests/contract.test.ts`. Он же
  сверяет ссылку на бота с шаблоном `x-bot.share_link_template`.
- **Бандл.** `scripts/check-bundle.mjs` падает, если `dist/` больше 350 кБ gzip
  (лимит из `SPEC.md`) или содержит dev-переменные. `pnpm build` собирает
  продакшен-бандл при любом `NODE_ENV`: без этого сборка с `NODE_ENV=test`
  (так запускает CI) включала в бандл отладочную сборку React.

### Как приложение читает ответы API

- **Ошибки** разбираются по `Problem.code`, а по HTTP-статусу — только если в
  ответе нет тела `Problem` с известным кодом (так может ответить прокси перед
  API). Тогда 401, 402, 403, 404, 409, 422 и 429 дают свои коды, любой другой
  статус — `INTERNAL`. `400` API не использует, поэтому «голый» 400 — тоже
  `INTERNAL`, а не «проверь данные».
- **Текст ошибки.** `Problem.message` — готовый текст для пользователя,
  приложение показывает его как есть. Исключение — текст без единой
  кириллической буквы: так отвечает не API, а прокси или фреймворк, и вместо
  него показывается свой текст. `request_id` виден на экране ошибки как «Код
  обращения», мелким шрифтом; тап копирует его. Берётся он из `Problem`, а
  если у ответа нет такого тела — из заголовка `X-Request-Id`.
- **Отказ по полям.** `POST /charts` может ответить `422` со списком
  `details.field_errors`. Приложение возвращает пользователя на самый ранний
  экран, поле которого отклонено (`consent` — согласие, `birth_date` — дата,
  `birth_time` и `time_precision` — время, `birth_place` — место), и показывает
  текст сервера у этого поля; фокус встаёт на поле. Текст исчезает, когда поле
  меняют, а новая отправка стирает все такие тексты. Если сервер назвал только
  поля, которых нет ни на одном экране, ошибка показывается на экране карты.
  Отказ по полю `query` в поиске места показывается у строки поиска.
- **Версия согласия.** Отказ по полю `consent.version` значит, что тексты этой
  сборки устарели. Исправить его на экране нельзя, поэтому он важнее остальных
  полей того же ответа: приложение перезагружается (раздел «Согласие и
  юридические тексты»).
- **Возраст.** Шаг даты считает так же, как контракт: взрослый — с 00:00
  UTC дня восемнадцатилетия (`Date.UTC(год + 18, месяц, день)`, для 29 февраля
  это 1 марта); дата «в будущем» — позже сегодняшнего дня по UTC. Проверка на
  клиенте только экономит запрос — решает сервер, и его отказ по `birth_date`
  приложение покажет на том же шаге.
- **Поиск места.** Запрос уходит с двух символов (без пробелов по краям) и не
  длиннее 120 — границы взяты из `@astro-soul/shared`, по ним же проверяет
  сервер. `200` с пустым списком — «ничего не нашли». `503` с кодом
  `GEO_NOT_FOUND` значит, что справочник мест недоступен: это ошибка с кнопкой
  повтора, а не пустой результат. Причина из `details.reason` пользователю не
  показывается.
- **Конверт карты.** `POST /charts` (и `201`, и `200`) и `GET /charts/current`
  отдают один объект, и читает его одна функция. Была ли карта уже построена,
  говорит `is_restored` в теле, а не код ответа. `404` на `GET /charts/current`
  — не ошибка, а «карты ещё нет».
- **Вернувшийся пользователь.** Если `GET /me` говорит, что карта есть
  (`has_chart` или `chart_id`), приложение открывается на экране карты и
  запрашивает `GET /charts/current`. Новому пользователю этот запрос не
  отправляется. Если карты всё же нет (`404`), начинается обычный путь с
  Welcome. Под такой картой есть кнопка «Ввести данные рождения заново»: она
  ведёт на экран согласия, анкета за ней пустая.
- **Картинка для шаринга.** «Поделиться картой» отправляет `wheel_png_url`:
  PNG чат показывает картинкой. Если сервер его не прислал, уходит ссылка на
  SVG (`wheel_url`). Когда задан `VITE_BOT_USERNAME`, к тексту сообщения
  добавляется ссылка на бота по шаблону контракта; адресом сообщения остаётся
  картинка.
- **Повторы.** Ответ 5xx клиент повторяет до двух раз (через 0,3 и 0,9 с) и
  только потом показывает ошибку. Ответы с другими статусами не повторяются.
  Никогда не повторяются `POST /events` (повторённая пачка посчиталась бы
  дважды), `POST /billing/invoice` (сервер считает счета) и `DELETE /me`:
  повторить их может только пользователь, кнопкой. `POST /reports` повторяется
  с тем же ключом идемпотентности.
- **`Me`.** Права (`entitlements.is_active`, `entitlements.full_report`) считаются
  выданными, только если сервер прислал ровно `true`; чего в ответе нет, того
  нет. `Me` перечитывается после оплаты и при открытии настроек.
- **Предупреждения к карте.** Экран карты показывает то, о чём предупреждает
  сервер (`warnings`), в его порядке, и своих предупреждений не добавляет.
  Слова есть для трёх кодов: `no_birth_time`, `approximate_time`,
  `approximate_place`. Код, которого сборка не знает, пропускается: сервер
  может добавлять новые. Список известных кодов — `CHART_WARNINGS` в
  `src/api/index.ts`, тексты — `chart.warnings` в `ru.ts`.
- **Точность времени.** Выбранный на шаге времени вариант уходит в `POST /charts`
  как `time_precision` (`exact`, `approximate`, `unknown`). Было ли у карты
  время рождения — а значит, есть ли у неё Асцендент и дома, — экран читает из
  самой карты: по `chart.birth.time_precision`, у карт, построенных до
  контракта 1.2.1, — по `birth.time_known`, а если нет и его — по
  `asc === null`. Это устройство карты, а не предупреждение.
- **Карта без времени рождения.** `asc`, `mc` и `houses` равны `null`.
- **Неполный ответ.** `mini_reading` и `wheel_url` по контракту обязательны, но
  экран не падает и без них: пустая строка разбора не выводится, вместо колеса
  без адреса — строка «Картинка колеса пока недоступна».

## Оплата и разбор

Правило одно: **ни один экран не решает, оплачено ли.** Что куплено, говорит
сервер — `Me.entitlements` и `Report.is_paid`. Приложение по ним только рисует.

### Пейволл (экран 7)

- **Что продаётся.** Полный разбор (`one_149`, разовая покупка для одной карты)
  и три подписки (`week_149`, `month_399`, `year_2990`). Коды — из `PlanCode`
  контракта (`src/lib/plans.ts`): переименованный код ломает сборку. Подписчику
  подписки не предлагаются; разбор предлагается, только когда пейволл открыт
  ради него (кнопкой под тизером или отказом `402`), и тогда он уже выбран.
- **Цена.** До счёта экран показывает цену из `@astro-soul/shared` — той же
  таблицы, по которой считает сервер. Как только счёт создан, цена — это его
  `stars`. Если она не та, что была на экране, счёт не открывается сам:
  экран показывает цену сервера и ждёт второго нажатия.
- **Счёт.** `POST /billing/invoice` с `plan_code`, а для разбора ещё и с
  `chart_id`: товар привязан к карте. Счёт создаётся по нажатию «Оплатить», а
  не заранее: сервер считает счета (три в час). Созданный счёт экран помнит и
  после отмены открывает его же.
- **Чем закончился счёт** — говорит Telegram, и это не подтверждение оплаты:
  - `paid` — приложение спрашивает сервер (`GET /me`): сразу и ещё раз через
    2 секунды. Сервер выдал купленное — разбор заказывается, подписка
    показывается активной. Не выдал — экран «Платёж обрабатывается. Открой
    приложение через минуту» с кнопкой «Проверить ещё раз». Ничего не
    открывается по одному слову Telegram;
  - `pending` — то же, но вопросов три (`payments.md`, раздел 6);
  - `cancelled` — пользователь передумал: экран остаётся как был, без текста
    ошибки;
  - `failed` — «Платёж не прошёл. Попробуй ещё раз или выбери другой способ»;
  - статус, которого приложение не знает, читается как `pending`.
- **Второй раз за то же не платят.** Пока сервер не подтвердил платёж,
  который Telegram назвал оплаченным, приложение его помнит (до перезагрузки
  страницы): на карте вместо цены — «Платёж обрабатывается» и «Проверить ещё
  раз», пейволл открывается на том же состоянии.
- **Ошибки счёта.** `429` — «Слишком много попыток оплаты. Попробуй через
  час» (свой текст: общий текст сервера говорит «через минуту») и время из
  `details.reset_at`, если сервер его прислал. `422` — «Не удалось создать
  счёт», текст сервера и код обращения; читаются обе формы ответа, с
  `details.field_errors` и без. Сеть и таймаут — повтор той же кнопкой.
- **Вне Telegram** счёт открыть нечем: «Оплата доступна в Telegram» и
  предупреждение в консоли; сервер о счёте не спрашивается. В Telegram старше
  Mini Apps 6.1 — просьба обновить Telegram.

### Разбор (экран 6)

- **Заказ.** `POST /reports` с телом `{chart_id, type: "full"}` и заголовком
  `Idempotency-Key`. Ключ — UUID v4, создаётся в момент нажатия и хранится в
  `sessionStorage` под картой и типом разбора, не дольше 24 часов. Повторное
  нажатие, повтор после ошибки и перезагрузка страницы отправляют тот же ключ.
  Новый ключ — только когда пользователь сам нажимает «Попробовать снова»
  после `failed` или `refunded`.
- **Ответ на заказ** даёт только `report_id`: каков разбор, приложение
  спрашивает следующим запросом, сразу.
- **Опрос.** `GET /reports/{id}`: первый сразу после заказа, следующий через
  2 секунды; пока ответы не приносят нового, пауза удваивается до 10 секунд
  (2, 4, 8, 10, 10…), ответ с новым возвращает её к 2. Пока страница скрыта,
  запросов нет; когда она вернулась — запрос сразу. Уход с экрана отменяет и
  таймер, и запрос в пути. На `ready`, `failed` и `refunded` опрос кончается.
- **Что на экране.** `queued` — «Разбор в очереди»; `generating` — «Пишем
  разбор», полоса с числом сервера и «Готово 3 из 7 глав», под ними главы,
  которые уже пришли; `ready` — оглавление и все главы; `failed` — «Не
  получилось», «Попробовать снова», поддержка и номер разбора; `refunded` —
  «Разбор не получился, звёзды вернулись на счёт», без слова «ошибка».
- **Прогресс** — только число сервера: полоса не движется сама и не показывает
  100, пока сервер не скажет `ready`. Если ответы не меняются дольше минуты —
  «Это дольше обычного, но разбор ещё готовится» и поддержка, без предложения
  платить.
- **Главы** идут по `order`. Глава с ключом, которого сборка не знает,
  показывается как любая другая; для главы, которой нет, ничего не
  подставляется. Текст (`body_md`) превращается в элементы React, строка HTML
  нигде не собирается: теги из текста выбрасываются, от ссылки остаются слова,
  от картинки ничего. Дисклеймер приходит в тексте последней главы, своего
  приложение не добавляет.
- **Неоплаченный разбор.** Главы показываются, только если `is_paid === true`.
  Иначе клиент API отбрасывает главы и ссылку на PDF ещё при чтении ответа
  (`toReport` в `src/api/index.ts`), так что до экрана и до DOM они не доходят,
  что бы ни прислал сервер. От такого разбора видно начало (`teaser`): три
  строки на карте и на экране разбора, и кнопка с ценой.
- **Отказы заказа.** `402` — на пейволл, с объяснением и уже выбранным
  разбором; сразу после покупки `402` значит «платёж ещё не дошёл», и экран
  говорит это. `422` — текст сервера о поле и код обращения. `409` — текст
  сервера как есть. `429` — «Слишком часто, попробуй через минуту».
- **PDF.** Кнопка есть, только когда сервер прислал `pdf_url`. Ссылка живёт в
  памяти. Перед открытием приложение проверяет её (`HEAD`); на `404`
  перечитывает разбор один раз и открывает новую ссылку.
- **Возвращение.** Если `Me.latest_report_id` назван, карта сразу спрашивает о
  нём и показывает, где разбор: «Разбор готов» и «К разбору». Сервер из PR #20
  этого поля не присылает; тогда у купившего на карте кнопка «Получить разбор»,
  и сервер отвечает на заказ тем разбором, который у него уже есть.

### Настройки (экран 9)

Открываются из правого верхнего угла карты и Welcome. Показывают подписку
(план, срок, автопродление; отменить её можно только в Telegram, ссылка
`tg://settings/star_subscriptions`), лимиты из `Me.quotas` («Осталось X из
Y»; `-1` — «Без ограничений», `0` — «Недоступно»), документы, поддержку и
удаление данных.

Удаление — кнопка и два подтверждения подряд (`SPEC.md`, сценарий 6: «двойное
подтверждение»). Кнопка «Удалить мои данные» ничего не удаляет. Первое
подтверждение говорит, что именно удалится, и ведёт дальше («Продолжить»).
Второе — последнее слово: «Удалить навсегда» отправляет `DELETE /me`. На втором
подтверждении «Не удалять» стоит там, где на первом было «Продолжить»: повторное
нажатие по ошибке в то же место данные сохраняет. После `204` —
экран «Данные удалены», последний в этом запуске: событий после него
приложение не отправляет. `409` — текст сервера как есть и поддержка; `401` —
«Сессия истекла, открой приложение заново»; сеть — та же кнопка ещё раз.
Запрос удаления не отменяется, если пользователь ушёл с экрана: чем он
кончился, приложение узнаёт в любом случае.

Пока `VITE_SUPPORT_CONTACT` не задан, кнопка поддержки везде неактивна и
называется «Поддержка скоро появится».

## Согласие и юридические тексты

Экран согласия идёт сразу после Welcome, до первого шага с данными: поиск места
отправляет введённое название на сервер раньше, чем уходит `POST /charts`.

- Галочка по умолчанию не стоит, «Продолжить» неактивна, пока её нет. Отметка
  живёт в памяти вместе с остальными ответами и переживает переход к документу
  и обратно; после перезапуска приложения её нужно поставить снова.
- «Не сейчас» возвращает на Welcome и стирает отметку и всё, что было введено.
- В `POST /charts` уходит `consent: { accepted: true, version }`. `version` —
  константа `CONSENT_VERSION` из `src/i18n/ru.ts`, дата текстов в формате
  `ГГГГ-ММ-ДД`. Без отметки тело запроса не собирается вовсе: `accepted: true`
  никогда не отправляется за пользователя.
- Тексты — дословно `legal-texts-2026-11-10.md` из корня репозитория:
  дисклеймер и строка под кнопкой на Welcome (строка открывает соглашение),
  экран согласия (вводное предложение, четыре пункта и отдельный абзац про
  статистику использования), два экрана документов (абзац на строку файла). Под обоими
  документами выводится строка «Версия документа: …» с той же версией, что уходит
  на сервер. Строка «Поддержка: <контакт>.» не выводится, пока в файле вместо
  контакта стоит заглушка.
- Эти тексты в `ru.ts` не редактируются. Новая формулировка приходит новым
  файлом `legal-texts-<дата>.md` вместе с этой датой в `CONSENT_VERSION` (и в
  `MOCK_CONSENT_VERSION` мока). `tests/legal-texts.test.ts` сверяет каждый текст
  с файлом и хранит SHA-256 текстов под каждой версией: он падает, если текст
  разошёлся с файлом или изменился без смены версии.

### Когда сервер не принимает версию согласия

Юридические тексты — часть сборки, поэтому новые могут прийти только с новой
сборкой. На `422` с полем `consent.version` приложение записывает отклонённую
версию в `sessionStorage` и перезагружает страницу. Дальше — по тому, что
загрузилось:

- **Сборка с другой версией текстов.** Приложение открывается сразу на экране
  согласия: галочка пустая, вверху экрана — «Условия обновились, подтверди ещё
  раз. Данные рождения нужно будет ввести заново.» Введённое до перезагрузки не
  сохраняется нигде, намеренно: данные рождения не кладутся в хранилище
  браузера.
- **Та же сборка** (хостинг ещё отдаёт старую). Экран «Условия обновились» с
  кнопкой «Обновить приложение» и, внутри Telegram, «Закрыть». Сама по себе
  вторая перезагрузка не запускается — иначе был бы цикл.
- **`sessionStorage` недоступен.** Тот же экран показывается сразу, без
  автоматической перезагрузки.

Чтобы это работало, хостинг не должен отдавать `index.html` из кеша без
перепроверки (`Cache-Control: no-cache`); файлы в `assets/` с хешем в имени
можно кешировать надолго. Шаблон такой раздачи — `deploy/nginx.miniapp.conf`
в корне репозитория (его ведёт бэкенд).

Как увидеть руками:

```js
// в консоли браузера, затем перезагрузить страницу
sessionStorage.setItem('astro-soul.consent-refused', '2026-01-01'); // сборка с новыми текстами
sessionStorage.setItem('astro-soul.consent-refused', '2026-11-10'); // та же сборка
```

В моке отказ даёт место `Версионово` или запуск с
`API_MOCK_CONSENT_VERSION=2099-01-01`.

### Что в этих текстах не совпадает с приложением

Решает человек: агенты юридические тексты не пишут и не меняют.

- В `legal.md` (раздел 2) вводное предложение текста согласия осталось на «вы»
  («вашего рождения», «ваше согласие»), остальное переведено на «ты».
  Приложение следует файлу текстов, там это предложение на «ты».
- Версия `2026-11-10` пережила две замены текстов. Владелец решил, что правки
  этой даты (тон, дисклеймер, абзацы про статистику) смысла согласия не меняют,
  и оставил версию прежней (файл текстов, «Ответы на вопросы агентов по
  текстам», п. 2). Хеш этой версии в тесте заменён дважды, с комментарием.
  Дальше любая смысловая правка — новая версия.
- Тексты обещают «Настройки → «Удалить мои данные»». Экран настроек теперь
  есть, кнопка называется так же и вызывает `DELETE /api/v1/me`.
- Тексты обещают, что данные удаляются автоматически после 24 месяцев без
  захода. Это дело сервера; в приложении об этом нет ничего, кроме самих
  текстов.
- Тексты называют статистику использования обезличенной. События уходят с
  первого экрана, до согласия, и сервер хранит их с внутренним `user_id`: так
  решено в `legal.md`, раздел 0. Того, что вводит пользователь, в событиях нет
  (раздел «Продуктовые события»).

## Продуктовые события

Приложение отправляет события из закрытого списка контракта
(`x-analytics-events`) пачками в `POST /events`.

| Когда | Событие |
| --- | --- |
| Запуск | `app_open` |
| Открыт экран | `screen_view {step}`; на экране согласия ещё `consent_view` |
| «Продолжить» на согласии | `consent_accepted {version}` |
| Шаг анкеты пройден | `birth_date_done`, `birth_time_done`, `birth_place_done` |
| Назад (любой кнопкой), «Не сейчас» | `step_back {step}` — экран, с которого ушли |
| Поиск места | `place_search` на каждый ушедший запрос; `place_search_empty`; `place_search_failed {code}` |
| Запрос карты | `chart_requested`, затем `chart_created`, `chart_restored` (карта с такими данными уже была: `is_restored` в ответе) или `chart_failed {code}` |
| Карта открыта при запуске | `chart_restored` |
| Сервер отклонил поля | `validation_failed {step, code, field}` на каждое поле |
| Проверка самого приложения остановила пользователя | `validation_failed_client {step, field}` — пока не уходит на сервер, см. ниже |
| «Поделиться картой» (на карте и на готовом разборе) | `share_clicked` |
| Открыт пейволл | `paywall_view` (вместе с `screen_view {step: paywall}`) |
| Нажато «Оплатить» | `checkout_started {plan_code}` — до запроса счёта |
| Счёт создан, Telegram его показывает | `checkout_opened {plan_code}` |
| Счёт закрыт без оплаты | `payment_cancelled {plan_code}` |
| Сервер выдал купленное | `payment_succeeded {plan_code}` — один раз, когда `GET /me` подтвердил платёж, с какого бы экрана ни пришёл вопрос. Слово Telegram «paid» этим событием не считается |
| Заказ разбора | `report_requested` |
| Сервер отказал в заказе без покупки (`402`) | `quota_exhausted {step: report}` |
| Готовый разбор на экране | `report_ready_view {report_id}` |
| Показана ошибка на пейволле, разборе или в настройках | `error_shown {screen, code}`: `code` — HTTP-статус (`409`, `500`), без ответа сервера — `NETWORK` или `TIMEOUT`, для платежа и разбора — `payment_failed`, `report_failed` |
| Данные удалены | `data_deleted` |

- **Что не уходит никогда:** введённое, найденное и выбранное пользователем,
  содержимое карты, текст разбора, тексты сервера. У `props` семь ключей —
  `step`, `code`, `field`, `version`, `screen`, `plan_code`, `report_id`, — а
  значения берутся из закрытых списков и кодов ошибок; `report_id` выдаёт
  сервер. Всё остальное вырезается перед отправкой.
- **Как уходит.** События копятся в памяти; пачка уходит через 3 секунды после
  первого события в ней или когда набралось 20. Когда страница уходит в фон или
  закрывается, остаток отправляется запросом с `keepalive`. Пачка отправляется
  один раз, ответ и ошибка ни на что не влияют, между запусками ничего не
  хранится. Без `initData` события не собираются.
- **Событие, которое придержано.** `validation_failed_client` — проверка
  самого приложения остановила пользователя (например, «младше 18» на шаге
  даты): одно событие на каждое появившееся сообщение об ошибке, с именем поля
  (`birth_date`, `birth_time`, `time_precision`, `birth_place`) и без причины —
  причина была бы сведением о введённом. В контракте 1.5.1 имя есть, но сервер
  из `main` его не принимает, а на одно незнакомое имя он отвечает `422` всей
  пачке. Поэтому экраны событие сообщают, а очередь его не отправляет: имя
  стоит в списке `HELD_BACK` (`src/analytics/events.ts`). Когда бэкенд
  подтвердит, что имя принято, строку из списка нужно убрать.
- **Удаление данных не удалось.** Отдельного имени для этого в контракте нет,
  и выдумывать его нельзя: уходит `error_shown {screen: settings, code}`.
- **Имена-синонимы.** Контракт 1.5.1 принимает два набора имён
  (`x-event-aliases`). Приложение отправляет `app_open`, `birth_date_done`,
  `birth_time_done`, `birth_place_done`, `screen_view`, `share_clicked`,
  `validation_failed` и не отправляет их синонимы `onboarding_start`,
  `onboarding_birth_date_set`, `onboarding_time_set`, `onboarding_place_set`,
  `mini_reading_view`, `wheel_shared`. `checkout_started` и `checkout_opened`
  записаны там как одно событие под двумя именами; в приложении это два разных
  момента, между ними — запрос счёта, который может не пройти.
- **Чего нет.** У `forecast_view`, `ask_used` и `subscription_expired_seen` в
  приложении пока нет повода: экранов прогноза и вопросов нет.
- **Где события теряются.** Время события — часы устройства; сервер отбрасывает
  события старше суток и опережающие его больше чем на 5 минут, так что с
  устройства, часы которого спешат сильнее, не дойдёт ничего. На Chromium 80 с API на
  другом origin может не дойти последняя пачка при закрытии: там `keepalive`
  не работает для запросов с preflight.

## Поддерживаемые клиенты

Сборка нацелена на Safari 15 (iOS 15) и Chromium 80 (Android WebView). Это
допущение: требований к версиям в `SPEC.md` нет. Vite понижает только синтаксис
и полифилов не добавляет, поэтому код приложения не использует API новее этих
движков, а единственный полифил, без которого SDK на них не стартует
(`Object.hasOwn`), лежит в `src/telegram/polyfills.ts`. Android 9 с ни разу не
обновлённым системным WebView (Chromium 69) не покрыт.

На клиентах Telegram старше Mini Apps 6.1 нет системной кнопки «Назад» —
приложение рисует свою — и нет счетов: пейволл просит обновить Telegram. Если
SDK не принимает параметры запуска (он проверяет их
по строгой схеме), приложение всё равно входит по «сырому» `initData` и работает
как веб-страница внутри Telegram: со своей кнопкой «Назад», без перекраски
шапки клиента.

## Проверка на устройстве

Автотесты идут в jsdom. Вёрстка просмотрена в headless Chromium на 390×844 и
320×568 с моком; там же пройдены отказ по версии согласия с перезагрузкой и
оба варианта запуска после неё, путь вернувшегося пользователя и «Поделиться»
со ссылкой на бота, а доставка событий при уходе со страницы проверена на
стороне сервера.

Пейволл, разбор и настройки пройдены там же, с моком, на обоих размерах. Счёт
«открывал» подставной клиент Telegram: страница получала от него
`invoice_closed` с нужным статусом, как от настоящего. Пройдено: отмена, отказ,
оплата с опозданием подтверждения («Платёж обрабатывается», затем «Проверить
ещё раз»), заказ и разбор от очереди до готового, застрявший разбор (минута
без изменений), `failed` и `refunded`, `402`, `429`, отказ в счёте, другая
цена в счёте, подписка, удаление данных и его отказ `409`, PDF.

С настоящим сервером то же пройдено против бэкенд-PR #20 (в `main` разборов
ещё нет): локальные `apps/api` из PR, Postgres, астро-движок в режиме
`fallback`, подставной провайдер текста (`fake-llm`) и подставной Bot API,
который выдаёт ссылки на счета; оплату серверу сообщал вебхук
`successful_payment`. Пройдено на 390×844 и 320×568: счёт и отмена; оплата с
опозданием вебхука; заказ (`202`) и готовый разбор из семи глав; повторный
заказ тем же ключом; подписка и `402` на заказ разбора по ней; `429` на
четвёртый счёт; удаление (`204`); приём всех пачек событий (`202`). Покупка
пройдена и на том пути, где работает SDK Telegram, и на запасном, без SDK.

Не пройдено с настоящим сервером: разбор, который не удался (`failed`,
`refunded`), `409` при удалении, тизер неоплаченного разбора — их показывал
только мок. Отказ сервера по дате рождения проходился с настоящим API в
итерации 2 и с тех пор не повторялся.

На настоящих клиентах Telegram (iOS, Android, Desktop) приложение не
запускалось. Перед релизом стоит пройти руками:

1. Запуск из бота: экран входа не мигает, шапка и нижняя панель клиента того же
   цвета, что фон приложения.
2. Welcome на маленьком телефоне: дисклеймер 18+ и кнопка видны без прокрутки.
3. Клавиатура на экранах даты и времени: цифровая раскладка, кнопка «Дальше»
   остаётся видна над клавиатурой, фокус сам переходит между полями.
4. Ошибка в поле, предупреждение после «Не знаю» и блок ошибки поиска места
   прокручиваются в видимую область при открытой клавиатуре.
5. Поиск места с открытой клавиатурой: видны ли найденные места и «Ничего не
   нашли». В headless Chromium в окнах 390×450, 360×380 и 320×330 (высота как
   при открытой клавиатуре) они оказались ниже видимой области: под полем
   видна строка «Найдено мест: …», а при пустом результате она пустая.
   Клавиша «Найти» на клавиатуре сворачивает её, а не отправляет форму.
6. Системная «Назад»: возвращает на предыдущий шаг, введённые данные на месте;
   на Welcome и на карте, открытой при запуске, кнопки нет.
7. Свайп вниз по содержимому не закрывает приложение (клиенты с Mini Apps 7.7+).
8. Колесо: SVG с сервера показывается в `<img>`, при обрыве сети — блок с повтором.
9. «Поделиться картой»: открывается выбор чата. Отправляется подписанная ссылка
   на PNG колеса, а в тексте сообщения — ссылка на бота (когда сборка сделана с
   `VITE_BOT_USERNAME`). Проверить, что получатель видит в чате картинку, а
   ссылка на бота открывает приложение, а не только чат с ботом.
10. Тёмная и светлая темы клиента: приложение всегда тёмное, контраст шапки в норме.
11. VoiceOver / TalkBack: заголовок экрана читается при переходе, ошибки и
    статус поиска объявляются.
12. Экран согласия на маленьком телефоне: текст прокручивается, галочка,
    «Продолжить» и «Не сейчас» остаются на месте; галочка читается вместе со
    своей подписью.
13. Документы с экрана согласия: «Назад» возвращает к согласию, отмеченная
    галочка на месте. В тексте согласия видна стрелка «Настройки → …»: в
    headless Chromium без системных шрифтов на её месте был пробел.
14. Отказ по версии согласия на настоящем клиенте: после перезагрузки внутри
    Telegram приложение снова входит (параметры запуска на месте) и показывает
    экран согласия с пояснением либо экран «Условия обновились».
15. Welcome: строка «Подробнее — в пользовательском соглашении.» нажимается
    пальцем и открывает соглашение; «Назад» возвращает на Welcome.
16. Повторный запуск из бота после построенной карты: открывается сразу карта.
    «Ввести данные рождения заново» под ней ведёт на экран согласия с пустой
    галочкой, «Не сейчас» возвращает к карте.
17. Экран согласия на обычном телефоне: ссылки на документы стоят под абзацем
    про статистику и на части экранов уходят под нижнюю панель — видно ли, что
    текст прокручивается.
18. Оплата в тестовом боте, каждым из трёх исходов: оплатить, закрыть счёт,
    счёт с отказом. После оплаты разбор заказывается сам, после закрытия на
    экране нет текста ошибки. Это единственная проверка настоящего
    `openInvoice`: в браузере его играл подставной клиент.
19. Знак ⭐ в ценах: в headless Chromium без системных шрифтов на его месте
    пусто, цена выглядит как «149».
20. Разбор на телефоне: главы появляются по одной; когда разбор готов и над
    главами встаёт оглавление, текст под глазами не прыгает (на iOS особенно:
    там прокрутку удерживает само приложение).
21. Telegram свёрнут во время разбора и развёрнут обратно: экран сразу
    показывает, что успело измениться.
22. Настройки → «Открыть подписки в Telegram»: открывает ли клиент ссылку
    `tg://settings/star_subscriptions`. На iOS, Android и Desktop отдельно.
23. Код обращения на экране ошибки: тап копирует его в буфер.
24. Welcome на маленьком телефоне после появления «Настроек» в углу: заголовок
    и первые пункты видны, остальные прокручиваются.

## Что намеренно не сделано

- Экран прогноза и «спроси карту» (экран 8, `/engagement/*`). Пейволл при этом
  уже продаёт подписку, которая обещает прогнозы, вопросы и совместимость.
- Тизер до первой покупки. Начало разбора (`teaser`) приходит только вместе с
  разбором, а разбор сервер создаёт только после покупки. У того, кто ещё не
  платил, на карте под заголовком «Полный разбор» текста нет: только кнопка с
  ценой.
- «Восстановить карту» в настройках.
- Совместимость и карта года (`compat_249`, `solar_590`): сервер их пока не
  собирает, приложение не продаёт.
- Анкета, заполненная данными уже построенной карты: «Ввести данные рождения
  заново» открывает пустую анкету.
- Память о неподтверждённом платеже через перезагрузку страницы: после неё
  карта снова показывает цену, если сервер платёж ещё не обработал.

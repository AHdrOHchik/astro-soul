# apps/web — Mini App «Разбор личности»

Клиент Telegram Mini App. Закрывает экраны 1–9 из `SPEC.md` и экран
согласия на обработку персональных данных: Welcome → согласие → BirthDate →
BirthTime → BirthPlace → Chart (карточка прогноза, колесо, три карточки, блок
полного разбора, «Поделиться»), дальше Forecast (прогноз на день) и Ask
(«спроси карту»), Paywall (покупка разбора и подписки), Report (заказ разбора
и сам разбор) и Settings (подписка, лимиты, документы, поддержка, удаление
данных). Тот, у кого карта уже есть, попадает сразу на неё. По пути
приложение отправляет продуктовые события. Приложение написано под контракт
`api.openapi.yaml` версии 1.5.5.

Код живёт в двух пакетах:

| Пакет | Что внутри |
| --- | --- |
| `apps/web` (`@astro-soul/web`) | Приложение: экраны, клиент API, обёртка над Telegram, тексты, токены темы, мок API для разработки |
| `packages/ui` (`@astro-soul/ui`) | UI-кит без текстов и без сети: кнопки, поля, карточки, каркас экрана, состояния. Здесь же базовый `tsconfig` фронтенда и его слой правил ESLint (`eslint.frontend.mjs`) |

Из остального монорепо приложение берёт `@astro-soul/shared` (цены планов,
границы длины запроса в поиске места), `api.openapi.yaml` (типы API) и
`legal-texts-<версия>.md` (юридические тексты, с ними сверяется тест).

## Запуск

Нужны pnpm 9 (`packageManager` в корневом `package.json`) и Node 22 не ниже
22.22.2: нижнюю границу задаёт jsdom 31, на котором идут тесты, верхнюю (`<23`) —
`engines` корневого `package.json`.

```sh
pnpm install
pnpm --filter @astro-soul/shared build   # один раз и после правок в packages/shared

# с моком вместо бэкенда, в обычном браузере
API_MOCK=1 VITE_DEV_INIT_DATA=mock-init-data pnpm --filter @astro-soul/web dev

# то же, но с «оплатой» без Telegram: весь путь от цены до готового разбора в браузере
API_MOCK=1 VITE_DEV_INIT_DATA=mock-init-data VITE_DEV_INVOICE=paid pnpm --filter @astro-soul/web dev

# с подписками на пейволле: без VITE_SUBSCRIPTIONS=enabled их не продаёт и dev-сервер
API_MOCK=1 VITE_DEV_INIT_DATA=mock-init-data VITE_DEV_INVOICE=paid VITE_SUBSCRIPTIONS=enabled pnpm --filter @astro-soul/web dev

# с настоящим API (по умолчанию проксируется http://localhost:8080)
API_PROXY_TARGET=http://localhost:8080 VITE_DEV_INIT_DATA='<initData>' pnpm --filter @astro-soul/web dev
```

`@astro-soul/shared` подключается собранным, из своего `dist/`. Пока он не
собран, не работают ни `dev`, ни `typecheck`, ни `test`, ни корневой `pnpm lint`.
Dev-сервер кладёт пакет в свой кеш зависимостей и изменений в нём не замечает
даже после обычного перезапуска: после пересборки `packages/shared` запускайте
`pnpm dev --force`.

Те же переменные можно положить в `apps/web/.env` (шаблон — `.env.example`,
сам `.env` в git не попадает). `initData` — это учётные данные: строка входит
от имени своего пользователя, поэтому берите её только от тестового аккаунта.
API принимает только строку, подписанную токеном того бота, с которым он запущен
(`TELEGRAM_BOT_TOKEN`), и не старше 24 часов.

Приложение вызывает `GET /me`, `DELETE /me`, `GET /charts/current`,
`POST /geo/resolve`, `POST /charts`, `POST /billing/invoice`, `POST /reports`,
`GET /reports/{id}`, `GET /engagement/forecast`, `POST /engagement/ask` и
`POST /events`; колесо показывает по `wheel_url` из ответа, а делится
картинкой по `wheel_png_url`. Чтобы API построил карту, рядом
с ним должен работать астро-движок (`pnpm dev:astro` из корня); как поднять
API, движок и базу — в корневом `README.md`.

Сервер из `main` (контракт 1.5.5) умеет всё перечисленное. С настоящим
сервером приложение проверялось до экрана 7 включительно и в настройках
(раздел «Проверка на устройстве»); прогноз и вопросы пройдены только с моком.
Серверу старше 1.5.1 это приложение не подходит: он не знает разборов и
принимает события только с полем `at`, а не `occurred_at`.

| Команда (из `apps/web`) | Что делает |
| --- | --- |
| `pnpm dev` | Dev-сервер Vite |
| `pnpm build` | Четыре строки о том, с чем собирается бандл (раздел «Сборка для выпуска»), проверка типов, продакшен-сборка в `dist/`, затем `scripts/check-bundle.mjs` |
| `pnpm preview` | Раздать собранный `dist/` |
| `pnpm clean` | Удалить `dist/` (его же вызывает корневой `pnpm clean`) |
| `pnpm typecheck` | Сверка типов API с контрактом и `tsc` отдельно для кода приложения и для Node-части (конфиг Vite, мок, скрипты сборки, тесты-охранники) |
| `pnpm test` | Vitest: компонентные и модульные тесты |
| `pnpm size` | Только проверка собранного `dist/` |
| `pnpm gen:api` | Перегенерировать `src/api/schema.gen.d.ts` из `api.openapi.yaml` |

Из корня репозитория `pnpm build | typecheck | test` запускают одноимённые
скрипты во всех пакетах; корневому `pnpm test` нужна ещё и тестовая база для
`apps/api` (см. корневой `README.md`).

Линт один на весь монорепо: `pnpm lint` из корня. Своего конфига ESLint у
фронтенда нет. Корневой `eslint.config.mjs` подключает слой
`packages/ui/eslint.frontend.mjs`, который добавляет к общим правилам
`strictTypeChecked` из typescript-eslint и правила React Hooks — только для
`apps/web` и `packages/ui`. `eslint` в `devDependencies` пакета `packages/ui`
закрывает peer-зависимость `eslint-plugin-react-hooks`. Диапазон версий там
должен совпадать с корневым: с другим диапазоном pnpm ставит в репозиторий
вторую копию ESLint.

## Переменные окружения

| Переменная | Где действует | Назначение |
| --- | --- | --- |
| `VITE_API_BASE_URL` | бандл | Origin API без `/api/v1`. Пусто — тот же origin, что у страницы |
| `VITE_BOT_USERNAME` | бандл | Имя бота, с `@` или без. С ним «Поделиться картой» добавляет к сообщению ссылку `https://t.me/<имя>?startapp=chart_<chart_id>`. Пусто — уходят только картинка и текст. Значение, которое не является именем (например, ссылка на бота), останавливает сборку |
| `VITE_SUPPORT_CONTACT` | бандл | Куда ведёт «Написать в поддержку»: имя в Telegram (с `@` или без) или ссылка `https://…`. Пусто — кнопка есть, но неактивна и называется «Контакт поддержки ещё не задан». Любое другое значение останавливает сборку |
| `VITE_SUBSCRIPTIONS` | бандл | Продаёт ли сборка подписки. Продаёт только при значении `enabled`. Не задана, пусто или `off` — не продаёт: пейволл продаёт только полный разбор, подписку не предлагает ни один экран; подписка, которая у пользователя уже есть, показывается как обычно. Любое другое значение (`of`, `OFF`, `0`, `yes`) останавливает и сборку, и dev-сервер |
| `VITE_DEV_INIT_DATA` | только dev-сборка | Строка `initData` для запуска вне Telegram. В продакшен-бандл не попадает: `pnpm build` падает, если попала |
| `VITE_DEV_INVOICE` | только dev-сборка | Чем заканчивается «оплата» вне Telegram: `paid`, `cancelled`, `failed` или `pending`. При `paid` dev-сборка ещё и сообщает моку, что счёт оплачен. Пусто — пейволл говорит «Оплата доступна в Telegram». В продакшен-бандл не попадает |
| `API_PROXY_TARGET` | dev-сервер | Куда проксировать `/api`, когда мок выключен |
| `API_MOCK` | dev-сервер, `vite preview` | `1` — отвечать моком из `mock/` |
| `API_MOCK_DELAY` | мок | Задержка ответа в мс (по умолчанию 400), чтобы были видны состояния загрузки |
| `API_MOCK_ME` | мок | Кто пользователь мока, слова через запятую: `401`, `500` (`GET /me` падает), `returning` (карта уже есть), `paid` (карта и купленный для неё разбор), `subscriber` (карта и подписка на месяц); пусто — новый пользователь |
| `API_MOCK_REPORT` | мок | Чем заканчивается каждый разбор: `ready` (по умолчанию), `failed`, `refunded`, `stuck` (застрял на двух главах) |
| `API_MOCK_REPORT_CHAPTER_MS` | мок | Сколько длится одна глава разбора, мс (по умолчанию 2500) |
| `API_MOCK_INVOICE` | мок | `POST /billing/invoice`: `422` (без `field_errors`), `500`, `price` (счёт на 50 ⭐ дороже ожидаемого) |
| `API_MOCK_FORECAST` | мок | `GET /engagement/forecast`: `auto` (по умолчанию: как на сервере, см. «Мок API»), `ready` (прогноз есть всегда), `pending` (`404` «ещё готовится»), `stale` (прогноз со вчерашней датой), `500` |
| `API_MOCK_DELETE` | мок | `DELETE /me`: `409` (с текстом сервера и `details.reason: refund_failed`), `401`, `500`; пусто — всё удаляется, вместе с подпиской и покупками (контракт 1.5.5) |
| `API_MOCK_PDF` | мок | `1` — у готового разбора есть PDF (в `apps/api` его пока нет) |
| `API_MOCK_CONSENT_VERSION` | мок | Версия согласия, которую мок принимает в `POST /charts` (по умолчанию — версия текстов приложения). Другая дата — «сервер с более новыми текстами»: любой запрос карты получит отказ по `consent.version` |

### Сборка для выпуска

В репозитории нет ни файла, ни задания CI, которые задавали бы значения для
выпуска: `.env` в git не попадает, а имя бота нельзя вписывать в код
(`legal-texts-2026-11-10.md`). Значения приходят из окружения того, кто
собирает `dist/`:

```sh
VITE_SUPPORT_CONTACT=@astro_soul_support \
VITE_BOT_USERNAME=wildcard_astro_soul_bot \
pnpm --filter @astro-soul/web build
# с продажей подписок — добавить VITE_SUBSCRIPTIONS=enabled
```

**По умолчанию подписки не продаются.** Продажу включает только
`VITE_SUBSCRIPTIONS=enabled`; забытая переменная — это сборка без подписок.
Ошибиться в эту сторону дёшево (продажа откладывается до следующей сборки), в
обратную — дорого (деньги взяты, их надо возвращать).

Забытая переменная сборку не останавливает (приложение работает и без неё),
поэтому первым делом, до проверки типов и до Vite, сборка пишет четыре строки —
с чем она сделана. Сборка без единой переменной:

```
subscriptions: OFF (set VITE_SUBSCRIPTIONS=enabled to sell)
support:       NOT SET → кнопка поддержки будет неактивна
bot:           NOT SET → «Поделиться» уйдёт без ссылки на бота
consent:       2026-11-10
```

Сборка с продажей подписок и обоими значениями:

```
subscriptions: ON SALE
support:       @astro_soul_support
bot:           @wildcard_astro_soul_bot
consent:       2026-11-10
```

`ON SALE` и `NOT SET` в этих строках — повод остановиться и проверить
окружение до выкладки. `consent` — версия текстов согласия, с которой собран
бандл (`CONSENT_VERSION`); она должна совпадать с версией сервера.

Строки собирает одна функция, `readBuildSettings` (`scripts/buildSettings.ts`):
её вызывают и первый шаг `pnpm build` (`scripts/print-build-settings.ts`), и
`vite.config.ts` — так что голый `vite build` пишет те же строки, а значение,
которое нельзя прочитать, останавливает и сборку, и dev-сервер. Тесты проверяют
саму функцию (`tests/build-settings.test.ts`), а не вывод сборки.

Секретов у клиента нет. Вход — только по `initData`: приложение держит строку
в памяти и отправляет заголовком `X-Telegram-Init-Data`, токенов не получает и
ничего не кладёт в `localStorage` и cookie. В `sessionStorage` приложение пишет
два ключа. `astro-soul.consent-refused` — версия согласия, которую отклонил
сервер, на время перезагрузки (раздел «Согласие и юридические тексты»).
`astro-soul.report-key.full.<chart_id>` — ключ идемпотентности заказа разбора
и время его создания (раздел «Оплата и разбор»): случайный идентификатор под
идентификатором карты. Данные рождения, текст разбора и ссылка на PDF туда не
попадают. Сам SDK Telegram сохраняет там же копию
параметров запуска (в них есть `initData`), чтобы пережить перезагрузку
страницы; она исчезает вместе с окном Mini App.

## Мок API

`mock/` — middleware dev-сервера, которое отвечает на `/api/v1/*` данными,
типизированными по `src/api/schema.gen.d.ts`: поле, которого нет в контракте,
не пройдёт `pnpm typecheck`. Мок ничего не считает: позиции планет в нём
условные, на колесе написано MOCK, а текст разбора прямо говорит, что он не
разбор. Тексты ошибок и строки короткого разбора — те же, что отдаёт
`apps/api`, в том числе для разборов, счетов и удаления.
В продакшен-бандл мок не входит.

Мок помнит своего пользователя, пока его не перезапустили: построенную карту
(после неё `GET /me` отвечает `has_chart: true`, `GET /charts/current` отдаёт
эту карту, а `POST /charts` с теми же данными — её же с кодом `200` и
`is_restored: true`), купленное, заказанные разборы. Поэтому перезагрузка
страницы после построения карты открывает сразу карту.

Начать заново с другим сценарием можно без перезапуска: открыть в браузере
`/api/v1/__mock/reset?me=paid&report=failed` и перезагрузить приложение.
Параметры — те же, что в переменных: `me`, `report`, `invoice`, `delete`,
`forecast`, `pdf=1`, `chapter_ms`. Без параметров — новый пользователь и
разбор, который удаётся.

Сценарии включаются вводом на экранах:

| Где | Что ввести | Что произойдёт |
| --- | --- | --- |
| Поиск места | `Мо`, `Ка`, `Но`, `Са`, `Ек`, `Вл`, `Ал`, `Ми`, `Ам` | Обычная выдача (поиск по началу названия, с двух символов) |
| Поиск места | любое другое, например `Ъъъ` | `200` с пустым списком → «Ничего не нашли» |
| Поиск места | `ошибка…` | `500` → ошибка с повтором |
| Поиск места | `лимит…` | `429 RATE_LIMITED` |
| Поиск места | `провайдер…` | `503 GEO_NOT_FOUND` с `details.reason: provider_timeout`: справочник мест недоступен → ошибка с повтором |
| Выбор места | `Ошибинск` | `POST /charts` → `500` |
| Выбор места | `Датино` | `422`, отклонено поле `birth_date` → шаг «Дата рождения» с текстом сервера |
| Выбор места | `Времянск` | `422`, отклонено поле `birth_time` → шаг «Время рождения» |
| Выбор места | `Отказово` | `422`, отклонено поле `birth_place` → шаг «Место рождения» |
| Выбор места | `Согласово` | `422`, отклонено поле `consent` → экран согласия |
| Выбор места | `Версионово` | `422`, отклонено поле `consent.version` → приложение перезагружается; сборка та же, поэтому дальше экран «Условия обновились» с кнопкой «Обновить приложение» |
| Выбор места | `Пустошь` | `201` с пустой картой → пустое состояние |
| Выбор места | `Безколёсово` | Карта есть, картинка колеса не грузится |
| Выбор места | `Примерново` | Карта с предупреждением `approximate_place` и ещё одним кодом, которого нет в контракте: приложение показывает первое и пропускает второй |
| Время | «Не знаю» | Карта без Асцендента и домов, предупреждение `no_birth_time` |
| Время | «Знаю примерно» | Предупреждение `approximate_time` |
| Запуск | `API_MOCK_ME=returning` | Карта уже есть: приложение открывается на ней |

Разбор, оплата и удаление — сценарии запуска (переменные или `__mock/reset`):

| Сценарий | Что произойдёт |
| --- | --- |
| `me=paid` | На карте «Получить разбор»: заказ принимается, разбор пишется по главе за `chapter_ms` |
| `me=returning` | На карте цена: `POST /reports` без покупки — `402` |
| `me=subscriber` | Подписка на месяц: в настройках план и срок, пейволл продаёт только разбор |
| `report=failed` | Разбор падает после двух глав: экран «Не получилось» |
| `report=refunded` | То же, а через 4 секунды разбор становится `refunded`, покупка отзывается |
| `report=stuck` | Разбор останавливается на двух главах: через минуту — «Это дольше обычного…» |
| `invoice=422`, `invoice=500`, `invoice=price` | Отказ в счёте без `field_errors`; ошибка сервера; счёт дороже, чем ждёт приложение |
| четвёртый счёт подряд | `429`, как в `apps/api` (не больше трёх счетов в час) |
| `delete=409`, `delete=401`, `delete=500` | Отказы `DELETE /me` |
| `pdf=1` | У готового разбора есть ссылка на PDF |

Прогноз и вопросы мок отдаёт по правилам `apps/api` (`modules/engagement`), но
ничего не считает и модель не зовёт: текст прогноза и ответ прямо говорят, что
они — мок.

| Сценарий | Что произойдёт |
| --- | --- |
| `forecast=auto` (по умолчанию) | Прогноз есть только у карты, с которой мок запущен (`me=returning`, `paid`, `subscriber`): её «ночь уже прошла». Без подписки — короткий текст без фокуса (`is_paid: false`), с подпиской — полный, с фокусом. У карты, построенной в этом запуске, прогноза нет: `404` «Прогноз на сегодня ещё готовится» |
| `forecast=ready` | Прогноз есть у любой карты |
| `forecast=pending` | `404` «ещё готовится» для любой карты → «Сегодняшний прогноз готовится» |
| `forecast=stale` | Прогноз со вчерашней датой: сервер так не отвечает, но так выглядит прогноз, оставшийся на экране после полуночи → «Прогноз на 13 ноября», без слова «сегодня» |
| `forecast=500` | Ошибка сервера → «Не получилось загрузить прогноз» с повтором |
| `me=returning` | Один вопрос в день (`ask_daily`: 0 из 1) |
| `me=subscriber` | Пять вопросов в день, два уже заданы: счётчику есть что показать |

Квота вопросов сбрасывается в полночь по часовому поясу места рождения карты
(без карты — по UTC), как на сервере.

| Вопрос | Что произойдёт |
| --- | --- |
| обычный, от 3 до 500 знаков | `200`: ответ, `based_on` из позиций карты, вопрос засчитан |
| короче 3 знаков | `422`, отклонено поле `question` → текст сервера под полем |
| со словом про здоровье, смерть, гарантии денег или суд («диагноз», «умру», «крипта», «иск в суд») | `200` с мягким отказом вместо ответа, без `based_on`; вопрос не засчитан |
| когда вопросы на день кончились | `429 QUOTA_EXCEEDED` с `details.reset_at` |
| начинается с `лимит` | `429 QUOTA_EXCEEDED` «Вопросы временно недоступны»: месячный бюджет сервиса, а не лимит пользователя |
| начинается с `ошибка` | `500` |

Чужая или удалённая карта: `404` «Такой карты нет. Построй карту заново» на
прогноз, на вопрос и на заказ разбора, `422` по полю `chart_id` на счёт за
разбор, `404` «Такого разбора нет» на разбор. Проверить «данные удалены на
другом устройстве»: открыть приложение и отправить со стороны
`DELETE /api/v1/me` с заголовком `X-Telegram-Init-Data` (значение любое) —
например, `curl -X DELETE -H 'X-Telegram-Init-Data: x'
http://localhost:5173/api/v1/me`. Следующее действие в приложении — прогноз,
вопрос, разбор, счёт, настройки — ведёт на Welcome, и ни один текст сервера о
пропавшей карте или разборе на экран не попадает.

После удаления мок, как сервер с контракта 1.5.5, не помнит о пользователе
ничего: ни карты, ни подписки, ни купленного разбора, ни прогноза (те же
данные рождения, введённые заново, — новая карта без прогноза), а счёт,
выставленный до удаления, после него ничего не покупает.

Разбор, которого у сервера больше нет (`404` на `GET /reports/{id}`), при
карте, которая на месте, отдельного сценария не требует. С `me=paid` получить
разбор и вернуться на карту; в соседней вкладке открыть
`/api/v1/__mock/reset?me=paid` — мок начал заново и разбор забыл, а открытое
приложение его id ещё держит. «К разбору» после этого открывает экран с
кнопкой «Получить разбор», без ошибки: приложение спросило `GET /me`, карта
есть, значит пропал только разбор.

Оплату мок сам не проводит: счёт становится оплаченным, когда об этом сообщит
«Telegram» — запрос `POST /api/v1/__mock/payments {invoice_link, delay_ms}`. Его
отправляет dev-сборка с `VITE_DEV_INVOICE=paid`; `delay_ms` играет вебхук,
который опаздывает. `POST /api/v1/__mock/revoke` отзывает покупку разбора, как
возврат через поддержку: от разбора остаётся то, что сервер показывает
неоплаченным, — тизер. Оба адреса — не часть API.

`Me.entitlements.full_report_chart_id` мок отдаёт в каждом ответе, как сервер с
контракта 1.5.4: карта, за которую куплен разбор, или `null`. У каждого набора
данных рождения в моке свой `chart_id` (те же данные — тот же id; у карты, с
которой мок запущен, — `00000000-0000-4000-8000-00000000c0de`), так что случай
«разбор куплен по другой карте» виден в браузере: запустить с `me=paid`,
нажать «Ввести данные рождения заново» и построить карту с другой датой. `Me` по-прежнему
отдаёт `full_report: true` и `full_report_chart_id` первой карты, а на новой
карте — цена; заказ разбора по ней мок отклоняет `402`, как сервер.

Мок проверяет форму тела `POST /charts`: без `consent`, без `time_precision`
или со временем при `unknown` он отвечает `422` с `details.field_errors`; версию
согласия он сверяет со своей (`API_MOCK_CONSENT_VERSION`). Возраст и часовой
пояс он не проверяет — эти отказы сервера показывают сценарии из таблицы.

`POST /events` мок разбирает по правилам контракта: неизвестное имя или
неверная форма события — `422` на всю пачку; событие с запрещённым ключом в
`props`, старше суток или из будущего молча отбрасывается; в ответе `202` с
числом принятых. `GET …/wheel.png` отдаёт настоящий PNG с условным колесом; `size`
— только 1080 или 1600, иначе `422`, как в контракте. `limit` в поиске места вне
1…10 — тоже `422`.

Без заголовка `X-Telegram-Init-Data` мок отвечает `401`, как требует контракт.
Поэтому продакшен-сборка, открытая через `API_MOCK=1 pnpm preview` в обычном
браузере, показывает экран «Открой приложение в Telegram» — так и должно быть.

### Правила, за которыми следят тесты и сборка

- **Токены.** Цвета, размеры, длительности и градиенты задаются только в
  `src/theme.css`; в остальных CSS — только `var(--…)`. Инлайновых `style` нет.
- **Тексты.** Вся кириллица — в `src/i18n/`. В остальном коде приложения и
  UI-кита её нет даже в комментариях (в тестах можно).
- **Старые движки.** В CSS не используются flex-`gap`, `aspect-ratio`, `inset`,
  `:has()`, `:is()`/`:where()`, `@layer`, `@container`, вложенность.
- Всё это проверяет `tests/design-system.test.ts`; он же ловит неопределённые и
  неиспользуемые токены.
- **Контракт.** `pnpm typecheck` (а значит и `pnpm build`) падает, если
  `src/api/schema.gen.d.ts` разошёлся с `api.openapi.yaml`. После изменения
  контракта — `pnpm gen:api`.
- **Юридические тексты.** Тексты Welcome (дисклеймер и строка под кнопкой),
  экрана согласия и экранов документов дословно совпадают с
  `legal-texts-<версия>.md`, а изменить их, не тронув хэш версии, нельзя — это
  проверяет `tests/legal-texts.test.ts` (подробнее — в разделе «Согласие и
  юридические тексты»).
- **Настройки сборки.** Подписки продаёт только `VITE_SUBSCRIPTIONS=enabled`;
  значение, которое нельзя прочитать, останавливает сборку; четыре строки
  сборки — ровно те, что в разделе «Сборка для выпуска». Это проверяют
  `tests/build-settings.test.ts`, `src/lib/subscriptions.test.ts` и
  `src/config.test.tsx`.
- **События.** Имена событий в приложении — ровно список `x-analytics-events`
  контракта, а среди ключей `props` нет ни одного из
  `x-events-forbidden-prop-keys` — это проверяет `tests/contract.test.ts`. Он же
  сверяет ссылку на бота с шаблоном `x-bot.share_link_template`.
- **Бандл.** `scripts/check-bundle.mjs` падает, если `dist/` больше 350 кБ gzip
  (лимит из `SPEC.md`) или содержит dev-переменные. `pnpm build` собирает
  продакшен-бандл при любом `NODE_ENV`: без этого сборка с `NODE_ENV=test`
  (так запускает CI) включала в бандл отладочную сборку React.

### Как приложение читает ответы API

- **Ошибки** разбираются по `Problem.code`, а по HTTP-статусу — только если в
  ответе нет тела `Problem` с известным кодом (так может ответить прокси перед
  API). Тогда 401, 402, 403, 404, 409, 422 и 429 дают свои коды, любой другой
  статус — `INTERNAL`. `400` API не использует, поэтому «голый» 400 — тоже
  `INTERNAL`, а не «проверь данные».
- **Текст ошибки.** `Problem.message` — готовый текст для пользователя,
  приложение показывает его как есть. Исключение — текст без единой
  кириллической буквы: так отвечает не API, а прокси или фреймворк, и вместо
  него показывается свой текст. `request_id` виден на экране ошибки как «Код
  обращения», мелким шрифтом; тап копирует его. Берётся он из `Problem`, а
  если у ответа нет такого тела — из заголовка `X-Request-Id`.
- **Конфликт (`409`).** Экран ошибки сам добавляет кнопку поддержки и не
  предлагает «Попробовать ещё раз»: на сервере что-то мешает, и повтор запроса
  этого не сдвинет. Пользователь не остаётся с одним текстом (находка QA-002).
- **Отказ по полям.** `POST /charts` может ответить `422` со списком
  `details.field_errors`. Приложение возвращает пользователя на самый ранний
  экран, поле которого отклонено (`consent` — согласие, `birth_date` — дата,
  `birth_time` и `time_precision` — время, `birth_place` — место), и показывает
  текст сервера у этого поля; фокус встаёт на поле. Текст исчезает, когда поле
  меняют, а новая отправка стирает все такие тексты. Если сервер назвал только
  поля, которых нет ни на одном экране, ошибка показывается на экране карты.
  Отказ по полю `query` в поиске места показывается у строки поиска.
- **Версия согласия.** Отказ по полю `consent.version` значит, что тексты этой
  сборки устарели. Исправить его на экране нельзя, поэтому он важнее остальных
  полей того же ответа: приложение перезагружается (раздел «Согласие и
  юридические тексты»).
- **Возраст.** Шаг даты считает так же, как контракт: взрослый — с 00:00
  UTC дня восемнадцатилетия (`Date.UTC(год + 18, месяц, день)`, для 29 февраля
  это 1 марта); дата «в будущем» — позже сегодняшнего дня по UTC. Проверка на
  клиенте только экономит запрос — решает сервер, и его отказ по `birth_date`
  приложение покажет на том же шаге.
- **Поиск места.** Запрос уходит с двух символов (без пробелов по краям) и не
  длиннее 120 — границы взяты из `@astro-soul/shared`, по ним же проверяет
  сервер. `200` с пустым списком — «ничего не нашли». `503` с кодом
  `GEO_NOT_FOUND` значит, что справочник мест недоступен: это ошибка с кнопкой
  повтора, а не пустой результат. Причина из `details.reason` пользователю не
  показывается.
- **Конверт карты.** `POST /charts` (и `201`, и `200`) и `GET /charts/current`
  отдают один объект, и читает его одна функция. Была ли карта уже построена,
  говорит `is_restored` в теле, а не код ответа. `404` на `GET /charts/current`
  — не ошибка, а «карты ещё нет».
- **Вернувшийся пользователь.** Если `GET /me` говорит, что карта есть
  (`has_chart` или `chart_id`), приложение открывается на экране карты и
  запрашивает `GET /charts/current`. Новому пользователю этот запрос не
  отправляется. Если карты всё же нет (`404`), начинается обычный путь с
  Welcome. Под такой картой есть кнопка «Ввести данные рождения заново»: она
  ведёт на экран согласия, анкета за ней пустая.
- **Картинка для шаринга.** «Поделиться картой» отправляет `wheel_png_url`:
  PNG чат показывает картинкой. Если сервер его не прислал, уходит ссылка на
  SVG (`wheel_url`). Когда задан `VITE_BOT_USERNAME`, к тексту сообщения
  добавляется ссылка на бота по шаблону контракта; адресом сообщения остаётся
  картинка.
- **Повторы.** Ответ 5xx клиент повторяет до двух раз (через 0,3 и 0,9 с) и
  только потом показывает ошибку. Ответы с другими статусами не повторяются.
  Никогда не повторяются `POST /events` (повторённая пачка посчиталась бы
  дважды), `POST /billing/invoice` (сервер считает счета), `DELETE /me` и
  `POST /engagement/ask` (вопрос, который дошёл до сервера, мог быть засчитан,
  а ключа идемпотентности у него нет): повторить их может только
  пользователь, кнопкой. `POST /reports` повторяется с тем же ключом
  идемпотентности.
- **Прогноз.** `404` на `GET /engagement/forecast` — не ошибка, а «прогноза
  ещё нет»: клиент API возвращает `null` и запрос не повторяет. Из ответа
  берутся `date`, `text`, `focus` и `is_paid`; ответ без текста или без даты —
  ошибка `INVALID_RESPONSE`. `focus` с кодом, для которого у сборки нет слова,
  читается как «фокуса нет»: код на экран не выводится. Код контракта `health`
  клиент API отдаёт приложению как `wellbeing` (`FOCUS_BY_CODE` в
  `src/api/index.ts`): на экране это «самочувствие», и слово «health» в коде
  приложения дальше клиента API не встречается. Полным прогноз считается,
  только если сервер прислал ровно `is_paid: true`.
- **Ответ на вопрос.** Из `200` берутся `answer` и `based_on` (только
  непустые строки). Пустой `answer` — `INVALID_RESPONSE`. `quota` из ответа
  не читается: счётчик берётся из `Me.quotas`.
- **`Me`.** Права (`entitlements.is_active`, `entitlements.full_report`) считаются
  выданными, только если сервер прислал ровно `true`; чего в ответе нет, того
  нет. `entitlements.full_report_chart_id` — непустая строка или `null`: поле,
  которого в ответе нет, читается как `null`. Оплачен ли разбор карты, решает
  только оно (раздел «Разбор куплен для карты»). `Me` перечитывается после
  оплаты и при открытии настроек.
- **Предупреждения к карте.** Экран карты показывает то, о чём предупреждает
  сервер (`warnings`), в его порядке, и своих предупреждений не добавляет.
  Слова есть для трёх кодов: `no_birth_time`, `approximate_time`,
  `approximate_place`. Код, которого сборка не знает, пропускается: сервер
  может добавлять новые. Список известных кодов — `CHART_WARNINGS` в
  `src/api/index.ts`, тексты — `chart.warnings` в `ru.ts`.
- **Точность времени.** Выбранный на шаге времени вариант уходит в `POST /charts`
  как `time_precision` (`exact`, `approximate`, `unknown`). Было ли у карты
  время рождения — а значит, есть ли у неё Асцендент и дома, — экран читает из
  самой карты: по `chart.birth.time_precision`, у карт, построенных до
  контракта 1.2.1, — по `birth.time_known`, а если нет и его — по
  `asc === null`. Это устройство карты, а не предупреждение.
- **Карта без времени рождения.** `asc`, `mc` и `houses` равны `null`.
- **Неполный ответ.** `mini_reading` и `wheel_url` по контракту обязательны, но
  экран не падает и без них: пустая строка разбора не выводится, вместо колеса
  без адреса — строка «Картинка колеса пока недоступна».

## Оплата и разбор

Правило одно: **ни один экран не решает, оплачено ли.** Что куплено, говорит
сервер — `Me.entitlements` и `Report.is_paid`. Приложение по ним только рисует.

### Разбор куплен для карты

Полный разбор покупается для одной карты, и сервер называет её:
`Me.entitlements.full_report_chart_id`. Разбор карты оплачен тогда и только
тогда, когда это поле равно её `chart_id`. Вопрос задаётся в одном месте —
`hasReportFor(me, chartId)` в `src/lib/plans.ts`:

- карта на экране спрашивает его, чтобы выбрать между «Получить разбор» /
  «К разбору» и ценой;
- `grants(me, plan, chartId)` спрашивает его, чтобы подтвердить покупку
  разбора: платёж за карту B не подтверждается разбором карты A.

`full_report: true` сам по себе ничего не открывает: он говорит только, что у
пользователя куплен разбор какой-то карты. У того, кто купил разбор карты A и
построил карту B, оба ответа `Me` несут `full_report: true`; на карте A —
«К разбору», на карте B — цена, и нажатие ведёт на пейволл, а не на заказ,
который сервер отклонит `402`. `full_report: true` с
`full_report_chart_id: null` — разбора нет, цена.

### Пейволл (экран 7)

- **Что продаётся.** Полный разбор (`one_149`, разовая покупка для одной карты)
  и три подписки (`week_149`, `month_399`, `year_2990`). Коды — из `PlanCode`
  контракта (`src/lib/plans.ts`): переименованный код ломает сборку. Подписчику
  подписки не предлагаются; разбор предлагается, только когда пейволл открыт
  ради него (кнопкой под тизером или отказом `402`), и тогда он уже выбран.
  Подписки продаёт только сборка с `VITE_SUBSCRIPTIONS=enabled`; любая другая
  продаёт только разбор (раздел «Сборка без подписок»).
- **Что обещают подписки.** Описание называет готовым только то, что
  приложение уже отдаёт: «Полные прогнозы, 5 вопросов карте в день». О том,
  чего ещё нет, сказано прямо: «Совместимость раз в месяц появится в
  ближайшие дни», «Карта года появится в ближайшие дни».
- **Цена.** До счёта экран показывает цену из `@astro-soul/shared` — той же
  таблицы, по которой считает сервер. Как только счёт создан, цена — это его
  `stars`. Если она не та, что была на экране, счёт не открывается сам:
  экран показывает цену сервера и ждёт второго нажатия.
- **Счёт.** `POST /billing/invoice` с `plan_code`, а для разбора ещё и с
  `chart_id`: товар привязан к карте. Счёт создаётся по нажатию «Оплатить», а
  не заранее: сервер считает счета (три в час). Созданный счёт экран помнит и
  после отмены открывает его же.
- **Чем закончился счёт** — говорит Telegram, и это не подтверждение оплаты:
  - `paid` — приложение спрашивает сервер (`GET /me`): сразу и ещё раз через
    2 секунды. Сервер выдал купленное — разбор заказывается, подписка
    показывается активной. Для разбора «выдал» значит «назвал карту, за
    которую платили» (`full_report_chart_id`), а не `full_report: true`: тот
    мог остаться от разбора другой карты. Не выдал — экран «Платёж
    обрабатывается. Открой приложение через минуту» с кнопкой «Проверить ещё
    раз». Ничего не открывается по одному слову Telegram;
  - `pending` — то же, но вопросов три (`payments.md`, раздел 6);
  - `cancelled` — пользователь передумал: экран остаётся как был, без текста
    ошибки;
  - `failed` — «Платёж не прошёл. Попробуй ещё раз или выбери другой способ»;
  - статус, которого приложение не знает, читается как `pending`.
- **Второй раз за то же не платят.** Пока сервер не подтвердил платёж,
  который Telegram назвал оплаченным, приложение его помнит (до перезагрузки
  страницы): на карте вместо цены — «Платёж обрабатывается» и «Проверить ещё
  раз», пейволл открывается на том же состоянии.
- **Ошибки счёта.** `429` — «Слишком много попыток оплаты. Попробуй через
  час» (свой текст: общий текст сервера говорит «через минуту») и время из
  `details.reset_at`, если сервер его прислал. `422` — «Не удалось создать
  счёт», текст сервера и код обращения; читаются обе формы ответа, с
  `details.field_errors` и без. Сеть и таймаут — повтор той же кнопкой.
  Отказ по полю `chart_id` на счёт за разбор — не ошибка счёта, а «карты
  больше нет» (раздел «Карта, которой больше нет»).
- **Вне Telegram** счёт открыть нечем: «Оплата доступна в Telegram» и
  предупреждение в консоли; сервер о счёте не спрашивается. В Telegram старше
  Mini Apps 6.1 — просьба обновить Telegram.

### Разбор (экран 6)

- **Заказ.** `POST /reports` с телом `{chart_id, type: "full"}` и заголовком
  `Idempotency-Key`. Ключ — UUID v4, создаётся в момент нажатия и хранится в
  `sessionStorage` под картой и типом разбора, не дольше 24 часов. Повторное
  нажатие, повтор после ошибки и перезагрузка страницы отправляют тот же ключ.
  Новый ключ — только когда пользователь сам нажимает «Попробовать снова»
  после `failed` или `refunded`.
- **Ответ на заказ** даёт только `report_id`: каков разбор, приложение
  спрашивает следующим запросом, сразу.
- **Опрос.** `GET /reports/{id}`: первый сразу после заказа, следующий через
  2 секунды; пока ответы не приносят нового, пауза удваивается до 10 секунд
  (2, 4, 8, 10, 10…), ответ с новым возвращает её к 2. Пока страница скрыта,
  запросов нет; когда она вернулась — запрос сразу. Уход с экрана отменяет и
  таймер, и запрос в пути. На `ready`, `failed` и `refunded` опрос кончается.
- **Что на экране.** `queued` — «Разбор в очереди»; `generating` — «Пишем
  разбор», полоса с числом сервера и «Готово 3 из 7 глав», под ними главы,
  которые уже пришли; `ready` — оглавление и все главы; `failed` — «Не
  получилось», «Попробовать снова», поддержка и номер разбора; `refunded` —
  «Разбор не получился, звёзды вернулись на счёт», без слова «ошибка».
- **Прогресс** — только число сервера: полоса не движется сама и не показывает
  100, пока сервер не скажет `ready`. Если ответы не меняются дольше минуты —
  «Это дольше обычного, но разбор ещё готовится» и поддержка, без предложения
  платить.
- **Главы** идут по `order`. Глава с ключом, которого сборка не знает,
  показывается как любая другая; для главы, которой нет, ничего не
  подставляется. Текст (`body_md`) превращается в элементы React, строка HTML
  нигде не собирается: теги из текста выбрасываются, от ссылки остаются слова,
  от картинки ничего. Дисклеймер приходит в тексте последней главы, своего
  приложение не добавляет.
- **Неоплаченный разбор.** Главы показываются, только если `is_paid === true`.
  Иначе клиент API отбрасывает главы и ссылку на PDF ещё при чтении ответа
  (`toReport` в `src/api/index.ts`), так что до экрана и до DOM они не доходят,
  что бы ни прислал сервер. От такого разбора видно начало (`teaser`): три
  строки на карте и на экране разбора, и кнопка с ценой.
- **Отказы заказа.** `402` — на пейволл, с объяснением и уже выбранным
  разбором; сразу после покупки `402` значит «платёж ещё не дошёл», и экран
  говорит это. `422` — текст сервера о поле и код обращения. `409` — текст
  сервера как есть. `429` — «Слишком часто, попробуй через минуту». `404` —
  карты больше нет: приложение ведёт на Welcome и текст сервера не
  показывает (раздел «Карта, которой больше нет»).
- **PDF.** Кнопка есть, только когда сервер прислал `pdf_url`. Ссылка живёт в
  памяти. Перед открытием приложение проверяет её (`HEAD`); на `404`
  перечитывает разбор один раз и открывает новую ссылку.
- **Возвращение.** `Me.latest_report_id` называет последний заказанный разбор
  пользователя, готовый или в работе; с контракта 1.5.3 поле есть всегда.
  Карта при запуске спрашивает о нём и показывает, где разбор: «Разбор готов»
  и «К разбору»; заново ничего не заказывается.
  - `null` — обычное состояние, не ошибка: разбора нет. Тому, кто не платил,
    карта показывает цену, купившему — «Получить разбор» (сервер отвечает на
    заказ разбором, который у него уже есть, если такой есть).
  - `404` на `GET /reports/{id}` по этому id — разбора у сервера больше нет.
    Разбор пропадает только вместе с данными пользователя, поэтому приложение
    сначала спрашивает `GET /me`, на месте ли карта. Карты нет — данные
    удалены на другом устройстве: приложение ведёт на Welcome и о разборе не
    говорит ничего (раздел «Карта, которой больше нет»). Карта есть —
    приложение молча забывает id: ни экрана ошибки, ни `error_shown`; карта и
    экран разбора выглядят так же, как при `null`. Иначе с `404` по разбору,
    который этот же экран только что заказал, при карте на месте: сервер
    принял заказ и потерял его, это ошибка с кодом обращения. Забытый id
    приложение больше не принимает, даже если `Me` продолжает его называть:
    иначе вопросы о разборе и `GET /me` пошли бы по кругу.

### Настройки (экран 9)

Открываются из правого верхнего угла карты и Welcome. Показывают подписку
(план, срок, автопродление; отменить её можно только в Telegram, ссылка
`tg://settings/star_subscriptions`), лимиты из `Me.quotas` («Осталось X из
Y»; `-1` — «Без ограничений», `0` — «Недоступно»), документы, поддержку и
удаление данных.

Удаление — кнопка и два подтверждения подряд (`SPEC.md`, сценарий 7: «двойное
подтверждение»). Кнопка «Удалить мои данные» ничего не удаляет. Первое
подтверждение говорит, что именно удалится, что будет с подпиской и что
останется, и ведёт дальше кнопкой «Удалить данные». Она тоже ничего не
удаляет. Второе — последнее слово: «Удалить навсегда» отправляет `DELETE /me`.

С контракта 1.5.5 удаление отменяет подписку: доступ закрывается сразу,
оплаченный период не возвращается. До 1.5.5 подписка жила до конца периода, и
диалог обещал именно это. `SPEC.md` требует сказать о новом до нажатия, и
первое подтверждение говорит это словами владельца: «Подписка при этом
отменяется, доступ закрывается сразу, оплаченный период не возвращается.»
Фразу видят все, а не только подписчики: решать по своей копии `Me`, кому её
не показывать, приложение не берётся. Следом — «Обезличенная история платежей
сохранится для бухгалтерского учёта и возвратов» (требование `legal.md`).

Второе подтверждение («Точно удалить?») повторяет главное словами владельца,
тремя предложениями: «Удаляются профиль, карты, разборы, прогнозы и вопросы —
в том числе купленный разбор. **Подписка отменяется сразу, оплаченный период
не возвращается.** Восстановить данные не получится.» Среднее предложение —
полужирным, обычным размером, отдельной строкой: это то, что уберегает от
сюрприза с деньгами, и мелким шрифтом оно не набирается нигде.

Кнопка «Удалить навсегда» первую секунду после появления неактивна
(`DELETE_GUARD_MS`): повторное нажатие по ошибке не должно стать тем, которое
удаляет. Порядком кнопок от него не защититься: второе подтверждение короче
первого, кнопки сдвигаются, и на 390×844 под пальцем после первой кнопки
оказывалась именно «Удалить навсегда» — это показал браузер, а не тест в
jsdom. Куда попадёт нажатие, зависит от вёрстки; когда оно придёт — нет.

В сборке, которая не продаёт подписки, кнопки «Оформить подписку» в настройках
нет; «Подписки нет.» или план и срок действующей подписки показываются как
обычно.

После `204` — экран «Данные удалены», последний в этом запуске: событий после
него приложение не отправляет. У экрана два варианта, по тому, была ли у
пользователя подписка:

| | Подписка была | Подписки не было |
| --- | --- | --- |
| Заголовок | «Данные удалены» | «Данные удалены» |
| Текст | «Подписка отменена. Если захочешь вернуться — начнёшь с чистого листа.» | «Если захочешь вернуться — начнёшь с чистого листа.» |
| Мелким шрифтом | «Обезличенная история платежей сохранится для бухгалтерского учёта и возвратов.» | то же |
| Ссылка | «Управлять подписками в Telegram» → `tg://settings/star_subscriptions` (`src/lib/telegramLinks.ts`, тот же адрес, что в настройках) | нет |

Во втором варианте на экране нет ни слова о подписке и ни одной ссылки.
Внутри Telegram в обоих вариантах есть кнопка «Закрыть».

«Подписка была» — это `subscription.plan !== 'none' && subscription.is_active`
в том `Me`, который настройки показывали, когда пользователь нажал «Удалить
мои данные». Это то же условие, по которому блок «Подписка» в настройках
показывает план и ссылку на Telegram: «Подписка отменена» читает тот, кто
перед этим видел подписку в настройках. Отменённая, но ещё оплаченная
подписка и пробный период считаются подпиской; закончившаяся — нет.

Значение запоминается при нажатии, уходит наверх через
`onDeleted(hadSubscription)` и живёт только в памяти. После удаления сервер ни
о чём не спрашивают: по подписанному запросу он создал бы пользователя заново,
пустого. Берётся `Me`, который настройки перечитали при открытии, а не тот, с
которым приложение запустилось: подписка могла закончиться или появиться, пока
приложение было открыто.

Если о подписке ничего не известно, показывается вариант без неё: промолчать
лучше, чем сказать неправду. Сегодня до этого не дойти: кнопка «Удалить мои
данные» появляется только вместе с загруженным `Me` (пока его нет, на экране
скелет или ошибка с повтором). Удаление ради этой строки ничего не ждёт и ничем
не блокируется.

Ссылка нужна потому, что автопродление в Telegram сервер сам не выключает
(issue #29): проверить и отменить его может только пользователь. Ключи заказов
из `sessionStorage` (единственное, что приложение хранит на устройстве между
перезагрузками) стираются вместе с данными. Это и есть обычный исход, в том
числе при зависшем платеже: с контракта 1.5.3 сервер сам разрешает платёж,
возвращает звёзды и удаляет.
`409` остался редким случаем — возврат технически не удался
(`details.reason: refund_failed`): текст сервера как есть и поддержка;
`401` — «Сессия истекла, открой приложение заново»; сеть — та же кнопка ещё
раз. Запрос удаления не отменяется, если пользователь ушёл с экрана: чем он
кончился, приложение узнаёт в любом случае.

Пока `VITE_SUPPORT_CONTACT` не задан, кнопка поддержки везде неактивна и
называется «Контакт поддержки ещё не задан»: сборка не обещает того, о чём не
знает.

## Прогноз и вопрос карте (экран 8)

Правило то же, что у оплаты: **что показать, решает сервер.** Приложение не
просит сделать прогноз, не ждёт его и не считает вопросы.

### Прогноз

- **Один запрос на открытие.** Карточка на карте и экран прогноза отправляют
  `GET /engagement/forecast?chart_id=…` по одному разу, когда открываются.
  Ещё один запрос — только нажатием «Попробовать ещё раз» после ошибки.
  Таймеров и опроса нет: сервер готовит прогнозы ночью и отвечает тем, что
  есть; от повторного вопроса прогноз раньше не появится.
- **Карточка на карте** — одна строка над колесом: название и первое
  предложение прогноза, остальное обрезается. Нажатие в любом состоянии
  открывает экран прогноза. Карточка есть и у карты, открытой при запуске, и
  у только что построенной.
- **Экран.** Весь текст, который отдал сервер, как есть. «Фокус дня: карьера»
  — ярлык рядом с текстом, только когда сервер назвал `focus` и у сборки есть
  для него слово (`forecast.focusNames` в `ru.ts`). Внизу — «Спросить карту».
- **Прогноза ещё нет (`404`).** Не ошибка: «Сегодняшний прогноз готовится»,
  «Загляни после 08:00», мелкой строкой под ними «Время считается по месту
  рождения.» и кнопка «К карте». Без роли `alert`, без кнопки повтора, без
  `error_shown`. Так выглядит и первый день карты: экран ничего не обещает
  про вопрос карте и входа на него не даёт — кнопка «Спросить карту» есть
  только у прогноза, который пришёл.
- **Запрос не удался.** «Не получилось загрузить прогноз», текст и код
  обращения сервера, «Попробовать ещё раз» и «К карте». Если приложение уже
  слышало прогноз в этом запуске (его показала карточка), а повторный запрос
  не прошёл, на экране остаётся то, что есть, без сообщения об ошибке.
- **Короткий прогноз (`is_paid: false`).** Сначала текст, под ним тихая
  строка «Полный прогноз — в подписке», которая ведёт на пейволл. Строки нет,
  если подписку предложить нельзя: она уже есть или сборка их не продаёт.
- **«Сегодня».** Сервер считает дни по часовому поясу места рождения карты.
  Заголовок «Прогноз на сегодня» стоит, только когда `Forecast.date` — это
  сегодняшнее число в этом поясе (`chart.birth.place.tz`), а не на устройстве.
  Иначе — «Прогноз на 14 ноября». Если у карты пояса нет, «сегодня» не
  пишется никогда: проверить нечем. Заголовок считается, когда экран
  рисуется: у того, кто держит экран открытым через полночь, он сменится при
  следующем переходе, а не сам.
- **«Поделиться»** отправляет картинку карты и те же слова, что кнопка на
  карте. Текст прогноза никуда не уходит.

### Спроси карту

- **Одно нажатие — один запрос.** Замок берётся до отправки и хранится не в
  состоянии компонента, а в `ref`: второе нажатие, пришедшее раньше
  перерисовки, уходит ни с чем. Клиент API этот запрос не повторяет ни при
  5xx, ни при обрыве сети.
- **Счётчик — только из `Me.quotas`** (`ask_daily`). `GET /me` отправляется
  при открытии экрана и после каждого отправленного вопроса, чем бы тот ни
  кончился. Сам экран вопросы не считает. «Сегодня осталось 3 вопроса из 5»
  видно до первой отправки; `-1` — «Без ограничений»; пока ответа на
  `GET /me` нет, на месте числа заглушка, а не то, что приложение слышало
  раньше. Если `GET /me` не удался, числа нет вовсе и по старому числу ничего
  не решается: вопрос можно отправить, а лимит скажет сервер.
- **Вопросы кончились** (свежий счётчик показывает ноль): поля и кнопки
  отправки нет. Вместо них спокойное «Вопросы на сегодня закончились. Новые —
  после полуночи.», момент сброса по часам устройства («Обновится 14 ноября
  в 22:00») и, если этот момент на устройстве не полночь, пояснение «Полночь
  считается по месту рождения.». Ниже — «В подписке 5 вопросов в день» (ссылка
  на пейволл), если подписку можно предложить. Если приложение раньше слышало
  «ноль», форма не показывается, пока сервер не подтвердит или не опровергнет
  это: поле, которое исчезает под пальцем, хуже заглушки.
- **`429`.** Приложение сначала перечитывает `Me`. Счётчик на нуле — то же
  спокойное состояние, с моментом из `details.reset_at`. Счётчик не на нуле —
  значит, остановил не лимит пользователя (так сервер отвечает, когда
  исчерпан месячный бюджет сервиса): показывается только текст сервера, без
  слов про полночь и подписку, вопрос остаётся в поле. `Me` перечитать не
  удалось — текст сервера как есть.
- **Ответ** показывается дословно, вместе с вопросом. «На чём основано» — если
  сервер прислал `based_on`. Новый вопрос заменяет прежнюю пару; истории нет,
  после ухода с экрана ответ не хранится.
- **Запрещённая тема.** Сервер отвечает на неё `200` с мягким отказом вместо
  ответа, и приложение показывает его как любой ответ: дословно, без роли
  ошибки. Сам экран темы не проверяет и вопрос не правит.
- **`422`** — текст сервера под полем и код обращения; текст исчезает, когда
  вопрос меняют. Длину до отправки приложение не проверяет, только не даёт
  ввести больше 500 знаков и не отправляет пустое поле.
- **Остальные ошибки** — «Ответ не получен», текст и код обращения сервера;
  вопрос остаётся в поле, повтор — той же кнопкой. Отдельной ветки для `402`
  нет: контракт такого ответа на вопрос не описывает и `apps/api` его не
  отправляет, поэтому и мок его не играет.

### Сборка без подписок (по умолчанию)

Подписки продаёт только сборка с `VITE_SUBSCRIPTIONS=enabled`. Переменная не
задана, пуста или равна `off` — подписки не продаются; значение, которое нельзя
прочитать (`of`, `0`, `yes`), останавливает и сборку, и dev-сервер, а не
превращается молча в один из двух ответов. Правило читается в одном месте —
`subscriptionsModeOf` (`src/lib/subscriptions.ts`), приложение берёт ответ из
`config.subscriptions`.

В такой сборке подписку не предлагает ни один экран: пейволл продаёт только
полный разбор (планы подписок не становятся элементами страницы — их нет в
DOM, а не они скрыты стилем), под коротким прогнозом и под «Вопросы
закончились» нет строк про подписку, в настройках нет кнопки «Оформить
подписку». Если разбор купить негде (пейволл открыт не ради него), экран
говорит «Сейчас здесь нечего оплачивать». Подписка, которая у пользователя уже
есть, работает и показывается как обычно.

Чего флаг не делает: тексты подписок остаются в файле бандла (флаг выбирает,
что рисовать, а не что собирать), а сервер по-прежнему выставит счёт за
подписку тому, кто попросит его в обход приложения. В описании разбора
остаются слова «Разовая покупка, без подписки».

### Карта, которой больше нет

Данные можно удалить на другом устройстве, пока эта страница открыта. Узнав,
что карты нет, приложение забывает всё, что о ней помнило (карту, разбор,
прогноз, ключи заказов, анкету, платёж за разбор, подтверждения которого оно
ждало), и начинает как при запуске: спрашивает `GET /charts/current`, получает
«карты нет» и открывает Welcome. Текст сервера («Такой карты нет. Построй
карту заново», «Такого разбора нет», «Карта не найдена») не показывается,
экрана ошибки и `error_shown` нет.

Откуда приложение это узнаёт:

- `404` на вопрос (`POST /engagement/ask`) и на заказ разбора (`POST /reports`);
- `422` по полю `chart_id` на счёт за разбор (`POST /billing/invoice`);
- `GET /me` без карты (`has_chart: false` и нет `chart_id`), когда его
  перечитывает экран, который работает с картой: экран вопроса, экран
  прогноза, настройки, открытые с карты (у того, кто карту ещё не строил,
  настройки открываются как обычно: `Me` без карты для него не новость);
- `404` на разбор (`GET /reports/{id}`): приложение перечитывает `Me`, и если
  карты нет и там — Welcome. Пока ответа нет, экран разбора не говорит ничего:
  ни «Такого разбора нет», ни предложения заказать разбор заново;
- `GET /me` без карты в ответ на вопрос «дошёл ли платёж за разбор»: сразу
  после оплаты и по кнопке «Проверить ещё раз», на пейволле и на карте. Разбор
  покупается для карты: нет карты — нечего и ждать, и вместо «Платёж
  обрабатывается» без конца приложение открывает Welcome. У карты, построенной
  после этого, своя цена.

`404` на прогноз сам по себе ничего не значит: тем же кодом сервер отвечает и
на «прогноз ещё не готов», и на «такой карты нет», различается только текст.
Поэтому, получив `404`, экран прогноза показывает «готовится» и один раз
перечитывает `Me`: если карты нет и там — Welcome. Карточка на карте `Me` не
перечитывает.

`401` — другое: это не «данных нет», а подпись запуска, которую сервер больше
не принимает (она живёт 24 часа). После удаления сервер так не отвечает: по
подписанному запросу он создаёт пользователя заново, пустого. С `401` спросить
сервер нельзя ни о чём, в том числе о карте, поэтому приложение говорит
«Сессия устарела. Закрой приложение и открой его снова из чата с ботом» и
предлагает «Закрыть». Новый запуск начинается с `GET /me`: если данных нет —
Welcome. С прошлого запуска на устройстве остаются только ключи заказов в
`sessionStorage`; карт, разборов и ответов `Me` приложение не хранит.

Чего приложение не замечает: страница, на которой ничего не нажимают, остаётся
как была (открытая карта или прочитанный разбор — это текст в памяти, сервер о
них не спрашивают).

#### Подписка, купленная после удаления

Подписка — не про карту: счёт за неё сервер выставит и после удаления (по
подписанному запросу он создаёт пользователя заново), и оплата пройдёт. `Me`,
которым сервер подтверждает такую оплату, называет подписку и не называет
карты. Это единственный случай в разделе, когда приложение само никуда не
ведёт: человек только что заплатил, и Welcome без единого слова выглядел бы
как пропавшие деньги.

Экран подтверждения на пейволле говорит словами владельца:

- заголовок — «Подписка активна до <дата>» (обычный заголовок этого экрана;
  без даты — «Подписка активна.»);
- под ним — «Карта не найдена — возможно, данные удалили на другом устройстве.
  Построй карту заново, подписка при этом сохранится.»;
- одна кнопка «Построить карту» вместо обычной («К разбору» или «Вернуться»).

Кнопка делает то же, что остальные пути этого раздела: приложение забывает
карту, спрашивает `GET /charts/current`, получает «карты нет» и открывает
Welcome; анкета начинается с согласия. Подписка остаётся, её показывают
настройки.

Экран показывается, когда верно всё сразу:

- подписку подтвердил ответ на вопрос, заданный с этого экрана: сразу после
  оплаты или по «Проверить ещё раз». `Me`, с которым экран открылся, для этого
  не годится: он может быть старше карты. После построения карты приложение
  `Me` не перечитывает, поэтому у подписчика, который построил первую карту в
  этом запуске, `Me` тоже «не называет карты» — а карта есть, и пейволл должен
  продать к ней разбор;
- в этом ответе подписка активна (`entitlements.is_active`), а карты нет
  (`has_chart: false` и нет `chart_id`);
- у приложения была карта: та, с которой оно открылось, или построенная в этом
  запуске. Тому, кто карту ещё не строил и оформил подписку из настроек,
  показывается обычный экран с «Вернуться».

Так же он выглядит на пейволле, открытом с цены на карте: разбор для карты,
которой нет, не продаётся. Пока платёж не подтверждён («Платёж
обрабатывается»), о карте не сказано ничего, и `Me` без карты в ответ на
вопрос о подписке приложение с места не сдвигает. Вопрос о платеже за разбор
сдвигает, как раньше: разбор покупается для карты.

Чего здесь нет:

- Подписку подтвердил не пейволл. Если с «Платёж обрабатывается» уйти кнопкой
  «Вернуться», `Me` перечитает другой экран (прогноз, вопрос, настройки), и
  приложение откроет Welcome молча, как на любом другом пути этого раздела.
  Подписка при этом на месте и видна в настройках.
- «Назад» с этого экрана возвращает на прежний экран с картой из памяти.
  Следующее действие с ней ведёт на Welcome.

## Согласие и юридические тексты

Экран согласия идёт сразу после Welcome, до первого шага с данными: поиск места
отправляет введённое название на сервер раньше, чем уходит `POST /charts`.

- Галочка по умолчанию не стоит, «Продолжить» неактивна, пока её нет. Отметка
  живёт в памяти вместе с остальными ответами и переживает переход к документу
  и обратно; после перезапуска приложения её нужно поставить снова.
- «Не сейчас» возвращает на Welcome и стирает отметку и всё, что было введено.
- В `POST /charts` уходит `consent: { accepted: true, version }`. `version` —
  константа `CONSENT_VERSION` (`src/i18n/consentVersion.ts`, её же отдаёт
  `src/i18n/ru.ts`), дата текстов в формате `ГГГГ-ММ-ДД`. Без отметки тело
  запроса не собирается вовсе: `accepted: true` никогда не отправляется за
  пользователя.
- Тексты — дословно `legal-texts-2026-11-10.md` из корня репозитория:
  дисклеймер и строка под кнопкой на Welcome (строка открывает соглашение),
  экран согласия (вводное предложение, четыре пункта и отдельный абзац про
  статистику использования), два экрана документов (абзац на строку файла). Под обоими
  документами выводится строка «Версия документа: …» с той же версией, что уходит
  на сервер. Строка «Поддержка: <контакт>.» не выводится, пока в файле вместо
  контакта стоит заглушка.
- Эти тексты в `ru.ts` не редактируются: они переносятся из файла текстов
  дословно. Версия (`CONSENT_VERSION`, а с ней `MOCK_CONSENT_VERSION` мока)
  поднимается только при изменении состава обрабатываемых данных или основания
  обработки (`legal.md` §6); правка формулировок версию не меняет и согласие
  заново не спрашивает. Так 2026-11-14 изменились пункт согласия про удаление
  и абзац соглашения про оплату (удаление отменяет подписку сразу, контракт
  1.5.5), а версия осталась `2026-11-10`.
- `tests/legal-texts.test.ts` сверяет каждый текст с файлом и хранит SHA-256
  текстов под каждой версией: он падает, если текст разошёлся с файлом или
  изменился, а хэш остался прежним. Хэш меняется только вместе с решением
  владельца о том, нужна ли новая версия, — в том же PR, что и текст.

### Когда сервер не принимает версию согласия

Юридические тексты — часть сборки, поэтому новые могут прийти только с новой
сборкой. На `422` с полем `consent.version` приложение записывает отклонённую
версию в `sessionStorage` и перезагружает страницу. Дальше — по тому, что
загрузилось:

- **Сборка с другой версией текстов.** Приложение открывается сразу на экране
  согласия: галочка пустая, вверху экрана — «Условия обновились, подтверди ещё
  раз. Данные рождения нужно будет ввести заново.» Введённое до перезагрузки не
  сохраняется нигде, намеренно: данные рождения не кладутся в хранилище
  браузера.
- **Та же сборка** (хостинг ещё отдаёт старую). Экран «Условия обновились» с
  кнопкой «Обновить приложение» и, внутри Telegram, «Закрыть». Сама по себе
  вторая перезагрузка не запускается — иначе был бы цикл.
- **`sessionStorage` недоступен.** Тот же экран показывается сразу, без
  автоматической перезагрузки.

Чтобы это работало, хостинг не должен отдавать `index.html` из кеша без
перепроверки (`Cache-Control: no-cache`); файлы в `assets/` с хешем в имени
можно кешировать надолго. Шаблон такой раздачи — `deploy/nginx.miniapp.conf`
в корне репозитория (его ведёт бэкенд).

Как увидеть руками:

```js
// в консоли браузера, затем перезагрузить страницу
sessionStorage.setItem('astro-soul.consent-refused', '2026-01-01'); // сборка с новыми текстами
sessionStorage.setItem('astro-soul.consent-refused', '2026-11-10'); // та же сборка
```

В моке отказ даёт место `Версионово` или запуск с
`API_MOCK_CONSENT_VERSION=2099-01-01`.

### Что в этих текстах не совпадает с приложением

Решает человек: агенты юридические тексты не пишут и не меняют.

- В `legal.md` (раздел 2) вводное предложение текста согласия осталось на «вы»
  («вашего рождения», «ваше согласие»), остальное переведено на «ты».
  Приложение следует файлу текстов, там это предложение на «ты».
- Версия `2026-11-10` пережила три замены текстов. Правки этой даты (тон,
  дисклеймер, абзацы про статистику) и правка 2026-11-14 (удаление отменяет
  подписку) версию не подняли: по правилу `legal.md` §6 её поднимает только
  изменение состава данных или основания обработки. Хеш этой версии в тесте
  заменён трижды, каждый раз с комментарием. В самом файле текстов
  («Ответы на вопросы агентов по текстам», п. 2) осталась прежняя формулировка
  правила — «любая смысловая правка = новая версия»; приложение следует §6.
- Тексты обещают «Настройки → «Удалить мои данные»». Экран настроек теперь
  есть, кнопка называется так же и вызывает `DELETE /api/v1/me`.
- Тексты обещают, что данные удаляются автоматически после 24 месяцев без
  захода. Это дело сервера; в приложении об этом нет ничего, кроме самих
  текстов.
- Тексты называют статистику использования обезличенной. События уходят с
  первого экрана, до согласия, и сервер хранит их с внутренним `user_id`: так
  решено в `legal.md`, раздел 0. Того, что вводит пользователь, в событиях нет
  (раздел «Продуктовые события»).
- Пункт согласия об удалении и абзац соглашения об оплате с 2026-11-14 говорят,
  что удаление отменяет подписку сразу и без возврата (контракт 1.5.5). Файл
  текстов и `legal.md` (раздел 2) в этом совпадают, приложение показывает их
  дословно; версия осталась `2026-11-10` (issue #30, решение владельца).

## Продуктовые события

Приложение отправляет события из закрытого списка контракта
(`x-analytics-events`) пачками в `POST /events`.

| Когда | Событие |
| --- | --- |
| Запуск | `app_open` |
| Открыт экран | `screen_view {step}`; на экране согласия ещё `consent_view` |
| «Продолжить» на согласии | `consent_accepted {version}` |
| Шаг анкеты пройден | `birth_date_done`, `birth_time_done`, `birth_place_done` |
| Назад (любой кнопкой), «Не сейчас» | `step_back {step}` — экран, с которого ушли |
| Поиск места | `place_search` на каждый ушедший запрос; `place_search_empty`; `place_search_failed {code}` |
| Запрос карты | `chart_requested`, затем `chart_created`, `chart_restored` (карта с такими данными уже была: `is_restored` в ответе) или `chart_failed {code}` |
| Карта открыта при запуске | `chart_restored` |
| Сервер отклонил поля | `validation_failed {step, code, field}` на каждое поле |
| Проверка самого приложения остановила пользователя | `validation_failed_client {step, field}` — см. ниже |
| «Поделиться картой» (на карте и на готовом разборе) | `share_clicked` |
| Открыт пейволл | `paywall_view` (вместе с `screen_view {step: paywall}`) |
| Нажато «Оплатить» | `checkout_started {plan_code}` — до запроса счёта |
| Счёт создан, Telegram его показывает | `checkout_opened {plan_code}` |
| Счёт закрыт без оплаты | `payment_cancelled {plan_code}` |
| Сервер выдал купленное | `payment_succeeded {plan_code}` — один раз, когда `GET /me` подтвердил платёж, с какого бы экрана ни пришёл вопрос. Слово Telegram «paid» этим событием не считается |
| Заказ разбора | `report_requested` |
| Сервер отказал в заказе без покупки (`402`) | `quota_exhausted {step: report}` |
| Готовый разбор на экране | `report_ready_view {report_id}` |
| Прогноз на экране прогноза | `forecast_view` — один раз на открытие экрана и только когда прогноз есть; карточка на карте события не даёт |
| «Поделиться» на экране прогноза | `share_clicked` |
| Сервер ответил на вопрос | `ask_used` — и на мягкий отказ тоже: что именно ответил сервер, событие не говорит |
| Вопросы на день кончились | `quota_exhausted {step: ask}` — один раз на открытие экрана: когда `Me` показал ноль (при открытии, после последнего ответа или после `429`), на `429`, после которого `Me` перечитать не удалось, и на `402`, с которого приложение ведёт на пейволл |
| `429` на вопрос, а по `Me` вопросы ещё есть | `error_shown {screen: ask, code: 429}`: это лимит сервиса, а не пользователя |
| Сервер отклонил вопрос (`422`) | `validation_failed {step: ask, code, field: question}` и `error_shown {screen: ask, code: 422}` |
| Показана ошибка на пейволле, разборе, прогнозе, экране вопроса или в настройках | `error_shown {screen, code}`: `code` — HTTP-статус (`409`, `500`), без ответа сервера — `NETWORK` или `TIMEOUT`, для платежа и разбора — `payment_failed`, `report_failed` |
| Данные удалены | `data_deleted` |

- **Что не уходит никогда:** введённое, найденное и выбранное пользователем,
  содержимое карты, текст разбора, тексты сервера. У `props` семь ключей —
  `step`, `code`, `field`, `version`, `screen`, `plan_code`, `report_id`, — а
  значения берутся из закрытых списков и кодов ошибок; `report_id` выдаёт
  сервер. Всё остальное вырезается перед отправкой.
- **Как уходит.** События копятся в памяти; пачка уходит через 3 секунды после
  первого события в ней или когда набралось 20. Когда страница уходит в фон или
  закрывается, остаток отправляется запросом с `keepalive`. Пачка отправляется
  один раз, ответ и ошибка ни на что не влияют, между запусками ничего не
  хранится. Без `initData` события не собираются.
- **Проверка самого приложения.** `validation_failed_client` — проверка
  приложения остановила пользователя (например, «младше 18» на шаге даты):
  одно событие на каждое появившееся сообщение об ошибке, с экраном и именем
  поля (`birth_date`, `birth_time`, `time_precision`, `birth_place`) и без
  причины — причина была бы сведением о введённом. До этой итерации событие
  придерживалось: сервер его имени не знал и отвечал `422` всей пачке. Сервер
  из `main` имя принимает (отчёт QA-002, пункт QA-02; проверено и запросом, и
  в браузере: пачка с этим событием — `202`), и событие отправляется как все.
- **Удаление данных не удалось.** Отдельного имени для этого в контракте нет,
  и выдумывать его нельзя: уходит `error_shown {screen: settings, code}`.
- **Имена-синонимы.** Контракт принимает два набора имён
  (`x-event-aliases`). Приложение отправляет `app_open`, `birth_date_done`,
  `birth_time_done`, `birth_place_done`, `screen_view`, `share_clicked`,
  `validation_failed` и не отправляет их синонимы `onboarding_start`,
  `onboarding_birth_date_set`, `onboarding_time_set`, `onboarding_place_set`,
  `mini_reading_view`, `wheel_shared`. `checkout_started` и `checkout_opened`
  записаны там как одно событие под двумя именами; в приложении это два разных
  момента, между ними — запрос счёта, который может не пройти.
- **Прогноз и вопрос.** Текст прогноза, вопрос и ответ в события не попадают:
  у этих событий либо нет `props`, либо в них экран и код. «Прогноз ещё
  готовится» событием ошибки не считается. Когда прогноз уже известен от
  карточки, `forecast_view` и `screen_view {step: forecast}` уходят в один
  момент, и `forecast_view` может стоять в пачке первым.
- **Чего нет.** У `subscription_expired_seen` в приложении пока нет повода:
  об истёкшей подписке оно отдельно не сообщает.
- **Где события теряются.** Время события — часы устройства; сервер отбрасывает
  события старше суток и опережающие его больше чем на 5 минут, так что с
  устройства, часы которого спешат сильнее, не дойдёт ничего. На Chromium 80 с API на
  другом origin может не дойти последняя пачка при закрытии: там `keepalive`
  не работает для запросов с preflight.

## Поддерживаемые клиенты

Сборка нацелена на Safari 15 (iOS 15) и Chromium 80 (Android WebView). Это
допущение: требований к версиям в `SPEC.md` нет. Vite понижает только синтаксис
и полифилов не добавляет, поэтому код приложения не использует API новее этих
движков, а единственный полифил, без которого SDK на них не стартует
(`Object.hasOwn`), лежит в `src/telegram/polyfills.ts`. Android 9 с ни разу не
обновлённым системным WebView (Chromium 69) не покрыт.

На клиентах Telegram старше Mini Apps 6.1 нет системной кнопки «Назад» —
приложение рисует свою — и нет счетов: пейволл просит обновить Telegram. Если
SDK не принимает параметры запуска (он проверяет их
по строгой схеме), приложение всё равно входит по «сырому» `initData` и работает
как веб-страница внутри Telegram: со своей кнопкой «Назад», без перекраски
шапки клиента.

## Проверка на устройстве

Автотесты идут в jsdom. Вёрстка просмотрена в headless Chromium на 390×844 и
320×568 с моком; там же пройдены отказ по версии согласия с перезагрузкой и
оба варианта запуска после неё, путь вернувшегося пользователя и «Поделиться»
со ссылкой на бота, а доставка событий при уходе со страницы проверена на
стороне сервера.

Пейволл, разбор и настройки пройдены там же, с моком, на обоих размерах. Счёт
«открывал» подставной клиент Telegram: страница получала от него
`invoice_closed` с нужным статусом, как от настоящего. Пройдено: отмена, отказ,
оплата с опозданием подтверждения («Платёж обрабатывается», затем «Проверить
ещё раз»), в том числе с уходом на карту и в настройки, пока платёж не
подтверждён (цена нигде не предлагается второй раз), заказ и разбор от очереди
до готового, застрявший разбор (минута без изменений), `failed` и `refunded`,
`402`, `429`, отказ в счёте, другая цена в счёте, подписка, удаление данных
(включая двойное нажатие на месте первой кнопки и нажатие на «Удалить навсегда»
в первую секунду: ничего не удаляется) и его отказ `409`, PDF.

С настоящим сервером то же пройдено против `apps/api` из `main` (контракт
1.5.3): локальные API, Postgres, астро-движок в режиме `fallback`, подставной
провайдер текста (`fake-llm`) и подставной Bot API, который выдаёт ссылки на
счета; оплату серверу сообщал вебхук `successful_payment`. Пройдено на 390×844
и 320×568: счёт и отмена; оплата с опозданием вебхука; заказ (`202`) и готовый
разбор из семи глав; перезагрузка после покупки — карта узнаёт разбор по
`Me.latest_report_id`, и «К разбору» открывает его без нового заказа; подписка
и `402` на заказ разбора по ней; `429` на четвёртый счёт; удаление (`204`);
приём всех пачек событий (`202`), в том числе с `validation_failed_client`.
Покупка пройдена и на том пути, где работает SDK Telegram, и на запасном, без
SDK.

Не пройдено с настоящим сервером: разбор, который не удался (`failed`,
`refunded`), `409` при удалении, тизер неоплаченного разбора — их показывал
только мок. Отказ сервера по дате рождения проходился с настоящим API в
итерации 2 и с тех пор не повторялся.

Прогноз и вопрос (экран 8) пройдены в headless Chromium на 390×844 только с
моком (карточка, прогноз и экран вопроса — ещё и на 320×568: ничего не
вылезает за край, длинное слово в вопросе переносится). Поведение `apps/api`
для них взято из его кода (`modules/engagement`) и из отчёта QA-003/004,
где сервер запускался; с этим приложением сервер не запускался. Пройдено на dev-сборке: карточка на карте (одна
строка, над колесом), короткий и полный прогноз, «готовится», ошибка с
повтором, прогноз со вчерашней датой; вопрос и ответ, двойное нажатие (один
запрос), мягкий отказ, `429` лимита пользователя и лимита сервиса, `422`,
`500`; удаление данных запросом со стороны, пока открыт экран вопроса
и пока открыта карта. Отдельно собран продакшен-бандл с
`VITE_SUBSCRIPTIONS=off` и значениями выпуска и открыт так, как его
открывает Telegram (параметры запуска в адресе): по одному запросу прогноза
на карточку и на экран и ни одного за следующие шесть секунд, один
`GET /me` на открытие экрана вопроса и один после отправки; подписку не
предлагает ни прогноз, ни «Вопросы закончились», ни настройки, а на пейволле
в DOM один план. В dev-сборке запросов при открытии вдвое больше: там React
запускает каждый эффект дважды.

Удаление по контракту 1.5.5 пройдено там же и тоже только с моком, подписчиком,
на 390×844 и 320×568: первое подтверждение с фразой о подписке, «Не удалять»
(ничего не удалено), оба подтверждения, экран «Данные удалены»; после него
`GET /me` без карты, подписки и покупок, а следующее открытие начинается с
Welcome. Первое подтверждение стало на две строки длиннее. На 390×844 оно
помещается целиком; в окнах 320×480 и 320×420 (маленький телефон внутри
Telegram) открывается с заголовка, фраза о подписке видна сразу, а до кнопок
нужно прокрутить. С настоящим сервером 1.5.5 удаление не проходилось: что он
отменяет подписку и отзывает покупки, взято из контракта и из кода `apps/api`.

Разбор для карты, удаление на другом устройстве и новые тексты пройдены там
же, только с моком, на dev-сборке без `VITE_SUBSCRIPTIONS` (подписки не
продаются):

- **Две карты, один разбор** (`me=paid`, затем другая дата рождения): на первой
  карте «Получить разбор», на второй цена; `Me` при этом отдаёт
  `full_report: true` и `full_report_chart_id` первой карты; разбор по дороге
  не заказывается; на пейволле в DOM один план.
- **Данные удалены запросом со стороны** (`DELETE /api/v1/me`), пока страница
  открыта: «К разбору» с карты; экран разбора, который в это время пишется
  (сам, на следующем опросе); настройки; «Проверить ещё раз» при платеже за
  разбор, который сервер не подтвердил, на пейволле и на карте (dev-сервер с
  `VITE_DEV_INVOICE=pending`). Каждый раз — Welcome с пустой галочкой
  согласия, без текста сервера и без блока ошибки; карта, построенная после
  этого, показывает цену, а не «Платёж обрабатывается».
- **Удаление** подписчиком на 390×844 и 320×568: второе подтверждение — три
  абзаца, средний полужирный и того же размера, что остальные; экран «Данные
  удалены» — три строки в заданном порядке, третья мельче, ссылка ведёт на
  `tg://settings/star_subscriptions`. Второе подтверждение помещается целиком
  на 390×844, 320×568 и 320×480; в окне 320×420 видны заголовок и все три
  абзаца, а до кнопок нужно прокрутить.
- **«Сегодняшний прогноз готовится»** на обоих размерах: под «Загляни после
  08:00» мельче — «Время считается по месту рождения.», кнопки «Спросить
  карту» нет.
- **Поддержка без контакта**: кнопка неактивна, «Контакт поддержки ещё не
  задан» на 320 переносится на две строки и за край не выходит.

С настоящим сервером ничего из этого не проходилось: что он отвечает `404` на
разбор удалённого пользователя и создаёт пользователя заново по подписанному
запросу, взято из кода `apps/api`.

Два варианта экрана «Данные удалены» и подписка, купленная после удаления,
пройдены там же, только с моком, на dev-сборке с `VITE_SUBSCRIPTIONS=enabled`,
на 390×844 и 320×568:

- **«Данные удалены» без подписки** (`me=returning`): заголовок, «Если
  захочешь вернуться — начнёшь с чистого листа.», мелкая строка; слова
  «подписка» и ссылок на экране нет. **С подпиской** (`me=subscriber`):
  «Подписка отменена. Если захочешь вернуться — начнёшь с чистого листа.» и
  ссылка на `tg://settings/star_subscriptions`. Оба варианта помещаются без
  прокрутки.
- **Подписка после удаления со стороны**: пейволл открыт с цены на карте,
  затем `DELETE /api/v1/me` запросом со стороны, «Подписка на месяц»,
  «Оплатить». На экране «Подписка активна до …», строка про карту и одна
  кнопка «Построить карту»; за следующие пять секунд приложение ничего не
  спросило и никуда не ушло. Кнопка → `GET /charts/current` → Welcome →
  согласие с пустой галочкой; в настройках после этого «Подписка на месяц».
  То же с пейволла, открытого из прогноза («Полный прогноз — в подписке»).
  Экран помещается без прокрутки на обоих размерах.
- **Обратные случаи**: карта на месте — обычный экран с «К разбору»; новый
  пользователь оформил подписку из настроек — обычный экран с «Вернуться»;
  он же после этого построил первую карту и нажал цену на ней — пейволл
  продаёт разбор (один план, «Оплатить 149»), оплата доходит до экрана
  разбора. Ради последнего случая экран и смотрит на ответ сервера, а не на
  `Me`, с которым открылся: `Me` такого подписчика карты не называет.

С настоящим сервером не проходилось и это: что он выставляет счёт пользователю,
данные которого только что удалены, и что `Me` после такой оплаты приходит с
подпиской и без карты, взято из кода `apps/api` и из мока.

На настоящих клиентах Telegram (iOS, Android, Desktop) приложение не
запускалось. Перед релизом стоит пройти руками:

1. Запуск из бота: экран входа не мигает, шапка и нижняя панель клиента того же
   цвета, что фон приложения.
2. Welcome на маленьком телефоне: дисклеймер 18+ и кнопка видны без прокрутки.
3. Клавиатура на экранах даты и времени: цифровая раскладка, кнопка «Дальше»
   остаётся видна над клавиатурой, фокус сам переходит между полями.
4. Ошибка в поле, предупреждение после «Не знаю» и блок ошибки поиска места
   прокручиваются в видимую область при открытой клавиатуре.
5. Поиск места с открытой клавиатурой: видны ли найденные места и «Ничего не
   нашли». В headless Chromium в окнах 390×450, 360×380 и 320×330 (высота как
   при открытой клавиатуре) они оказались ниже видимой области: под полем
   видна строка «Найдено мест: …», а при пустом результате она пустая.
   Клавиша «Найти» на клавиатуре сворачивает её, а не отправляет форму.
6. Системная «Назад»: возвращает на предыдущий шаг, введённые данные на месте;
   на Welcome и на карте, открытой при запуске, кнопки нет.
7. Свайп вниз по содержимому не закрывает приложение (клиенты с Mini Apps 7.7+).
8. Колесо: SVG с сервера показывается в `<img>`, при обрыве сети — блок с повтором.
9. «Поделиться картой»: открывается выбор чата. Отправляется подписанная ссылка
   на PNG колеса, а в тексте сообщения — ссылка на бота (когда сборка сделана с
   `VITE_BOT_USERNAME`). Проверить, что получатель видит в чате картинку, а
   ссылка на бота открывает приложение, а не только чат с ботом.
10. Тёмная и светлая темы клиента: приложение всегда тёмное, контраст шапки в норме.
11. VoiceOver / TalkBack: заголовок экрана читается при переходе, ошибки и
    статус поиска объявляются.
12. Экран согласия на маленьком телефоне: текст прокручивается, галочка,
    «Продолжить» и «Не сейчас» остаются на месте; галочка читается вместе со
    своей подписью.
13. Документы с экрана согласия: «Назад» возвращает к согласию, отмеченная
    галочка на месте. В тексте согласия видна стрелка «Настройки → …»: в
    headless Chromium без системных шрифтов на её месте был пробел.
14. Отказ по версии согласия на настоящем клиенте: после перезагрузки внутри
    Telegram приложение снова входит (параметры запуска на месте) и показывает
    экран согласия с пояснением либо экран «Условия обновились».
15. Welcome: строка «Подробнее — в пользовательском соглашении.» нажимается
    пальцем и открывает соглашение; «Назад» возвращает на Welcome.
16. Повторный запуск из бота после построенной карты: открывается сразу карта.
    «Ввести данные рождения заново» под ней ведёт на экран согласия с пустой
    галочкой, «Не сейчас» возвращает к карте.
17. Экран согласия на обычном телефоне: ссылки на документы стоят под абзацем
    про статистику и на части экранов уходят под нижнюю панель — видно ли, что
    текст прокручивается.
18. Оплата в тестовом боте, каждым из трёх исходов: оплатить, закрыть счёт,
    счёт с отказом. После оплаты разбор заказывается сам, после закрытия на
    экране нет текста ошибки. Это единственная проверка настоящего
    `openInvoice`: в браузере его играл подставной клиент.
19. Знак ⭐ в ценах: в headless Chromium без системных шрифтов на его месте
    пусто, цена выглядит как «149».
20. Разбор на телефоне: главы появляются по одной; когда разбор готов и над
    главами встаёт оглавление, текст под глазами не прыгает (на iOS особенно:
    там прокрутку удерживает само приложение).
21. Telegram свёрнут во время разбора и развёрнут обратно: экран сразу
    показывает, что успело измениться.
22. Настройки → «Открыть подписки в Telegram» и экран «Данные удалены» →
    «Управлять подписками в Telegram» (ссылка есть только у того, у кого была
    подписка): открывает ли клиент ссылку `tg://settings/star_subscriptions`.
    На iOS, Android и Desktop отдельно.
23. Код обращения на экране ошибки: тап копирует его в буфер.
24. Welcome на маленьком телефоне после появления «Настроек» в углу: заголовок
    и первые пункты видны, остальные прокручиваются.
25. Удаление данных пальцем: быстрое двойное нажатие на «Удалить данные» в
    первом подтверждении ничего не удаляет; «Удалить навсегда» становится
    активной примерно через секунду, и это заметно глазу. На маленьком
    телефоне первое подтверждение длиннее экрана: видно ли, что его нужно
    прокрутить до кнопок.
26. Карточка прогноза на карте: строка обрезается многоточием и не теснит
    колесо на маленьком телефоне; нажатие открывает прогноз.
27. Экран вопроса с открытой клавиатурой: видны поле, счётчик и кнопка
    «Спросить»; после ответа экран показывает ответ, а не остаётся на поле.
28. Вопрос с настоящим сервером: сколько секунд идёт ответ и что видно всё
    это время («Спрашиваем карту…»); быстрое двойное нажатие даёт один ответ
    и списывает один вопрос.
29. Прогноз утром с настоящим сервером: до ночного задания — «Сегодняшний
    прогноз готовится», после — текст; у пользователя в другом часовом поясе,
    чем место рождения, заголовок «на сегодня» совпадает с датой под ним.
30. Удаление данных с действующей подпиской и настоящим сервером (контракт
    1.5.5): после «Данные удалены» приложение, открытое заново, начинается с
    Welcome, подписки и купленного разбора нет. Отдельно посмотреть в
    настройках Telegram, осталось ли там автопродление (issue #29): ссылка с
    экрана «Данные удалены» ведёт именно туда.
31. Удаление на втором устройстве с настоящим сервером: на первом открыта
    карта с купленным разбором. «К разбору», прогноз, вопрос, настройки —
    каждое из этих действий ведёт на Welcome с пустой анкетой, без текста
    ошибки.
32. Две карты и один купленный разбор с настоящим сервером: на карте, для
    которой разбор куплен, — «К разбору», на второй — цена.
33. Удаление данных без подписки: на экране «Данные удалены» нет ни слова о
    подписке и нет ссылки, только «Закрыть». То же у того, чья подписка
    закончилась.
34. Подписка после удаления на втором устройстве, с настоящим сервером и
    тестовым ботом: на первом открыт пейволл, на втором данные удалены, на
    первом оплачена подписка. Экран: «Подписка активна до …», «Карта не
    найдена…», одна кнопка «Построить карту»; она ведёт на Welcome, а в
    настройках подписка на месте. Это единственная проверка того, что
    настоящий сервер выставляет такой счёт и отвечает `Me` с подпиской и без
    карты.
35. Подписчик без карты (подписка оформлена из настроек до первой карты)
    строит карту и нажимает цену на ней: пейволл продаёт разбор, слов «Карта
    не найдена» нет.

## Что намеренно не сделано

- Совместимость и карта года внутри подписки. Описания подписок на пейволле
  называют готовым только то, что приложение уже отдаёт (полные прогнозы,
  пять вопросов в день); про совместимость и карту года там сказано
  «появится в ближайшие дни». В день выпуска любой из них фразу надо
  переписать (`plans` в `ru.ts`).
- История вопросов: на экране одна пара «вопрос — ответ», после ухода с экрана
  она не хранится.
- Прогноз за другой день и уведомление «прогноз готов»: экран показывает то,
  что сервер отдаёт на сегодня, и сам его не ждёт.
- Тизер до первой покупки. Начало разбора (`teaser`) приходит только вместе с
  разбором, а разбор сервер создаёт только после покупки. У того, кто ещё не
  платил, на карте под заголовком «Полный разбор» текста нет: только кнопка с
  ценой.
- «Восстановить карту» в настройках.
- Совместимость и карта года (`compat_249`, `solar_590`): сервер их пока не
  собирает, приложение не продаёт.
- Анкета, заполненная данными уже построенной карты: «Ввести данные рождения
  заново» открывает пустую анкету.
- Память о неподтверждённом платеже через перезагрузку страницы: после неё
  карта снова показывает цену, если сервер платёж ещё не обработал.
- Данные удалены с другого устройства, а эта страница осталась открытой:
  карта остаётся на экране до следующего действия. Приложение узнаёт, что
  карты нет, из ответа на вопрос, прогноз, разбор, заказ разбора, счёт за
  разбор или из `Me`, который перечитывают настройки и проверка платежа за
  разбор (раздел «Карта, которой больше нет»), и тогда ведёт на Welcome; само
  оно сервер об этом не спрашивает, пока пользователь ничего не делает.
  Покупка подписки карту не называет и пройдёт и после удаления. Если её
  подтверждает пейволл, он говорит «Карта не найдена…» и предлагает
  «Построить карту»; если её подтверждает другой экран, приложение открывает
  Welcome без объяснения, а подписка видна в настройках.
- Слов об автопродлении. Сервер при удалении отменяет подписку у себя, а в
  Telegram об этом не сообщает: вызова, который отключал бы автопродление, в
  `apps/api` нет (issue #29). Диалог говорит то, что требует `SPEC.md`, а экран
  «Данные удалены» даёт тому, у кого была подписка, ссылку «Управлять
  подписками в Telegram»; фразы «отключи автопродление» нет ни там, ни там.
  Нужна ли она, решают владелец и бэкенд: это текст про деньги.

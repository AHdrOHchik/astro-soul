# apps/web — Mini App «Разбор личности»

Клиент Telegram Mini App. Закрывает экраны 1–5 из `SPEC.md` и экран согласия
на обработку персональных данных из `legal.md`: Welcome → согласие → BirthDate →
BirthTime → BirthPlace → Chart (колесо, три карточки, тизер разбора,
«Поделиться»). Покупка, Report и Paywall (экраны 6–7) — в следующих итерациях.
Приложение написано под контракт `api.openapi.yaml` версии 1.2.1.

Код живёт в двух пакетах:

| Пакет | Что внутри |
| --- | --- |
| `apps/web` (`@astro-soul/web`) | Приложение: экраны, клиент API, обёртка над Telegram, тексты, токены темы, мок API для разработки |
| `packages/ui` (`@astro-soul/ui`) | UI-кит без текстов и без сети: кнопки, поля, карточки, каркас экрана, состояния. Здесь же базовый `tsconfig` фронтенда и его слой правил ESLint (`eslint.frontend.mjs`) |

Из остального монорепо приложение берёт `@astro-soul/shared` (цены планов) и
`api.openapi.yaml` (типы API).

## Запуск

Нужны pnpm 9 (`packageManager` в корневом `package.json`) и Node 22 не ниже
22.22.2: нижнюю границу задаёт jsdom 31, на котором идут тесты, верхнюю (`<23`) —
`engines` корневого `package.json`.

```sh
pnpm install
pnpm --filter @astro-soul/shared build   # один раз и после правок в packages/shared

# с моком вместо бэкенда, в обычном браузере
API_MOCK=1 VITE_DEV_INIT_DATA=mock-init-data pnpm --filter @astro-soul/web dev

# с настоящим API (по умолчанию проксируется http://localhost:8080)
API_PROXY_TARGET=http://localhost:8080 VITE_DEV_INIT_DATA='<initData>' pnpm --filter @astro-soul/web dev
```

`@astro-soul/shared` подключается собранным, из своего `dist/`. Пока он не
собран, не работают ни `dev`, ни `typecheck`, ни `test`, ни корневой `pnpm lint`.
Dev-сервер кладёт пакет в свой кеш зависимостей и изменений в нём не замечает
даже после обычного перезапуска: после пересборки `packages/shared` запускайте
`pnpm dev --force`.

Те же переменные можно положить в `apps/web/.env` (шаблон — `.env.example`,
сам `.env` в git не попадает). `initData` — это учётные данные: строка входит
от имени своего пользователя, поэтому берите её только от тестового аккаунта.
API принимает только строку, подписанную токеном того бота, с которым он запущен
(`TELEGRAM_BOT_TOKEN`), и не старше 24 часов.

Приложение вызывает `GET /me`, `POST /geo/resolve` и `POST /charts`, а колесо
показывает по `wheel_url` из ответа. В `apps/api` всё это есть. Чтобы API
построил карту, рядом с ним должен работать астро-движок (`pnpm dev:astro` из
корня); как поднять API, движок и базу — в корневом `README.md`.

| Команда (из `apps/web`) | Что делает |
| --- | --- |
| `pnpm dev` | Dev-сервер Vite |
| `pnpm build` | Проверка типов, продакшен-сборка в `dist/`, затем `scripts/check-bundle.mjs` |
| `pnpm preview` | Раздать собранный `dist/` |
| `pnpm clean` | Удалить `dist/` (его же вызывает корневой `pnpm clean`) |
| `pnpm typecheck` | Сверка типов API с контрактом и `tsc` отдельно для кода приложения и для Node-части (конфиг Vite, мок, тесты-охранники) |
| `pnpm test` | Vitest: компонентные и модульные тесты |
| `pnpm size` | Только проверка собранного `dist/` |
| `pnpm gen:api` | Перегенерировать `src/api/schema.gen.d.ts` из `api.openapi.yaml` |

Из корня репозитория `pnpm build | typecheck | test` запускают одноимённые
скрипты во всех пакетах; корневому `pnpm test` нужна ещё и тестовая база для
`apps/api` (см. корневой `README.md`).

Линт один на весь монорепо: `pnpm lint` из корня. Своего конфига ESLint у
фронтенда нет. Корневой `eslint.config.mjs` подключает слой
`packages/ui/eslint.frontend.mjs`, который добавляет к общим правилам
`strictTypeChecked` из typescript-eslint и правила React Hooks — только для
`apps/web` и `packages/ui`. `eslint` в `devDependencies` пакета `packages/ui`
закрывает peer-зависимость `eslint-plugin-react-hooks`. Диапазон версий там
должен совпадать с корневым: с другим диапазоном pnpm ставит в репозиторий
вторую копию ESLint.

## Переменные окружения

| Переменная | Где действует | Назначение |
| --- | --- | --- |
| `VITE_API_BASE_URL` | бандл | Origin API без `/api/v1`. Пусто — тот же origin, что у страницы |
| `VITE_DEV_INIT_DATA` | только dev-сборка | Строка `initData` для запуска вне Telegram. В продакшен-бандл не попадает: `pnpm build` падает, если попала |
| `API_PROXY_TARGET` | dev-сервер | Куда проксировать `/api`, когда мок выключен |
| `API_MOCK` | dev-сервер, `vite preview` | `1` — отвечать моком из `mock/` |
| `API_MOCK_DELAY` | мок | Задержка ответа в мс (по умолчанию 400), чтобы были видны состояния загрузки |
| `API_MOCK_ME` | мок | Сценарий `GET /me`: `returning`, `401`, `500`; иначе новый пользователь |

Секретов у клиента нет. Вход — только по `initData`: приложение держит строку
в памяти и отправляет заголовком `X-Telegram-Init-Data`, токенов не получает и
ничего не кладёт в `localStorage` и cookie. Сам SDK Telegram сохраняет копию
параметров запуска (в них есть `initData`) в `sessionStorage` вкладки, чтобы
пережить перезагрузку страницы; она исчезает вместе с окном Mini App.

## Мок API

`mock/` — middleware dev-сервера, которое отвечает на `/api/v1/*` данными,
типизированными по `src/api/schema.gen.d.ts`: поле, которого нет в контракте,
не пройдёт `pnpm typecheck`. Мок ничего не считает: позиции планет в нём
условные, на колесе написано MOCK. Тексты ошибок и строки короткого разбора —
те же, что отдаёт `apps/api` при контракте 1.2.1. В продакшен-бандл мок не
входит.

Сценарии включаются вводом на экранах:

| Где | Что ввести | Что произойдёт |
| --- | --- | --- |
| Поиск места | `Мос`, `Каз`, `Нов`, `Сан`, `Ека`, `Вла`, `Кал`, `Алм`, `Мин`, `Амс` | Обычная выдача (поиск по началу названия) |
| Поиск места | любое другое, например `Ъъъ` | `200` с пустым списком → «Ничего не нашли» |
| Поиск места | `ошибка…` | `500` → ошибка с повтором |
| Поиск места | `лимит…` | `429 RATE_LIMITED` |
| Поиск места | `провайдер…` | `503 GEO_NOT_FOUND`: справочник мест недоступен → ошибка с повтором |
| Выбор места | `Ошибинск` | `POST /charts` → `500` |
| Выбор места | `Датино` | `422`, отклонено поле `birth_date` → шаг «Дата рождения» с текстом сервера |
| Выбор места | `Времянск` | `422`, отклонено поле `birth_time` → шаг «Время рождения» |
| Выбор места | `Отказово` | `422`, отклонено поле `birth_place` → шаг «Место рождения» |
| Выбор места | `Согласово` | `422`, отклонено поле `consent` → экран согласия |
| Выбор места | `Пустошь` | `201` с пустой картой → пустое состояние |
| Выбор места | `Безколёсово` | Карта есть, картинка колеса не грузится |
| Время | «Не знаю» | Карта без Асцендента и домов |

Мок проверяет форму тела `POST /charts`: без `consent`, без `time_precision`
или со временем при `unknown` он отвечает `422` с `details.field_errors`.
Возраст и часовой пояс он не проверяет — эти отказы сервера показывают сценарии
из таблицы.

Без заголовка `X-Telegram-Init-Data` мок отвечает `401`, как требует контракт.
Поэтому продакшен-сборка, открытая через `API_MOCK=1 pnpm preview` в обычном
браузере, показывает экран «Открой приложение в Telegram» — так и должно быть.

## Устройство кода

```
src/
  main.tsx          точка входа: тема, Telegram, клиент API
  App.tsx           вход (GET /me), стек экранов в памяти, возврат к полю, которое отклонил сервер
  config.ts         единственное место, где читается import.meta.env
  theme.css         все дизайн-токены; base.css — сброс и базовая типографика
  api/              клиент по контракту: http.ts (заголовки, таймаут, повторы), errors.ts, schema.gen.d.ts
  telegram/         единственный модуль, который импортирует SDK Telegram
  i18n/ru.ts        все тексты интерфейса и версия согласия; format.ts — даты, градусы, числа
  lib/birth.ts      разбор и проверка даты и времени рождения, сборка тела POST /charts
  hooks/            useRequest (запрос + отмена + повтор), usePlaceSearch (поиск с задержкой)
  components/       ErrorState — общий вид ошибки запроса
  screens/          экраны; chart/ — колесо, карточки, тизер
  test/fixtures.ts  выдуманные данные и подставные api/telegram для тестов
mock/               мок API для разработки
tests/              тесты-охранники: дизайн-система и юридические тексты (Node, без браузера)
scripts/            проверка собранного бандла
```

### Правила, за которыми следят тесты и сборка

- **Токены.** Цвета, размеры, длительности и градиенты задаются только в
  `src/theme.css`; в остальных CSS — только `var(--…)`. Инлайновых `style` нет.
- **Тексты.** Вся кириллица — в `src/i18n/`. В остальном коде приложения и
  UI-кита её нет даже в комментариях (в тестах можно).
- **Старые движки.** В CSS не используются flex-`gap`, `aspect-ratio`, `inset`,
  `:has()`, `:is()`/`:where()`, `@layer`, `@container`, вложенность.
- Всё это проверяет `tests/design-system.test.ts`; он же ловит неопределённые и
  неиспользуемые токены.
- **Контракт.** `pnpm typecheck` (а значит и `pnpm build`) падает, если
  `src/api/schema.gen.d.ts` разошёлся с `api.openapi.yaml`. После изменения
  контракта — `pnpm gen:api`.
- **Юридические тексты.** Тексты экрана согласия и экранов документов дословно
  совпадают с `legal.md`, а версия согласия меняется вместе с ними — это
  проверяет `tests/legal-texts.test.ts` (подробнее — в разделе «Согласие и
  юридические тексты»).
- **Бандл.** `scripts/check-bundle.mjs` падает, если `dist/` больше 350 кБ gzip
  (лимит из `SPEC.md`) или содержит dev-переменные. `pnpm build` собирает
  продакшен-бандл при любом `NODE_ENV`: без этого сборка с `NODE_ENV=test`
  (так запускает CI) включала в бандл отладочную сборку React.

### Как приложение читает ответы API

- **Ошибки** разбираются по `Problem.code`, а по HTTP-статусу — только если в
  ответе нет тела `Problem` с известным кодом (так может ответить прокси перед
  API). Тогда 401, 402, 403, 404, 409, 422 и 429 дают свои коды, любой другой
  статус — `INTERNAL`. `400` API не использует, поэтому «голый» 400 — тоже
  `INTERNAL`, а не «проверь данные».
- **Текст ошибки.** `Problem.message` — готовый текст для пользователя,
  приложение показывает его как есть. Исключение — текст без единой
  кириллической буквы: так отвечает не API, а прокси или фреймворк, и вместо
  него показывается свой текст. `request_id` виден на экране ошибки как «Код
  обращения».
- **Отказ по полям.** `POST /charts` может ответить `422` со списком
  `details.field_errors`. Приложение возвращает пользователя на самый ранний
  экран, поле которого отклонено (`consent` — согласие, `birth_date` — дата,
  `birth_time` и `time_precision` — время, `birth_place` — место), и показывает
  текст сервера у этого поля; фокус встаёт на поле. Текст исчезает, когда поле
  меняют, а новая отправка стирает все такие тексты. Если сервер назвал только
  поля, которых нет ни на одном экране, ошибка показывается на экране карты.
  Отказ по полю `query` в поиске места показывается у строки поиска.
- **Возраст.** Шаг даты проверяет «18 лет» и «дата не в будущем» по
  календарному дню UTC: так считает `apps/api`, а в контракте день не назван
  (issue #9). Проверка на клиенте только экономит запрос — решает сервер, и
  его отказ по `birth_date` приложение покажет на том же шаге.
- **Поиск места.** `200` с пустым списком — «ничего не нашли». `503` с кодом
  `GEO_NOT_FOUND` значит, что справочник мест недоступен: это ошибка с кнопкой
  повтора, а не пустой результат.
- **Повторы.** Ответ 5xx клиент повторяет до двух раз (через 0,3 и 0,9 с) и
  только потом показывает ошибку. Ответы с другими статусами не повторяются.
- **Точность времени.** Выбранный на шаге времени вариант уходит в `POST /charts`
  как `time_precision` (`exact`, `approximate`, `unknown`) и возвращается в
  `chart.birth.time_precision`; по нему экран карты решает, какое
  предупреждение о точности показать. У карт, построенных до контракта 1.2.1,
  этого поля нет: тогда «время неизвестно» определяется по `birth.time_known`,
  а если нет и его — по `asc === null`.
- **Карта без времени рождения.** `asc`, `mc` и `houses` равны `null`.
- **Неполный ответ.** `mini_reading` и `wheel_url` по контракту обязательны, но
  экран не падает и без них: пустая строка разбора не выводится, вместо колеса
  без адреса — строка «Картинка колеса пока недоступна».

## Согласие и юридические тексты

Экран согласия идёт сразу после Welcome, до первого шага с данными: поиск места
отправляет введённое название на сервер раньше, чем уходит `POST /charts`.

- Галочка по умолчанию не стоит, «Продолжить» неактивна, пока её нет. Отметка
  живёт в памяти вместе с остальными ответами и переживает переход к документу
  и обратно; после перезапуска приложения её нужно поставить снова.
- В `POST /charts` уходит `consent: { accepted: true, version }`. `version` —
  константа `CONSENT_VERSION` из `src/i18n/ru.ts`, дата текста в формате
  `ГГГГ-ММ-ДД`, как требует `legal.md`. Без отметки тело запроса не собирается
  вовсе: `accepted: true` никогда не отправляется за пользователя.
- Тексты экрана согласия — дословно `legal.md`, раздел 2. Ссылки на документы
  открывают экраны самого приложения. Самих документов в репозитории нет,
  поэтому «Политика обработки персональных данных» показывает таблицу и строку
  «Не собираем» из раздела 1, а «Пользовательское соглашение и оплата» —
  дисклеймер из раздела 3. Таблица выводится по строкам (название колонки рядом
  со значением): три колонки рядом на экране 320 px не помещаются.
- Эти тексты в `ru.ts` не редактируются. Новая формулировка приходит из
  `legal.md` вместе с новой датой в `CONSENT_VERSION`.
  `tests/legal-texts.test.ts` сверяет каждый текст с `legal.md` и хранит
  SHA-256 текстов под каждой версией: он падает, если текст разошёлся с
  `legal.md` или изменился без смены версии.

Что в этих текстах не совпадает с приложением. Решает человек: по `legal.md`
агенты юридические тексты не пишут и не меняют.

- Тексты обращаются на «вы», остальной интерфейс — на «ты»; подпись галочки —
  «Я согласен» (мужской род).
- Согласие обещает «Настройки → «Удалить мои данные»». Экрана настроек в
  приложении нет; `DELETE /api/v1/me` в контракте есть.
- Политики и пользовательского соглашения как документов нет: экраны
  показывают только то, что есть в `legal.md`. Когда документы появятся, их
  текст и новая версия согласия должны попасть в приложение вместе.
- На Welcome остался дисклеймер первой итерации. `legal.md` (раздел 3) называет
  обязательным для первого экрана другой текст, с обращением на «вы»; сейчас он
  выводится только на экране соглашения.

## Поддерживаемые клиенты

Сборка нацелена на Safari 15 (iOS 15) и Chromium 80 (Android WebView). Это
допущение: требований к версиям в `SPEC.md` нет. Vite понижает только синтаксис
и полифилов не добавляет, поэтому код приложения не использует API новее этих
движков, а единственный полифил, без которого SDK на них не стартует
(`Object.hasOwn`), лежит в `src/telegram/polyfills.ts`. Android 9 с ни разу не
обновлённым системным WebView (Chromium 69) не покрыт.

На клиентах Telegram старше Mini Apps 6.1 нет системной кнопки «Назад» —
приложение рисует свою. Если SDK не принимает параметры запуска (он проверяет их
по строгой схеме), приложение всё равно входит по «сырому» `initData` и работает
как веб-страница внутри Telegram: со своей кнопкой «Назад», без перекраски
шапки клиента.

## Проверка на устройстве

Автотесты идут в jsdom. Вёрстка просмотрена в headless Chromium на 390×844 и
320×568 с моком. В том же браузере с настоящим API (локальные `apps/api`,
астро-движок и Postgres за прокси dev-сервера) пройдены путь нового
пользователя до карты и отказ сервера по дате рождения. На настоящих клиентах
Telegram (iOS, Android, Desktop) приложение не запускалось. Перед релизом стоит
пройти руками:

1. Запуск из бота: экран входа не мигает, шапка и нижняя панель клиента того же
   цвета, что фон приложения.
2. Welcome на маленьком телефоне: дисклеймер 18+ и кнопка видны без прокрутки.
3. Клавиатура на экранах даты и времени: цифровая раскладка, кнопка «Дальше»
   остаётся видна над клавиатурой, фокус сам переходит между полями.
4. Ошибка в поле, предупреждение после «Не знаю» и блок ошибки поиска места
   прокручиваются в видимую область при открытой клавиатуре.
5. Поиск места: результаты и «Ничего не нашли» не уезжают под клавиатуру;
   клавиша «Найти» на клавиатуре сворачивает её, а не отправляет форму.
6. Системная «Назад»: возвращает на предыдущий шаг, введённые данные на месте;
   на Welcome кнопки нет.
7. Свайп вниз по содержимому не закрывает приложение (клиенты с Mini Apps 7.7+).
8. Колесо: SVG с сервера показывается в `<img>`, при обрыве сети — блок с повтором.
9. «Поделиться картой»: открывается выбор чата. Отправляется подписанная ссылка
   на SVG колеса. Проверить, что получатель видит в чате: если Telegram не
   строит превью для SVG, это будет голая ссылка, и для шаринга нужен другой
   адрес (PNG, страница с OG-тегами или ссылка на бота) — его нет в контракте.
10. Тёмная и светлая темы клиента: приложение всегда тёмное, контраст шапки в норме.
11. VoiceOver / TalkBack: заголовок экрана читается при переходе, ошибки и
    статус поиска объявляются.
12. Экран согласия на маленьком телефоне: текст прокручивается, галочка и
    «Продолжить» остаются на месте; галочка читается вместе со своей подписью.
13. Документы с экрана согласия: «Назад» возвращает к согласию, отмеченная
    галочка на месте. В тексте согласия видна стрелка «Настройки → …»: в
    headless Chromium без системных шрифтов на её месте был пробел.

## Что намеренно не сделано

- Покупка полного разбора: кнопка в тизере называет цену, но неактивна. Цена
  берётся из `@astro-soul/shared` (`priceOf('one_149')`) — по `payments.md` это
  единственное место, где хранятся цены. Сам сценарий оплаты
  (`POST /billing/invoice` → счёт Telegram → повторный `GET /me`) относится к
  экранам 6–7.
- Возврат к уже построенной карте: `GET /charts/{chart_id}` в контракте есть, но
  `GET /me` не отдаёт идентификатор карты, поэтому вернувшийся пользователь
  вводит данные заново. Запрос на контракт — issue #5.
- Предупреждения к карте от сервера: в ответе `POST /charts` их нет. Экран
  карты показывает только то, что выводится из `time_precision`. Запрос на
  контракт — issue #6.
- Аналитика: в контракте нет метода, которым клиент мог бы отправить событие.
  Запрос на контракт — issue #7.
- Экран настроек с удалением данных.

# apps/admin — админ-панель «Разбор личности»

Отдельное SPA для владельца продукта и поддержки: найти человека, вернуть
звёзды, откатить разбор, включить/выключить push, безопасно поменять цену —
без разработчика и без SQL. Написана под контракт `api.openapi.yaml` **1.6.15**.

Панель намеренно не входит в бандл мини-аппа: своё приложение, своя сборка,
свой порт, свои тексты. Общих с `apps/web` модулей нет — `apps/web/http.ts`
носит `X-Telegram-Init-Data`, админке нужны cookie-сессия и CSRF-токен.

## Чего здесь нет (и не будет без решения владельца)

- рассылок и любых массовых операций, в том числе «выделить всё»;
- ручного редактирования текстов отчётов;
- выгрузки ПДн списком: данные рождения показываются на одного человека, по
  запросу поддержки, и этот запрос оставляет запись в аудите; CSV-выгрузки
  журнала аудита тоже нет — `before`/`after` содержат права и суммы, и выгрузка
  превратила бы журнал в файл, который гуляет по чатам;
- собственного SQL и «универсального запроса»: ровно именованные `/admin/*`;
- клиентской арифметики: цена, право на грант и сумма возврата приходят с
  сервера, панель их не пересчитывает и не хранит в константах.

## Запуск

```sh
pnpm install

# с настоящим локальным API (поднятым, например, `pnpm dev:api`)
pnpm dev:admin            # http://localhost:5199, /api/* проксируется на 8080

# без бэкенда — dev-мокер с фикстурами и красной плашкой «ДЕМО»
pnpm dev:admin:mock

pnpm --filter @astro-soul/admin run build      # прод-сборка + страж мока
pnpm --filter @astro-soul/admin run preview    # собранное — на 5299
pnpm --filter @astro-soul/admin run test       # vitest (jsdom)
```

Переменные (`API_MOCK`, `API_PROXY_TARGET`, `ADMIN_DEV_PORT`,
`VITE_TG_BOT_USERNAME`) описаны в `.env.example` в корне репозитория.
`API_MOCK=1` — только `vite dev`: `vite build` с этой переменной падает, а
`scripts/check-no-mock.mjs` дополнительно ищет строки фикстур в `dist`.

## Схема доступа: один origin, никаких исключений

`admin.<домен>` — реверс-прокси на тот же origin, что и API:

```nginx
# правильно: /api/v1/... уходит бэкенду как есть
location /api/ {
  proxy_pass http://api:3000;
}

# НЕЛЬЗЯ: `proxy_pass http://api:3000/;` с косой чертой обрезает префикс
# /api, и каждый маршрут бэкенда отвечает 404. Это самая частая ошибка
# в этой схеме — если панель показывает «нет маршрута» на всём, начиная с
# /admin/me, проверь сначала слэш.
```

Cookie-сессия — `__Host-admin_session`: `HttpOnly`, `SameSite=Lax`, `Secure`
в проде (в dev — по переменной окружения, иначе браузер её выбрасывает на
`http://localhost`). CSRF обязателен на `POST`/`PATCH`/`DELETE` заголовком
`X-Admin-CSRF` — и в dev тоже. CORS нет: он не нужен при одном origin.

## Вход

Вход один: Telegram Login Widget → `POST /api/v1/admin/auth/telegram` (сервер
проверяет HMAC и `ADMIN_TG_ID`, ставит `__Host-admin_session`) → `GET
/api/v1/admin/me` (профиль + CSRF) → `POST /api/v1/admin/auth/logout`. Все три
маршрута пришли в контракте **1.6.15** (`round40-backend`); до этого панель
имела право только сказать «сервер ещё не принимает сессии» — этой заглушки
больше нет, как нет и обходного «Обзора без входа»: публичные `/health` и
`/founders/count` по-прежнему ходят на настоящий API и в ДЕМО не подменяются.

Что из этого следует для кода:

- **`csrf_token` живёт только в памяти вкладки** (`src/auth/tokenStore.ts`).
  Ни `localStorage`, ни `sessionStorage`: токен в них пережил бы закрытие
  вкладки и читался бы любым скриптом на домене, то есть перестал бы быть
  защитой. После перезагрузки страницы панель берёт токен заново из `/admin/me`.
- `X-Admin-CSRF` уходит на каждый `POST`/`PATCH`/`DELETE`, и `authTelegram` —
  единственное исключение (`security: []`: сессии ещё нет, предъявлять нечего).
  Без токена изменяющий запрос **не отправляется вообще** — это локальная ошибка
  `CSRF_MISSING`, а не «сервер отказал».
- **`401` — единственный источник правды** про конец сессии. Индикация «сессия
  до HH:MM» в шапке — подсказка по часам браузера (в `title` так и сказано), а
  гасит вход `onUnauthorized` на любом приватном запросе: экран входа, токен
  обнулён, повторный вход работает без перезагрузки страницы.
- Тексты отказа — пять разных, и подменять один другим запрещено
  (`src/auth/loginErrors.ts`): `401 invalid_hash`, `401 auth_stale`,
  `403 forbidden`, `429` с `details.retry_after` («повтори через N секунд») и
  `404`/«маршрута нет в контракте» → «Сервер ещё не принимает сессии».
  Последняя фраза принадлежит только этому последнему случаю.
- Виджет работает **только на домене, указанном в BotFather → Bot Settings →
  Domain**: на `http://localhost` и на IP он не рисуется, это ограничение
  Telegram, а не панели. Отсюда `VITE_TG_BOT_USERNAME` и два состояния экрана
  входа («не задан бот», «виджет не загрузился»).

## Как панель врёт себе и как это запрещено

Правило одно: нет маршрута — нет данных на экране. Номером раздела оно здесь не
ссылается намеренно: номер может измениться, правило — нет. Реестр `src/api/routes.ts`
хранит для каждого адреса `inContract`, и `http.assertCallable` не выпускает
запрос на путь, которого нет в контракте (в dev-моде — с явным флагом
`allowUnknownRoutes`, который в прод-сборке всегда `false`).

- `src/api/routes.contract.test.ts` — тест-страж: сверяет реестр с ключами
  `paths:` из `api.openapi.yaml` и с версией контракта. Маршрут появился в
  контракте, а флаг не поднят, — тест падает.
- `src/ui/Block.tsx` — единственный рендерер состояний: `unavailable`
  («Недоступно в этой версии» + список маршрутов, дети не рисуются), `error`
  (код + `request_id` + причины по полям), пустой ответ («Пусто»). Нули и
  прочерки вместо данных не показывает.
- `src/screens/NotImplemented.tsx` — разделы, у которых маршрутов нет вовсе
  («Платежи и генерации», «Основатели и партнёры», «Эксплуатация»):
  одна строка + перечень того, чего ждёт экран. «Тарифы» и «Пользователи»
  устроены иначе: их маршруты уже описаны в реестре (с ответами владельца в
  `answers/admin-pr1-review.md`), экраны работают в ДЕМО-режиме, а в проде
  каждый блок показывает «недоступно» со списком адресов — не пустую таблицу.
- Необратимое действие требует второго шага: `ui/HoldConfirm.tsx` (удержание
  кнопки 2 с) и `lib/confirm.ts` (режим с явным вводом значения). Работает на
  отзыве права, смене цены (повтор новой цены) и полном возврате звёзд (повтор
  серверной суммы). Поля «сколько вернуть» на экране нет как класса: возврат
  только полный, сумму считает сервер. Пуш и блокировка — обратимы, но
  блокировка не отправляется без основания.

## Что проверять руками после деплоя

`pnpm --filter @astro-soul/admin run build && pnpm --filter @astro-soul/admin run preview`
рядом с поднятым API, затем в браузере: `/api/v1/health` через домен панели
(не напрямую), `/admin/me` → `401` без cookie и `200` с cookie, `POST` без
`X-Admin-CSRF` → `403`.

Шаги входа и журнала (то, что в ДЕМО проверяется кликом, а в бою — только
человеком на домене из BotFather):

1. `pnpm dev:admin:mock` → «Войти через Telegram» (виджет намеренно не
   работает на localhost, поэтому в ДЕМО вход делает кнопка-заглушка) → панель
   открывается, в шапке имя и «сессия до HH:MM».
2. DevTools → Application: в `localStorage`/`sessionStorage` нет ни одной
   записи про токен. После F5 панель снова спрашивает `/admin/me` и вход
   продолжается.
3. «Выйти» → экран входа, `429`/`403`/`401 auth_stale` воспроизводятся моком
   (см. `mock/plugin.test.ts`), текст у каждого свой.
4. «Аудит»: «Показать ещё» дописывает страницу по `next_cursor` (в Network нет
   ни `page=`, ни `offset=`), `limit=201` в хеше → 422 текстом сервера, пустые
   `before`/`after` → «—», запись планировщика помечена «сервис».

В песочнице браузера нет, поэтому шаги 1–4 за человеком; curl-проверка мока
(та же ветка отказа на каждый случай) — в `docs/qa/reports/`.

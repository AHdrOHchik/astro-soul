# AGENTS.md — правила работы ИИ-агентов в репозитории

> Этот файл — единственный источник правды о процессе. Если инструкция в промпте агента противоречит этому файлу, побеждает этот файл. Правки — только через PR с меткой `process`.

## 0. Роли

| Роль | Ветка | Директории, которые он **владеет** | Что делает |
|---|---|---|---|
| **BACKEND** | `be/NNN-*` | `apps/api/**`, `apps/bot/**`, `packages/astro/**`, `packages/shared/**`, `migrations/**`, `infra/**` | бэкенд, бот, астро-движок, платежи Stars, миграции, деплой |
| **FRONTEND** | `fe/NNN-*` | `apps/web/**`, `packages/ui/**` | мини-апп: онбординг, карта, пейволл, кабинет |
| **QA** | `qa/NNN-*` | `docs/qa/**`, `e2e/**`, `packages/shared/src/contracts/**` (только тесты) | независимая проверка, приёмочные сценарии, вердикт по PR |

Никто не пишет в чужие директории. Если нужно — открывается **запрос на контракт** (см. §5), а не правка чужого кода.

## 1. Общий контур работы

```
Этап 0: инициализация  → агенты читают AGENTS.md, README, docs/ARCHITECTURE.md, контракты
Этап 1: контракт       → FRONTEND/BACKEND правят только contracts/*.json, QA ревьюит контракт
Этап 2: реализация     → каждый в своей ветке, PR в main, обязательные тесты
Этап 3: проверка       → QA ставит вердикт в PR (APPROVE / REQUEST CHANGES), см. §6
Этап 4: интеграция     → только после APPROVE от QA, мердж через squash
Этап 5: релиз          → тег vX.Y.Z, деплой на staging, затем prod
```

## 2. Определение готовности (Definition of Done)

Задача считается сделанной, только если одновременно:

1. Код собирается с нуля (`pnpm install && pnpm build`) без ошибок и предупреждений типов.
2. `pnpm lint` и `pnpm typecheck` проходят без ошибок.
3. Есть тесты: для бэка — unit на бизнес-логику + интеграционный на эндпоинт; для фронта — компонентный тест на критичные экраны; для QA — e2e-сценарий на пользовательский путь.
4. Публичные контракты соответствуют `contracts/`; при изменении — обновлён файл контракта и его версия (semver).
5. Обновлён `CHANGELOG.md` и, если нужно, `docs/`.
6. Нет секретов в коде: только `process.env` / GitHub Secrets.
7. Все новые тексты интерфейса на русском и лежат в `apps/web/src/i18n/ru.ts` / `apps/bot/src/texts/ru.ts` (не хардкодятся в компонентах).
8. Для платёжных изменений — есть тест на идемпотентность и сценарий возврата.
9. Пройден чек-лист безопасности из `docs/qa/checklist.md` (для задач, затрагивающих auth, платежи, ПДн).

## 3. Git и PR

- **Ветки:** `be/NNN-slug`, `fe/NNN-slug`, `qa/NNN-slug`, где `NNN` — номер задачи (см. `TODO.md` / GitHub Issues). Hotfix: `hotfix/slug`.
- **Коммиты:** Conventional Commits (`feat(web): экран онбординга`, `fix(api): идемпотентность платежа`). Один коммит — одно логическое изменение. Сообщения на русском допустимы, тип — латиницей.
- **Размер PR:** ≤ 600 изменённых строк (без lock-файлов и снапшотов). Больше — разбивай.
- **Заголовок PR:** `[BE|FE|QA] NNN краткое описание`.
- **Тело PR** заполняется по шаблону `.github/pull_request_template.md`, включая раздел «Что проверять QA».
- **Мердж:** squash + rebase, ветка удаляется. Прямой push в `main` запрещён (branch protection).
- **Конфликты:** агент решает их только в своих файлах. Конфликт в чужом файле — стоп, комментарий в PR, эскалация к владельцу файла.

## 4. Файлы, менять которые без согласования нельзя

| Файл | Кто может менять |
|---|---|
| `contracts/api.openapi.yaml` | BACKEND как автор, QA как ревьюер; FRONTEND только через issue |
| `contracts/events.md`, `contracts/telegram-payments.md` | BACKEND + QA |
| `contracts/design-tokens.json` | FRONTEND + QA |
| `AGENTS.md`, `docs/*` (кроме `docs/qa/**`) | только по PR с меткой `process` и подтверждением владельца проекта |
| `.github/workflows/*` | BACKEND (CI), QA может добавлять только джобы тестов |
| `migrations/**` | только BACKEND; после мерджа — не редактировать, только новые миграции |

## 5. Запрос на контракт (Contract Request)

Если агенту нужны данные, которых нет в контракте, он **не додумывает**, а:

1. Создаёт issue по шаблону `contract-request` с полями: что нужно, зачем, ожидаемая форма, дедлайн.
2. Пингует владельца контракта в PR/issue.
3. До ответа работает над другими частями задачи за фича-флагом.

**Красный флаг:** агент придумал endpoint/поле, которого нет в `contracts/`, и на этом построил экран — такой PR отклоняется QA автоматически.

## 6. Вердикт QA

QA **не пишет фичи**. Его вывод — один из трёх:

- `APPROVE` — можно мерджить, замечаний нет или только косметика;
- `REQUEST CHANGES` — список блокирующих пунктов с номерами (`QA-1`, `QA-2`...), каждый — воспроизводимый;
- `BLOCKED` — фундаментальная проблема (несовместимость контрактов, дыра в платежах, утечка ПДн), нужен разбор архитектуры.

Формат вердикта — в `docs/qa/report-template.md`. Вердикт пишется **комментарием в PR** и дублируется файлом `docs/qa/reports/NNN-revN.md`.

## 7. Политика «нет доверия по умолчанию»

QA проверяет утверждения агентов, а не верит отчётам:

- «Тесты проходят» → QA запускает сам и прикладывает вывод.
- «Контракт соблюдён» → QA прогоняет валидацию схемы против живого ответа.
- «Платёж работает» → QA проходит сценарий в тестовом боте, включая возврат и повторную доставку события.
- «Данные удаляются» → QA проверяет в БД, что строк действительно нет.

## 8. Секреты и данные

- В репозитории нет токенов, ключей и приватных URL. Только `.env.example`.
- Тестовые персональные данные — только вымышленные. Реальные даты рождения тестировщиков и пользователей в фикстуры не попадают.
- Логи не содержат дату/время/место рождения в открытом виде: только `chart_id`.
- LLM получает обезличенный контекст (без имени, без telegram_id).

## 9. Лимиты и поведение при затыке

- Потолок на задачу: **1 PR, ≤ 600 строк, ≤ 3 итерации правок по замечаниям QA**. На четвёртой — эскалация: issue с меткой `blocked` + краткое описание того, что уже пробовали.
- Агент не «улучшает» чужие модули по пути. Увидел проблему — issue.
- Агент не добавляет зависимости без обоснования в PR: имя, размер, лицензия, зачем, альтернативы.
- Запрещено: отключать тесты, ставить `any`, `@ts-ignore`, `eslint-disable` без комментария-обоснования, коммитить `.env`, менять версию Node/Python без согласования.

## 10. Эскалация к человеку

Эскалация нужна, когда: контракт не agreed после 2 итераций; QA дважды дал `BLOCKED`; затрагиваются ПДн, лицензии или правила Telegram; требуется платная подписка/аккаунт; оценка выросла более чем в 2 раза.

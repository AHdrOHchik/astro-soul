# Правила расчётов: прогноз дня и «спроси карту»

Документ фиксирует **правила школы**, по которым Python-сайдкар считает
детерминированные факты (итерация 30, `POST /forecast/facts`). Модель ничего не
считает: она переводит эти факты в текст. Поэтому правила живут здесь, а не в
промпте и не в голове разработчика.

Код: `packages/astro/astro/daily.py`. Тесты: `packages/astro/tests/test_forecast.py`.

## 1. Управитель дня

Правило — классическое халдейское: день недели → планета.

| День недели | `weekday` | Управитель |
|---|---|---|
| понедельник | 0 | Луна (`moon`) |
| вторник | 1 | Марс (`mars`) |
| среда | 2 | Меркурий (`mercury`) |
| четверг | 3 | Юпитер (`jupiter`) |
| пятница | 4 | Венера (`venus`) |
| суббота | 5 | Сатурн (`saturn`) |
| воскресенье | 6 | Солнце (`sun`) |

`weekday` — ISO-номер дня недели из `date.weekday()` (понедельник = 0).
Управитель дня попадает в набор натальных точек, к которым ищутся транзиты:
если у человека Луна в Овне, а управитель дня — Марс, то транзиты к натальному
Марсу входят в факты дня.

## 2. Момент расчёта

Факты считаются на **полдень местного дня**: `date` + `timezone` из профиля,
12:00, затем перевод в UTC. Для Москвы (UTC+3) это `09:00Z`.

`timezone` — **часовой пояс места рождения**, а не текущего местоположения.
Это смысловое ограничение, а не техническое: «сегодня» у человека начинается
там, где он родился, и прогноз дня должен совпадать с его календарём, а не с
серверным. Ограничение повторено в `timezone_note` ответа и в описании
маршрута — клиент показывает его человеку.

## 3. Луна

- знак и градус — из долготы Луны на момент расчёта (`sign_of`, `degree_of`);
- фаза — по углу «Луна − Солнце», восемь названий:
  новолуние (0°), растущий серп (45°), первая четверть (90°), растущая Луна
  (135°), полнолуние (180°), убывающая Луна (225°), последняя четверть (270°),
  убывающий серп (315°);
- освещённость — `(1 − cos(угол)) / 2`, то есть 0 в новолуние и 1 в полнолуние.
  Формула, а не таблица: таблица разъехалась бы с эфемеридой.

## 4. Ретроградность

Планета ретроградна, если скорость (`speed` из Swiss Ephemeris) меньше нуля на
момент расчёта. Список отсортирован по порядку планет из `constants.PLANETS`,
то есть детерминирован.

## 5. Транзиты к натальной карте

- транзитные планеты — все аспектные (`ASPECT_PLANETS`), кроме узла;
- натальные точки — Солнце, Луна, Асцендент и МС (если время рождения
  известно), плюс управитель дня;
- аспекты — соединение, оппозиция, трин, квадрат, секстиль с орбами из
  `TRANSIT_ORBS`, но **для прогноза дня орб ужесточён до 3°**: день короткий,
  и «аспект в шести градусах» про сегодня ничего не говорит;
- сортировка — по силе (убывание), затем по орбу, затем по ключам планет;
  отдаётся не больше **восьми** сильнейших.

## 6. Окна времени суток

Считаются из транзитов Луны, без модели:

1. день режется на шаги по 2 часа (12 шагов);
2. на каждом шаге ищется аспект Луны (орб ≤ 3°) к натальным Венере/Юпитеру
   («легче») или Сатурну/Марсу («осторожнее»); если ни одного — шаг ровный;
3. соседние шаги одного класса сливаются в интервал, но не длиннее 6 часов:
   иначе ровный день превратился бы в одно окно на сутки;
4. если значимых («легче»/«осторожнее») интервалов меньше двух, добираем
   ровные и подписываем частью суток: «ровный фон: утро». Выдумывать «легче в
   15:00» нельзя — фон действительно ровный;
5. отдаётся 2–3 интервала, по времени начала.

Границы окна — местное время с смещением (`2026-11-20T00:00:00+03:00`).

## 7. Детерминизм

Один и тот же вход (дата, пояс, карта) даёт побайтово один и тот же JSON:
в расчёте нет ни текущего времени процесса, ни случайности, все списки
отсортированы по полным ключам. Это проверяется тестом
`test_facts_are_byte_identical_for_same_input`, и на этом свойстве держится
кэш: `daily_forecasts` хранит факты строкой и не пересчитывает их при чтении.

`ENGINE_VERSION = 1.1.0` — версия, в которой появились эти расчёты.
Смена версии не пересчитывает уже сохранённые прогнозы: у каждой строки
`daily_forecasts.engine_version` записан свой.

# Бэкапы БД: `scripts/db-dump.sh`

Операционный документ: как делается дамп, куда он уезжает, как убедиться, что всё
живо, и что делать, когда алерт `backup_stale` сработал.

Короткая версия: **дамп считается сделанным только после выгрузки с сервера.**
Локальный файл — не бэкап: он умирает вместе с диском.

---

## 1. Что делает скрипт

`scripts/db-dump.sh`:

1. проверяет настройки и свободное место;
2. делает `pg_dump --format=custom` во временный `.<имя>.partial`;
3. переименовывает его в `astro-soul-YYYYMMDDTHHMMSSZ.dump` (UTC, атомарный `mv`
   в том же каталоге);
4. выгружает файл с сервера — `aws s3 cp` (S3-совместимое хранилище) или `scp`
   на отдельный хост;
5. **после** успешной выгрузки переписывает файл-маркер `BACKUP_STATE_FILE`;
6. удаляет локальные дампы старше `BACKUP_RETENTION_DAYS` (по умолчанию 7 дней).

Формат `custom` (`-Fc`) — не `pg_dumpall` и не `pg_dump` в `psql`-скрипте: он
сжимается сам, восстанавливается через `pg_restore` выборочно (одна таблица,
если нужно) и не содержит `CREATE DATABASE`.

## 2. Переменные окружения

Секретов в репозитории нет: креденшелы S3 берутся из окружения или `~/.aws`
(штатное поведение `aws`), ключи `scp` — из `~/.ssh`.

| Переменная | Обязательна | Назначение |
|---|---|---|
| `DATABASE_URL` | да | Строка подключения к прод-БД. Лучше — пользователь только на чтение |
| `BACKUP_S3_URL` | одно из двух | `s3://bucket/prefix`, куда кладётся файл |
| `BACKUP_REMOTE` | одно из двух | `user@host` для `scp` (другой сервер/диск) |
| `BACKUP_DIR` | нет | Локальный каталог, по умолчанию `var/backups` |
| `BACKUP_RETENTION_DAYS` | нет | Сколько дней держать локальные копии, ≥ 7, по умолчанию 7 |
| `BACKUP_MIN_FREE_MB` | нет | Минимум свободного места перед дампом, по умолчанию 512 |
| `BACKUP_STATE_FILE` | да, для алерта | Файл-маркер; тот же путь, что `BACKUP_STATE_FILE` у API |
| `PG_DUMP_BIN` | нет | Путь к `pg_dump`, если он не в `PATH` |

Если не задан ни `BACKUP_S3_URL`, ни `BACKUP_REMOTE`, скрипт **падает** с кодом
2. Это осознанно: «сделал локально и успокоился» — худший вид бэкапа.

## 3. Как запустить

Вручную:

```bash
export DATABASE_URL='postgres://astro_soul:***@127.0.0.1:5432/astro_soul'
export BACKUP_S3_URL='s3://astro-soul-backups/pg'
export BACKUP_STATE_FILE='/var/lib/astro-soul/backup-last-success'
./scripts/db-dump.sh
```

Из cron, ежедневно в 03:30 UTC:

```cron
30 3 * * * cd /srv/astro-soul && set -a && . ./.env && set +a && ./scripts/db-dump.sh >> /var/log/astro-soul-backup.log 2>&1
```

Сначала запусти руками и посмотри на вывод: скрипт печатает каждый шаг с
UTC-временем.

## 4. Куда кладутся файлы

- локально: `${BACKUP_DIR}/astro-soul-20261120T033000Z.dump` (и временный
  `.<имя>.partial`, который существует только во время дампа);
- на удалённой стороне: `${BACKUP_S3_URL}/astro-soul-20261120T033000Z.dump` или
  `user@host:` в домашнем каталоге пользователя (см. `BACKUP_REMOTE`);
- маркер: `${BACKUP_STATE_FILE}` — текст `file=`, `size_bytes=`, `uploaded_at=`.
  Обновляется **после** выгрузки; его mtime читает API.

Ротацию на удалённой стороне делает не этот скрипт, а хранилище: в S3 —
lifecycle-правило (например, «хранить 30 дней, потом в Glacier»), на отдельном
хосте — свой cron. Локально скрипт держит не меньше недели истории.

## 5. Как проверить, что бэкап есть

```bash
# 1. Локальный файл и его размер
ls -lh var/backups/astro-soul-*.dump | tail -3

# 2. Маркер: когда был последний успех
cat /var/lib/astro-soul/backup-last-success
stat -c '%y %n' /var/lib/astro-soul/backup-last-success

# 3. Копия на удалённой стороне (S3)
aws s3 ls s3://astro-soul-backups/pg/ | tail -3

# 4. Что видит API (нужен admin initData — см. QA-отчёт итерации 36)
curl -s https://<host>/api/v1/admin/alerts -H "X-Telegram-Init-Data: <admin initData>" | jq '.alerts[] | select(.id=="backup_stale")'
```

`backup_stale` в `GET /admin/alerts`: `value` — возраст последнего успеха в
часах, `threshold: 36`, срабатывание — старше 36 часов **или** маркера нет.
`null` в `value` означает «маркера нет»: либо бэкап ни разу не проходил, либо
`BACKUP_STATE_FILE` не задан у API. Оба случая одинаково плохие, и молчание
здесь не значит «всё хорошо».

Ожидаемый размер: база с реальными данными — единицы-десятки мегабайт;
`-Fc` сжимает примерно в 5–10 раз относительно дампа в SQL. Файл в 0 байт или
файл, который меньше предыдущего в разы, — повод проверить `pg_dump` и место на
диске, а не «повезло со сжатием».

## 6. Коды выхода

| Код | Что значит | Что делать |
|---|---|---|
| 0 | дамп сделан и выгружен | — |
| 2 | не настроено окружение, нет `pg_dump`/`aws`/`scp`, не задан `DATABASE_URL` | проверить переменные и `PATH` в cron (частый случай: cron не читает `.env`) |
| 3 | меньше `BACKUP_MIN_FREE_MB` свободного места | почистить старые дампы/логи, расширить диск |
| 4 | `pg_dump` завершился ошибкой | смотреть stderr: обычно кончились соединения, место или нет `SELECT`-прав |
| 5 | выгрузка не удалась | проверить ключи `aws`/`scp` и доступность хранилища; локальный файл удалён намеренно |
| 6 | не удалось записать маркер | дамп выгружен, но мониторинг не узнает: проверить права на каталог `BACKUP_STATE_FILE` |

При коде 5 локальный файл **удаляется**: половина бэкапа, принятая за бэкап,
опаснее, чем явная ошибка. Диагностика — в логе cron, там же текст ошибки
`aws`/`scp`.

## 7. Восстановление

**Статус: не проверено.** В песочнице разработки нет прод-данных и прод-БД,
поэтому реальное восстановление здесь не выполнялось. Ниже — процедура, которую
нужно один раз прогнать руками перед тем, как считать бэкапы рабочими.

1. Поднять пустую БД той же мажорной версии (`postgres:16`).
2. Восстановить:
   ```bash
   pg_restore --dbname "$RESTORE_DATABASE_URL" --no-owner --no-acl --clean --if-exists \
     astro-soul-20261120T033000Z.dump
   ```
   без `--clean --if-exists` — на пустую базу.
3. Сверить: `SELECT count(*) FROM users;`, `SELECT count(*) FROM payments;`,
   `SELECT max(created_at) FROM events;` — числа должны быть «примерно как в
   проде на момент дампа».
4. Поднять API на восстановленной базе и пройти `GET /health` и `GET /me`.
5. Записать в этот раздел дату проверки и результат.

Пока пункт 7 не пройден, честная формулировка такая: **дампы делаются и лежат
вне сервера, восстановление из них не проверялось.**

## 8. Что этот скрипт не делает

- не бэкапит приватное хранилище файлов (`FILE_STORAGE_DIR`: PDF разборов и
  карточки шаринга). Карточки восстановимы по содержимому (кэш), PDF — тоже
  пересобираются из разбора; но если файлы нужны как есть, каталог копируется
  отдельной задачей;
- не бэкапит `.env` и секреты (они хранятся в менеджере секретов, а не в
  репозитории);
- не шифрует файл на стороне скрипта: шифрование делает хранилище (SSE для S3,
  шифрованный том для отдельного хоста). Если хранилище без шифрования — это
  отдельная задача, а не «добавим `gpg` в скрипт».

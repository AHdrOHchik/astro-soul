# Локальный запуск через Docker

`docker-compose.yml` в корне поднимает только инфраструктуру: **Postgres 16** и
**Redis 7**. Сам API и астро-движок запускаются процессами Node/Python — так
проще смотреть логи и перезапускать по одному.

```bash
docker compose up -d              # postgres + redis
cp .env.example .env              # заполнить секреты (BOT_TOKEN, PSEUDONYM_PEPPER)
pnpm install
pnpm db:migrate                   # схема
pnpm db:seed                      # таблица plans = packages/shared/src/plans.ts
pnpm dev:api                      # API на PORT из .env
pnpm dev:astro                    # сайдкар астро-движка (нужен для /charts)
```

Проверить, что окружение не «стендовое», перед выкладкой:

```bash
./check.sh --prod
```

Скрипт читает только переменные окружения процесса (не `.env`) и выходит с
кодом 1, если находит настройки, допустимые только в тестах: подменённый
`TELEGRAM_API_BASE_URL`, `LLM_FAKE=1`, выключенные лимиты
(`RATE_LIMIT_*=0`) и флаг тестовых тарифов (ниже).

## Тестовые тарифы за 1 ⭐

Владельцу нужен настоящий путь оплаты в клиенте Telegram, а 149–399 ⭐ для
проверки дорого. Денежных путей два, тестовых тарифов тоже два, флаг один:

| plan_code | Что | ⭐ |
|---|---|---|
| `test_1` | подписка на неделю, права как `month_399` | 1 |
| `test_report_1` | разовый разбор на одну карту, как `one_149` (без `subscription_period`) | 1 |

В проде их нет: тариф существует только при явно включённом флаге.

**Как включить подписку (только на стенде или локально):**

```
1. В .env: PAYMENTS_TEST_PLANS=1
2. Перезапустить API (не только сборку)
3. В приложении вызвать POST /billing/invoice с plan_code=test_1
   (или временно подставить test_1 в пейволл руками — в код это не коммитим)
4. openInvoice → заплатить 1 ⭐
5. GET /me → subscription.is_active: true, plan: month, expires_at: +7 дней
6. После теста: editUserStarSubscription(is_canceled: true) через DELETE /me
   ИЛИ отписаться в настройках Telegram → Мои звёзды → подписки
7. В .env убрать PAYMENTS_TEST_PLANS, перезапустить API
```

Пункт 6 — не формальность: **подписка живёт в Telegram, а не в базе**. Если её
не отменить, Telegram спишет 1 ⭐ ещё раз через неделю — и это будет первый
реальный рекуррентный платёж в проекте, на тарифе, который потом удалят.

**Почему нельзя на проде:**

- при включённом флаге любой, кто знает код `test_1` (а код есть в репозитории),
  покупает подписку за одну звезду через обычный `POST /billing/invoice`;
- `./check.sh --prod` поэтому падает с кодом 1 и называет переменную;
- в `docker-compose.yml`, `.env.example` и `docs/DOCKER.md` значение по
  умолчанию не выставлено: включить флаг можно только руками, в конкретном
  окружении, и так же руками его видно в `check.sh`.

**Как проверить разовый разбор (второй путь):**

```
1. В .env: PAYMENTS_TEST_PLANS=1, перезапустить API
2. POST /billing/invoice { plan_code: "test_report_1", chart_id: "<ваша карта>" }
3. openInvoice → заплатить 1 ⭐
4. GET /me → entitlements.full_report: true, full_report_chart_id = <ваша карта>
5. Открыть разбор → генерация → семь глав
6. Построить вторую карту → на ней должна быть ЦЕНА, а не «К разбору»
7. Убрать PAYMENTS_TEST_PLANS из .env, перезапустить API
```

Пункт 6 — самая ценная проверка: именно на ней в итерации 11 нашёлся дефект
«оплата привязана к пользователю, а не к карте». На тестовом тарифе он
воспроизводится за 1 ⭐ вместо 149 ⭐.

Настоящая генерация стоит реальных денег у Сбера (~17,5 ₽ за разбор, с
перегенерациями ~23 ₽ при выручке 1,2 ₽). Если проверяется только путь
«оплатил → доступ → экран разбора», включите `LLM_FAKE=1`: разбор-заглушка
бесплатен, а путь оплаты от этого не меняется. Настоящую генерацию включайте,
когда проверяете качество текста, — это разные проверки. `LLM_REPORT_CAP_RUB`
(80 ₽) и `LLM_MONTHLY_CAP_RUB_FORECAST` при этом не меняются.

Учёт: тестовый платёж помечается `payments.is_test = true`, не входит в
выручку (`stars_received_30d`), в `paying`/`conversion_to_paid` и в счётчики
отказов; в `/admin/metrics` он виден отдельным полем `test_payments_30d`.
Ненулевое значение на проде — забытый флаг.

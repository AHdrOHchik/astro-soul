# round30_3: сквозные сценарии и границы проверки

| Сценарий | Тест(ы) | Что именно проверяет | Чего тест не проверяет |
|---|---|---|---|
| B1 — карта исчезла | `apps/web/src/App.test.tsx` — «after forecast reports a deleted chart…»; `apps/web/src/screens/QuestionsScreen.test.tsx` — 404 при отправке; `apps/web/src/screens/compatibility/CompatibilityScreen.test.tsx` — 404 старой ссылки; `apps/web/src/screens/settings/SettingsScreen.test.tsx` — 500 удаления данных | 404 `chart_not_found` на «Сегодня» переводит приложение в состояние без карты; следующий рендер «Сегодня» не делает `GET /forecast/today`; свежий `GET /me` сохраняет в тесте те же оплаченные подписку и квоты; ошибочное удаление не объявляет данные удалёнными. Старые данные разбора/совместимости не показываются как актуальные после 404. | В контракте нет отдельного `DELETE /chart`; тест симулирует серверное обнаружение исчезновения карты и свежий ответ `/me`, а не реальное удаление записи из БД. 500 проверяется для существующего `DELETE /me` (удаление всех данных), не для отдельной карты. |
| B2 — разбор удалён | `apps/web/src/screens/report/ReportScreen.test.tsx` — известный ID отвечает 404; `apps/web/src/App.test.tsx` — свежий `GET /me` больше не содержит `latest_report_id` | У старой ссылки на разбор экран явно сообщает «Разбор удалён», не оставляет текст глав; предлагает создать новый разбор. Приложение забывает ID после 404 и нового `GET /me` с `latest_report_id: null`; локальные тесты существующего удаления подтверждают, что ошибка запроса `DELETE /me` не завершает удаление/не переводит приложение на success-экран. | В контракте нет `DELETE /reports/{id}` и отдельного `GET /reports` списка. Поэтому тестирует реакцию на 404 старого ID и свежий `/me`, но не реальное удаление разбора и не физическое исчезновение из отсутствующего списка. |
| B3 — оплата ожидается, но не подтверждена | `apps/web/src/screens/paywall/PaywallScreen.test.tsx` — Telegram вернул `pending`, `GET /me` не даёт права; повтор после отмены счёта; конфликт 409/already_paid | Без серверного права экран остаётся в ожидании: нет товара/доступа, callback разблокировки не вызывается. После закрытия отменённого счёта следующая попытка запрашивает новый invoice URL. При 409 состояние перечитывается через `GET /me`; переход разрешается только если свежий ответ действительно даёт доступ. | jsdom подменяет результат Telegram (`paid`/`pending`/`cancelled`): здесь проверяется только реакция интерфейса на этот ответ и мок API, а не реальное закрытие нативного окна, доставка `successful_payment`/webhook или задержка Telegram. Это требуется отдельно проверить вручную в Telegram на тестовом платеже; до такой проверки результат оплаты не считается end-to-end подтверждённым. |

**Контрактная граница:** не добавлялись отсутствующие в OpenAPI индивидуальные ручки удаления или список разборов; тесты используют документированные 404/GET `/me` и существующий `DELETE /me`. Отсутствие этих ручек — ограничение сквозной проверки, не новая клиентская имитация API.

## Что и почему

В round30_3 приводим отображение `failed` в списках, квоты после неудачных запросов и empty-state к контракту backend 1.6.7. Дополнительно закрываем три проверяемых без живого API сквозных маршрута и ровно четыре дизайн-аудит находки из заданных 18. Остальные 14 не входят в объём.

## Что сделано

- В списках совместимостей и вопросов `failed` тихо фильтруется на клиенте; типы и прямая загрузка записи не меняются. У совместимости после фильтра пустое состояние получает цену из `GET /billing/plans`; `refused` в истории вопросов остаётся нормальной записью.
- Для прямой загрузки неудачного разбора добавлено ясное сообщение и действие повторить. После неудачных forecast/question/compatibility обновляются данные квот; пустые ответы и empty-state не превращаются в сетевые ошибки.
- Добавлены сценарии карты, старой ссылки на разбор и pending payment на моках. Контрактных отдельных ручек `DELETE /chart` и `DELETE /reports/{id}` и списка разборов в `api.openapi.yaml` нет — клиент не изображает их существующими.
- Бесплатные примеры вопросов больше не кнопки; разделены повторы загрузки истории и отправки вопроса. Для прогноза установлен только локальный 30-секундный deadline; timeout отделён от offline. Отсутствующие facts не подменяются выдуманными значениями.
- При возврате из окна invoice созданный invoice не переиспользуется. `409/already_paid` может открыть доступ только после свежего `GET /me` с соответствующим правом; одного ответа Telegram или старого `/me` недостаточно.
- **Дизайн-аудит:** исправлены ровно 4 из 18 находок `AUDIT.md`: №13, №9, №14, №15 (C1–C4 из задания). Затронутые файлы: `apps/web/src/screens/DailyForecastScreen.tsx`, `apps/web/src/screens/DailyForecastScreen.test.tsx`, `apps/web/src/api/daily-questions.test.ts`, `apps/web/src/api/http.ts`, `apps/web/src/api/http.test.ts`, `apps/web/src/api/index.ts`, `apps/web/src/screens/QuestionsScreen.tsx`, `apps/web/src/screens/QuestionsScreen.test.tsx`, `apps/web/src/i18n/round30.ts`. Сам `AUDIT.md` в этой рабочей копии не найден; номера и ограничение «только четыре» сохранены из задания.
- Таблица сценарий → тесты → проверяемое/непроверяемое: [`docs/qa/round30-3-scenarios.md`](round30-3-scenarios.md).

## Что проверять QA

- Удалить карту в Telegram: Today, старая ссылка на разбор и сохранённая совместимость должны не выглядеть текущими; подписка/квоты — после свежего `/me`; отдельно проверить ошибку удаления.
- Удалить разбор и открыть прежнюю ссылку: должен быть текст «Разбор удалён»; проверить состояние списка и `latest_report_id` сервером. В UI контракте нет отдельного endpoint удаления/списка, см. ограничения ниже.
- Реальный invoice-return в Telegram: закрытие/отмена без `successful_payment`, ожидание webhook, свежий invoice при повторе, конфликт `already_paid`. jsdom тестирует только callback и реакцию UI на мок API — реальное поведение Telegram остаётся ручной проверкой, платежи для проверки только тестовые.
- Прогноз: проверить живой ответ позже 20 секунд, 30-секундный timeout и retry в Telegram WebView; проверить timeout отдельно от отключённой сети.

## Контракт

Контракты не менялись. Списки и квоты читаются по существующим OpenAPI 1.6.7. Фильтрация `failed` — защита UI на случай кэша/гонки, а не изменение серверных статусов. Отдельные ручки `DELETE /chart`, `DELETE /reports/{id}` и `GET /reports` в `api.openapi.yaml` отсутствуют; тесты проверяют только документированные ответы 404/`GET /me` и существующий `DELETE /me`.

## Не проверено

- Живой API, Telegram WebView и настоящий платёж не использовались. В частности, пользовательский возврат из системного Telegram invoice и получение `successful_payment`/webhook требуют ручного QA.
- Удаление отдельного разбора и отдельной карты нельзя провести сквозным UI/API тестом без контрактных endpoints. Тесты проверяют реакцию на 404 и последующий `/me`, а не изменение БД.
- Сравнение gzip — с указанным baseline 113.9/121.0 kB; прирост общий +0.8 kB. Текущая сборка не превысила бюджет.

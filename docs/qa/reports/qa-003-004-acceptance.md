## 2. Осталось / новое

### A (блокер). `DELETE /me` обезличивает платёж не полностью: `user_id` остаётся, а он детерминирован из `telegram_id`

**Шаги** (`node /tmp/resurrect-sub.mjs`, стенд :8083):

1. пользователь покупает `year_2990` → `/me`: `plan: year`, `is_active: true`, `expires_at` +365 дней;
2. `DELETE /me` → `204`;
3. тот же `telegram_id` впервые открывает мини-апп (`GET /me`).

**Получено:**

```
1. подписка куплена: plan=year is_active=true expires_at=2027-11-14 stars_paid_total=2990
2. после DELETE /me: подписок в БД: 1 | статус: active
3. вернулся: is_new = true
   подписка: plan=year is_active=true expires_at=2027-11-14 stars_paid_total=2990
   entitlements.is_active = true | ask_per_day = 5 | full_forecast = true
```

**Почему так.** `me.service.ts:133` обезличивает платёж односторонне:

```sql
UPDATE payments SET telegram_id = NULL, anonymized_at = now()
 WHERE user_id = $1 AND anonymized_at IS NULL
```

`user_id` при этом остаётся. А `users.repository.ts:51` → `userIdFromTelegramId()` считает `user_id`
как `HMAC-SHA256(PSEUDONYM_PEPPER, "telegram:<id>")`, то есть **из `telegram_id` детерминированно**.
При первом входе после удаления `ensureUser` вставляет строку `users` с тем же `id`, и старые
`payments(user_id)`, `entitlements(user_id)` и `subscriptions(user_id)` снова указывают на живого
пользователя.

**Последствия по состояниям:**

| Что | До удаления | После возврата | Ожидание |
|---|---|---|---|
| подписка | `active`, `year` | **`active`, `year`, все права** | подписка живёт до конца периода, но новый аккаунт её не «наследует» молча |
| `entitlements` на разбор | `active`, `chart_id = A` | `active`, `chart_id = NULL` | — |
| `GET /me` | `full_report: true` | **`full_report: true`** | |
| `POST /reports` на новую карту | — | **`402 PAYMENT_REQUIRED`** | 402 корректен: оплаты за новую карту не было |
| `payments.user_id` | `user_id гражданина` | **тот же `user_id`, уже живой** | не должен ссылаться на восстановленную `users` |

То есть деньги за разбор второй раз не теряются (402 на `POST /reports` — хорошо), но **подписка
воскресает целиком, включая `stars_paid_total`**, и учёт «кто заплатил» снова связан с человеком,
который просил удалить свои данные. Задание требует ровно обратного: «`payments.user_id` не ссылается
на восстановленную `users`».

**Замечание к QA-15 из 002.** Блокер 002 просил, чтобы «платёж после `DELETE /me` не выдавал права».
Это выполнено: в прогоне `delete-then-pay` платёж `rejected`, `entitlements` пусты, `refundStarPayment`
вызван, вебхук на отказ — `200`. Но условие «`payments.user_id` не ссылается на восстановленную
`users`» не выполнено ни до, ни после — это остаток, который итерация 9 не закрывала, а итерация 10
не тронула.

**Что нужно решить (нужно решение владельца, это не только код):**

1. обнулять `user_id` вместе с `telegram_id` при удалении (`payments`, `entitlements`, `subscriptions`)
   — тогда «воскресать» нечему, но возвраты по `charge_id` остаются возможны;
2. либо оставить `user_id` для бухгалтерии, но добавить в `entitlements`/`subscriptions` проверку
   «запись создана до создания текущего `users`» — признак жизни, а не личности;
3. и в любом случае — отдельный тест: «удалился, вернулся, подписки и прав не прибавилось».

### B (не блокер). `full_report_chart_id` отдаётся, но фронт его не читает

PR #24 обещает: «после `DELETE /me` и новой карты → `full_report_chart_id: null` … фронт не считает
новую карту оплаченной». Сервер отдаёт поле верно (проверено на Б-1). Но `grep full_report_chart_id`
по `apps/web/src` даёт **ноль** вхождений вне `schema.gen.d.ts`: фронт читает только
`me.entitlements.full_report` (`App.tsx:451`) и потому на неоплаченной новой карте рисует
**«Получить разбор»** вместо цены. Пользователь нажимает — получает `402`, и это единственное, что его
останавливает. Данные для правильного решения на клиенте уже приходят; решения нет.

### C (не блокер). `VITE_SUBSCRIPTIONS` из задания в коде отсутствует

Задание: «`VITE_SUBSCRIPTIONS` (нет → кнопка `disabled` с текстом), выключенные подписки → блока
тарифов нет в DOM». В `apps/web/src` переменной нет ни в `config.ts`, ни в `env.d.ts`, ни в
`.env.example`; подписки в пейволле зашиты константой `SUBSCRIPTION_PLANS` (`lib/plans.ts:14`).
Ни проверки «включено ли», ни ветки «не показывать блок» нет. Две другие переменные из того же пункта
работают: `VITE_SUPPORT_CONTACT` пустой → `SupportButton` рендерит `disabled` с текстом
«Поддержка скоро появится» (`SupportButton.tsx:16-21`), `VITE_BOT_USERNAME` собирается в ссылку
`https://t.me/<имя>?startapp=chart_<id>`.

### D (не блокер). `TELEGRAM_API_BASE_URL` нет в `.env.example`

Переменная есть в `config/env.ts:20` и работает, но в шаблоне окружения её нет. Стенд, поднятый по
`.env.example`, уходит в настоящий `api.telegram.org`; в песочнице это `telegram_unreachable` →
`POST /billing/invoice` `502` и **ноль инвойсов**, что легко прочитать как «QA-15 не воспроизводится».
Именно так и случился первый невалидный прогон этой сессии. Правка на одну строку.

### D-бис (не блокер). Штатный стаб Bot API не умеет `403` и `429`

`e2e/qa/bot-stub.mjs` на любой метод отвечает `200` (`fail` умеет только `ok:false` с
`error_code: 400`), а `TelegramClient.sendPush` различает «заблокировал» и «слишком часто» **по
HTTP-статусу** (`telegram.client.ts:130-138`). То есть ветки `403 → push_blocked_at` и
`429 → deferred` штатным стендом не воспроизводятся вообще. В приёмке использован расширенный стаб;
предлагаю перенести его в `e2e/qa/` — иначе эти два требования задания остаются непроверяемыми
без ручной правки стенда.

### E (не блокер). `full_report: true` при `latest_report_id: null` ведёт на «Получить разбор» → 402

Прямое следствие A+B: новый пользователь с воскресшим `full_report` видит на карте кнопку «Получить
разбор», жмёт её и получает `402`. Экран не объясняет, что разбор надо купить заново, — он говорит
«Полный разбор — отдельная покупка» только после отказа. Лечится тем же, что B: читать
`full_report_chart_id`.

### Мелочь. События, пережившие `DELETE /me`, ссылаются на удалённого пользователя

`events.user_id` не имеет FK, и после удаления остаются строки с `user_id` удалённого
(`invoice_created`, `payment_rejected`, `refund_issued` — 3 штуки в прогоне QA-15). ПДн в них нет
(только `plan`, `stars`, `code`), так что это не утечка, но «события мёртвого пользователя» — такая же
недоделка обезличивания, как A. Найдено попутно, в блокеры не выношу.

## 7. Пуш 08:00 (задача 6) — закрыт

Фикстуры — 4 карты в зоне `America/Anchorage` (местное 07:51, окно 08:00±30), у трёх пользователей
активность «сейчас», у четвёртого — 8 дней назад. Стабу заданы адресные отказы: `sendMessage` → `403`
для второго чата и `429` (с `retry-after`) для третьего.

```
{'pushes_sent': 1, 'pushes_skipped_inactive': 1, 'pushes_deferred': 1, 'pushes_failed': 0}
```

| Требование | Получено |
|---|---|
| отбор по местному времени **места рождения** | 4 карты в окне 07:30–08:30 попали, остальные — нет |
| только активные 7 дней (обе стороны) | активный доставлен, «8 дней» → `pushes_skipped_inactive: 1` |
| `403` → пометка карты | `charts.push_blocked_at` заполнен, `forecasts.push_sent_at` пуст |
| `429` → `pushes_deferred`, без ретрая | `pushes_deferred: 1`; **повторный прогон** снова даёт `deferred: 1` и **ни одного нового вызова** `sendMessage` (всего 4 за оба прогона) |
| счётчики | все четыре в `JobRunResult` и в ответе джоба |
| текст 1–2 предложения + кнопка | `"День про ясность. Собери силы.\n\nПолный прогноз — в приложении."` + `inline_keyboard` с `Проверить`→`Открыть`, `web_app.url = https://t.me/qa_bot?startapp=chart_<id>` |

Повторный прогон: `{'pushes_sent': 0, 'pushes_skipped_inactive': 1, 'pushes_deferred': 1,
'pushes_failed': 0}` — отправленное второй раз не уходит, 403-карта больше не пушится.

**Про 429 уточнение, важное для чтения задания.** «В этом прогоне не ретраим» — это ровно одна
попытка за прогон, а не «навсегда пропущен»: следующий прогон в том же окне попробует снова, иначе
прогноз, не доставленный в 08:00, не дошёл бы никогда. Проверено на нашем чате: после первого прогона
к нему ровно 1 попытка, после второго — 2, а `forecasts.push_sent_at` по-прежнему `NULL`. Это
соответствует `infra/cron.md` («в этом прогоне не ретраим») и расходится только с более сильным
прочтением «не ретраим никогда», которого в задании нет.

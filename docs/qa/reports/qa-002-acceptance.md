## 3. Осталось

### QA-15 (блокер, приоритет №1). Платёж после удаления данных по-прежнему выдаёт права и воскрешает пользователя

Воспроизведено на PR #20 в **двух порядках**. `node e2e/qa/acceptance-002.mjs delete-then-pay`.

**Порядок A: инвойс → `DELETE /me` → `pre_checkout_query` → `successful_payment`**
```
инвойс выставлен: 201 payload.u=<id пользователя A>
DELETE /me: 204
после удаления invoices: 1|created          ← инвойс не инвалидирован
pre_checkout_query после удаления: вебхук=200 | ответ бота= {"ok":true}
successful_payment после удаления: вебхук=200
payments    : one_149|processed|t
entitlements: report|active
invoices    : paid
/me full_report= true  is_new= true          ← пользователь создан заново
```

**Порядок B: инвойс → `pre_checkout_query` → `DELETE /me` → `successful_payment`**
```
DELETE /me между событиями: 204
successful_payment: вебхук=200
payments    : one_149|processed|t
entitlements: report|active
refundStarPayment вызовов: 0
события: invoice_created, payment_processed
```

- **Ожидалось (задание 002, §4):** инвойс инвалидируется на `DELETE /me`; оплата по нему → автовозврат звёзд; доступ не выдаётся; событие в метриках.
- **Получено:** доступ выдан, звёзды не возвращены, события отказа нет. После удаления `is_new=true` — пользователь создан заново, а оплаченный разово разбор привязан к `chart_id`, которого уже нет: `charts` удалены каскадом вместе с `users`, `invoices.chart_id` — `ON DELETE SET NULL`.
- **Код:** `me.service.ts:90-110` (`deleteMe`) разрешает зависшие платежи и возвращает неразрешённые, **но `invoices` не трогает**: ни `status`, ни признака недействительности. `payments.service.ts` при `successful_payment` находит инвойс по `(payload.u, payload.k)` и не проверяет ни его статус, ни существование пользователя. `pre_checkout` (`resolvePending`) проверяет только формат payload и валюту.
- **Почему блокер:** человек удаляет данные, чтобы уйти, — и платит в пустоту либо получает товар, привязанный к несуществующей карте. Дополнительно: `user_id` детерминирован от `telegram_id` через `PSEUDONYM_PEPPER`, поэтому «удаление» не окончательно по построению — очередной платёж воссоздаёт ту же строку `users`. Для требования «удали мои данные» это противоречие, а не недосмотр.
- **Что закрыло бы:** при `DELETE /me` помечать неоплаченные инвойсы (`cancelled`/`invalidated`); в `successful_payment` и `pre_checkout` отказывать по инвойсу в таком статусе и по отсутствующему пользователю; на отказ — `rejected` + `payment_rejected` + возврат звёзд (в порядке A деньги списаны уже после удаления, значит возврат обязателен).

### QA-18 (не блокер). `Me.latest_report_id` заявлен, но не отдаётся

`CHANGELOG` 1.5.2: «добавлен `Me.latest_report_id`»; в схеме поле есть (`api.openapi.yaml:278`), в
`Me.required` его нет — и в ответе `GET /me` его тоже нет:
```
ключи ответа: user_id,display_name,is_new,has_profile,has_chart,chart_id,
              subscription,entitlements,quotas,onboarding_step
latest_report_id: undefined
```
Схему это формально не нарушает, но обещание не выполнено: клиент не может открыть последний готовый
разбор, не зная его id. **Не блокер** потому, что поле необязательное и разбор доступен по
`POST /reports` + `GET /reports/{id}`.

  ```
  но внутри главы core слово «решения» — 31 раз, 26 % всех слов;

                (рубрика требует «абзацев 3–6, в каждом 2–4 предложения»)
  ```
- **Что проверяет валидатор** (`apps/api/src/modules/reports/validators.ts`): длину (±30 %), формат (H1/таблица/ссылка/HTML/маркер списка), «вы», отсылки к интерфейсу, запрещённые темы, Хирон, дома при `unknown`, пересечение по 8-граммам **с предыдущими главами**, дисклеймер. Абзацев и повторов **внутри** главы нет ни в одной проверке — отсюда `validation: []` при тексте, где четверть слов — одно и то же.
- **Почему не блокер:** это дефект подставного провайдера, а не пользовательского тракта: с настоящей моделью такого текста не будет. Но валидатор обязан ловить это **независимо от модели** — иначе первый же плохой ответ провайдера уйдёт человеку за 149 ⭐. Рубрика п.7 и п.9 написаны именно для этого случая и кодом не покрыты.
- **Цена:** два регулярных выражения и счётчик частот; ловится до вызова судьи, то есть бесплатно.

### Замечание. `refund_issued` так и не пишется, хотя имя в контракте есть

`x-analytics-server-events` содержит три имени. Пишутся два: `payment_rejected` (подтверждено, `props.code` верный) и `subscription_expired`. `refund_issued` в `apps/api/src` не встречается ни разу — при этом `payment_refunded` пишется в БД, хотя этого имени нет ни в одном списке контракта. То есть серверные события и контракт снова разошлись, только в другую сторону. Не блокер (метрики возвратов считаются по `payments`), но `x-analytics-server-events` сейчас неточен в двух местах из трёх.

## 6. Платёж после удаления данных (приоритет №1)

См. §3, QA-15. Воспроизведение одной командой: `node e2e/qa/acceptance-002.mjs delete-then-pay` —
оба порядка в одном прогоне, на PR #20 оба дают доступ.

Соседний сценарий — «удаление при зависшем платеже» — **закрыт и ведёт себя правильно**:
`DELETE /me` сначала пытается разрешить платёж тем же кодом, что вебхук, затем возвращает звёзды,
и только если возврат не удался — `409` с `details.reason="refund_failed"` и контактом поддержки.
Проверено: `dp1` → 204 после разрешения, платёж `rejected`, `telegram_id` обезличен. То есть вход в
эту дыру закрыли, а выход (платёж, пришедший **после** удаления) — нет.

| Требование задания | Факт на PR #20 |
|---|---|
| инвойс инвалидируется | **нет**: после `DELETE /me` инвойс `created`, затем `paid` |
| оплата → автовозврат звёзд | **нет**: `refundStarPayment` = 0 |
| доступ не выдаётся | **нет**: `entitlements report|active`, `/me full_report=true` |
| событие в метриках | **нет**: ни `payment_rejected`, ни `refund_issued` |

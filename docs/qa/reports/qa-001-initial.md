## Блокеры (исправить до прода)

### QA-11. `successful_payment` без выставленного инвойса выдаёт платный доступ. Сумма платежа не сверяется

- **Где:** `apps/api/src/modules/billing/payments.service.ts`, `handleSuccessfulPayment` (строки ~130–200); нет проверки в `BillingRepository`/`invoices`.
- **Шаги (воспроизводится скриптом):**
  1) `node e2e/qa/money.mjs m11` (нужны живой API + стаб Bot API, см. «Доказательства»);
  2) скрипт отправляет в вебхук апдейт `message.successful_payment` с `total_amount: 1`, `invoice_payload = {"p":"year_2990","u":"<свой user_id>","k":"<случайный uuid>"}` и `telegram_payment_charge_id`;
  3) скрипт читает БД и `GET /me`.
- **Ожидалось:** платёж без инвойса от сервера не выдаёт доступ; несовпадение суммы с ценой плана блокирует выдачу (или как минимум ставит её в ручной разбор).
- **Получено:**
  ```
  доставка апдейта: 200 {"ok":true}
  payments:  year_2990|1|processed
  subscriptions: year|active|2027-11-12T08:56:53Z
  invoices (сервер инвойс не выставлял): 0
  /me: plan=year, is_active=true, full_forecast=true, ask_per_day=5, solar_included=true
  лог: {"level":"error","msg":"payment_amount_mismatch","expected":2990,"actual":1}
  ```
  То есть годовая подписка за 1 звезду, по инвойсу, которого сервер не создавал.
- **Почему блокирует:** деньги. Механика ровно как у QA-11 в задании приёмки (M1 «сумма берётся с сервера»): сервер не сверяет ни факт инвойса, ни сумму. Сам по себе вебхук защищён секретом в пути и заголовке (проверено, M2e → 403), но эта защита — единственная, и она общая для всех апдейтов; при её утечке (секрет лежит в `.env`, в конфиге деплоя и в пути URL) последствия — бесплатный доступ к любому плану. Второй, более вероятный вход: баг в клиенте/прокси, из-за которого до вебхука доезжает апдейт чужого бота/тестового окружения.
- **Отдельно:** несовпадение суммы пишется только в лог (`error`), в `GET /admin/metrics` его нет — то есть факт «кто-то заплатил 1 звезду за год» не виден никому, кроме того, кто читает логи. Это уже не деньги, а наблюдаемость (см. «Не блокирует»).
- **Как проверить после фикса:**
  - `node e2e/qa/money.mjs m11` → в БД ноль строк, `/me` без подписки, в вебхуке ответ 200 (Telegram не должен ретраить бесконечно);
  - апдейт с суммой, не равной `PLANS[plan].stars`, доступ не выдаёт;
  - апдейт с `payload.k`, которого нет в `invoices`, доступ не выдаёт;
  - регресс: `node e2e/qa/money.mjs m3` и `m4` по-прежнему дают доступ и сдвигают срок.

### QA-13. Тексты обещают удаление в «Настройки → Удалить мои данные» и автоудаление через 24 месяца — ни того, ни другого нет

- **Где:**
  - тексты: `apps/web/src/i18n/ru.ts:193, 220, 229`, источник — `legal-texts-2026-11-10.md` (экраны согласия, «Политика», «Пользовательское соглашение»);
  - отсутствующий экран: в `apps/web/src/screens/` нет Settings, `DELETE /me` в коде фронта не вызывается вовсе (`grep -rn "deleteMe\|DELETE /me" apps/web/src` → пусто);
  - отсутствующий джоб: `apps/api/src/modules/ops/jobs.service.ts` умеет только `subscriptions_downgrade` и `refund_undelivered`; поиска по `inactiv|retention|24 месяц` в `apps/api`, `packages`, `migrations` нет.
- **Шаги:** 1) открыть экран согласия в собранном фронте; 2) прочитать абзац про удаление; 3) найти в приложении экран «Настройки»; 4) проверить, есть ли джоб автоудаления.
- **Ожидалось:** сам `legal.md:57` формулирует правило: «если в тексте написано „Настройки → Удалить мои данные", этот экран обязан существовать до релиза. Сейчас он появится в итерации с экраном Settings — **до неё продукт не выпускаем**».
- **Получено:** экрана нет, автоудаления нет, текст показывается пользователю как действующий. API при этом удаляет корректно (P4, см. ниже) — то есть пользователь физически не может воспользоваться своим правом из интерфейса.
- **Почему блокирует:** ПДн + доверие + 152-ФЗ. Это не «недоделанная фича», а невыполнимое обещание в юридическом тексте, который пользователь подтверждает галочкой. Авторы сами зафиксировали это как условие блокировки релиза.
- **Как проверить после фикса:** либо экран Settings с рабочей кнопкой (вызывает `DELETE /me`, показывает 409 честно — см. QA-14), либо тексты переписаны и версия согласия поднята (`CONSENT_VERSION` + `legal-texts-<дата>.md`, `tests/legal-texts.test.ts` это поймает). Джоб автоудаления — либо реализован, либо вычеркнут из текста.

### QA-14. `DELETE /me` при незавершённом платеже отвечает 409 «Дождись, пока платёж завершится» — а он уже завершён и ждать нечего (ловушка)

- **Где:** `apps/api/src/modules/me/me.service.ts`, `deleteMe`; `BillingRepository.hasPendingPayments` (тот же запрос); `apps/api/src/i18n/ru.ts` → `CONFLICT`.
- **Шаги:**
  1) `node e2e/qa/money.mjs m6` создаёт платёж `processed=false` старше 11 минут (это ровно то состояние, в котором оказывается пользователь, если обработчик упал после записи платежа);
  2) затем `node e2e/qa/money.mjs m7` (тот же пользователь) → `DELETE /me`.
- **Ожидалось:** либо честный текст («платёж обрабатывается, попробуй через N минут, или напиши в поддержку»), либо автоматическое доведение платежа (возврат) и удаление.
- **Получено:**
  ```
  DELETE /me: 409 {"code":"CONFLICT","message":"Есть незавершённая оплата. Дождись, пока платёж завершится, и повтори."}
  users остался: 1
  ```
  При этом такой платёж не «завершится» никогда сам: джоб его только возвращает (`refundUndelivered`), а условие 409 смотрит на `processed = false AND status = 'paid'` — после возврата (`status='refunded'`) оно снимается, но лишь если крон вообще запущен (см. QA-15/риск R-4). Без крона — вечный 409 и вечное «подожди».
- **Почему блокирует:** ПДн/права субъекта + доверие. Пользователь просит удалить данные, получает отказ с советом ждать — и у него нет ни одного способа это разрешить из интерфейса (см. QA-13).
- **Как проверить после фикса:** пользователь с «зависшим» платежом либо удаляется (платёж обезличивается и уходит в возврат), либо получает текст с конкретным сроком и путём в поддержку; `e2e/qa/money.mjs m7` перестаёт быть тупиком.

## Не блокирует, но починить

1. **QA-12. Контракт в репозитории — 1.4.0, а не 1.5.0.** `head -5 api.openapi.yaml` → `version: 1.4.0`; упоминаний `1.5.0` в `api.openapi.yaml`, `packages/shared/src/contracts/generated.ts`, `apps/web/src/api/schema.gen.d.ts` нет (`grep -rn "1\.5\.0"` → только `pnpm-lock.yaml`). Оба заявления задания, которые «надо проверить фактически» через 1.5.0, проверены по факту кода:
   - `Me.entitlements` и `Me.chart_id` API отдаёт всегда (проверено валидацией по схеме, C2 — OK);
   - `validation_failed_client` в контракте и на сервере **отсутствует** (E4 ниже) — противоречие «фронт не отправляет / в контракте есть» разрешается так: **ни в контракте, ни на сервере**, фронт держит событие в очереди и не шлёт. То есть в воронке этого события не будет никогда.
2. **QA-12b. `Problem.request_id = "no-request-context"` при битом JSON.** `curl -X POST -d '{oops'` → `422` с `request_id: "no-request-context"` и **без заголовка `X-Request-Id` в ответе**; переданный клиентом `X-Request-Id: qa-bad-json` тоже теряется. Причина: body-parser падает до `RequestIdMiddleware`. Контракт (C5) обещает request_id для поиска в логах — здесь его нет, поддержка запрос не найдёт. Ожидание: 4xx в едином формате с настоящим `request_id`.
3. **QA-8. 422 приходит в формате, отличном от объявленного.** У `POST /billing/invoice` с `plan_code: "free_0"`:
   `"details": {"fields": [{"path":"plan_code","code":"invalid_enum_value"}]}` — вместо `details.field_errors[{field,message}]` (`billing.dto.ts`, `parseInvoiceRequest`). Контракт 1.2.1 прямо обещает `field_errors`, и фронт ищет именно его (`fieldErrorsOf`) → на этот 422 поле не подсветится, пользователь увидит общий текст.
4. **QA-11b (наблюдаемость денег).** `payment_amount_mismatch`, `payment_payload_invalid`, `payment_unknown_plan` пишутся только в лог. В `GET /admin/metrics` их нет, алертов нет. Добавить счётчик в метрики и в `events` — иначе первый сигнал о QA-11 придёт от пользователя.
5. **QA-2b. Текст отказа `pre_checkout_query` на «вы»:** `"Товар недоступен, попробуйте ещё раз"` (`payments.service.ts`). Правило контракта 1.2.1 — все тексты на «ты». Мелочь, но это единственный текст Bot API, который пользователь видит в момент оплаты.
6. **QA-6. Узкое место гео на конверсии.** 149 городов хватает на миллионники, но не на малые города (см. G6 в доказательствах: 12/20). При этом фолбэк `GEO_PROVIDER=nominatim` в `.env.example` описан, а в `.env` по умолчанию `bundled`. Из 8 промахов 4 — реальные российские города (Геленджик, Суздаль, Урюпинск, Кировск). В отчёте — как риск, не как баг.
7. **QA-вне-списка: `POST /reports` объявлен в контракте, но не реализован.** `POST /api/v1/reports` описан в `api.openapi.yaml:918` (202 + `report_id`), а сервер отвечает `404 NOT_FOUND`. По условиям приёмки LLM-конвейер не тестируется, поэтому это не блокер, но формально это расхождение кода со схемой (C1): контракт обещает эндпоинт, которого нет. Либо эндпоинт появляется вместе с поколением разбора, либо он помечен как недоступный в контракте. Пока контракт 1.4.0 его описывает, фронт может на него рассчитывать — и получит 404.
8. **QA-вне-списка: неизвестные маршруты без `initData` отвечают 401, а не 404.** `GET /api/v1/nope` без заголовка → `401 UNAUTHORIZED`, с заголовком → `404`. Это следствие правила A4 (auth-middleware раньше роутера) и не дефект: атакующий не узнаёт, какие маршруты существуют. Отмечаю, чтобы не переоткрывали.

## Риски и наблюдения

- **R-1. Продление зависит от `subscription_expiration_date` от Telegram.** M4: 2026-12-12 → 2027-01-11 ровно как заявлено. Но если Telegram не пришлёт поле (апдейт старого формата/ручное переигрывание), код берёт `now() + period` — то есть **срок назад не сдвигается** (`upsertSubscription`), но и не продлевается вперёд от текущего `expires_at`: на третьей оплате без поля срок остался `2027-01-11`, хотя пользователь заплатил ещё за месяц. Это потерянный оплаченный период. Проверено: `e2e/qa/money.mjs m4`, третий шаг.
- **R-2. Bot API — стаб.** Реальное списание звёзд, реальный `refundStarPayment`, реальные `subscription_expiration_date` при автопродлении не проверены никем и не могут быть проверены в песочнице. Проверить вручную в тестовом боте (см. «Что не проверено»).
- **R-3. Мини-апп не зарегистрирован у бота.** `startapp=chart_<id>` и `openInvoice` в живом Telegram не проверены. Серверная часть `GET /charts/current` для этого готова (проверено), клиентская — нет (экранов пейволла нет).
- **R-4. Джоб ничего не запускает сам.** `POST /internal/jobs/run` без секрета → 403 (J1, верно), с секретом → 202 (верно). Но в репозитории нет крона, а без него: подписки не помечаются `expired`, автовозвраты не делаются, «подписка закончилась» не отправляется. Доступ при этом деградирует сам (проверено M5: `entitlements` становятся бесплатными по `expires_at > now()`), поэтому риск — не «бесплатный доступ», а «деньги за недоставленный товар не вернулись» и «пользователь не узнал, что подписка кончилась».
- **R-5. `churn_30d` — это доля отписок среди всех подписок, а не когортный churn.** `admin-metrics.service.ts`: `count(status in ('expired','cancelled') AND updated_at >= now()-30d) / count(*)`. Читать так: «сколько процентов всех когда-либо созданных подписок отвалилось за 30 дней». Подписка, живущая 35 дней, в знаменателе остаётся навсегда, а в числителе учитывается только один раз — метрика будет занижаться по мере роста базы. Для решений по деньгам не годится, годится как «примерно». В отчёте фиксирую: не путать с retention.
- **R-6. Лимиты запросов — в памяти процесса.** `rate-limit.middleware.ts` честно это признаёт (Redis в песочнице нет). При нескольких подах лимит умножается на число подов, при рестарте сбрасывается. Для `POST /billing/invoice` это антифрод-дыра (см. QA-10 ниже — лимит вообще не считает то, что обещано).
- **R-7. Swiss Ephemeris / Хирон.** В fallback-режиме Хирон не считается, и это **видно наружу**: `chart.omitted_planets = ["chiron"]`, контракт это описывает. В текстах пользователя Хирона нет (проверено: `i18n/ru.ts`, экраны). Замечание: легаси-дубликат движка `astro/engine.py` (корень репозитория, файл под git) содержит `"Chiron": (swe.CHIRON, "Хирон", "⚷")` и не совпадает с `packages/astro/astro/engine.py` — новичок-разработчик может запустить не тот движок. Держать в отчёте как технический долг.
- **R-8. `/health` различает `db: ok/down` и `llm: ok/down/unknown`, но не различает причину `astro: down`.** Проверено: сайдкар остановлен → `503 INTERNAL` на `/charts` за 9 мс, `/health` → `degraded`, `/me` продолжает работать. Это хорошо; в `502`/`503` нет подсказки «движок», только общий текст — для дежурного смотри `astro` в `/health`.
- **R-9. Заявленные числа тестов сходятся точно.** `pnpm -r test`: api **127**, web **326**, ui **24**, shared **8**; `pytest` **49** (проверено на реальном venv с `pyswisseph 2.10.3.2`). `pnpm lint` и `pnpm typecheck` проходят. Это ровно то, что заявляли авторы (сумма 534 JS + 49 Python = 583; в задании названо «546 зелёных» — расхождение в самой формулировке задания, а не в коде).
- **R-10. Три места, где авторы сами признали неполноту (проверено фактически):**
  - `wheel_png_url` и `Me.entitlements` — API отдаёт всегда (C2 OK, валидация по схеме);
  - `churn_30d` — см. R-5;
  - `jobs/run` без крона — см. R-4.

## Приложение 2: проверки, которые прошли, но их стоит зафиксировать как «сделано правильно»

Чтобы не переделывать при следующей приёмке:

- **A2**: подмена `user.id` в `initData` без пересчёта подписи → 401 (подпись считается по всей строке, `data_check_string` собирается из всех пар).
- **A5**: чужая карта → **404**, а не 403 — как требует задание (не подтверждает существование чужого id).
- **A6/A7**: колесо отдаётся только по подписи; без `sig`, с битым `sig`, с истёкшим — 403 (сравнение `timingSafeEqual`).
- **M3**: транзакция + `SELECT ... FOR UPDATE` по `telegram_payment_charge_id` + `ON CONFLICT DO NOTHING` — дубль действительно не создаёт ни второй строки `payments`, ни второго `entitlements`; `sendMessage` тоже один.
- **M6**: возврат идемпотентен (`refunds_attempted:1` → `0`), отзывает доступ (`full_report: true → false`), повторный вызов `PaymentsService.refund()` возвращает `false`.
- **J2**: «подписка закончилась» отправляется **один раз** (второй запуск джоба — ноль сообщений), отметка живёт в `events` и ограничена 30 днями.
- **P1**: в 133 строках лога за весь прогон (включая платежи, карты, события, гео, ошибки) нет ни даты рождения, ни времени, ни координат, ни города, ни `telegram_id`. Единственный идентификатор — `user_id` (псевдонимный UUID) и `chart_id`.
- **P4**: удаление действительно каскадное (`users/profiles/charts/asks/forecasts/reports/quotas` = 0), платежи обезличиваются (`telegram_id = NULL`, `anonymized_at`), а `invoices.payload` содержит только псевдонимный UUID — ПДн там нет.
- **P8**: карта по `startapp=chart_<id>` не может открыть чужую карту: клиент читает `GET /charts/current` своей сессии.
- **K2**: идемпотентность `POST /charts` на уровне БД (`unique (user_id, input_hash)` + `xmax = 0`), а не «на глаз».
- **K8**: размер PNG 1600 — ровно 326 641 Б, как заявляли авторы.
- **G4**: `limit: 0` → 422, без молчаливой обрезки.
- **E3**: батч из 3 событий с `last_name` → `202 {accepted: 2}` — как заявляли.
- **U11 (код)**: ссылка `t.me/<bot>?startapp=chart_<id>` собирается только при валидном `BOT_USERNAME` и валидном `startapp`; без него уходит картинка и текст.
- **U13**: бандл 95.4 kB gzip при бюджете 350; в `dist` нет `VITE_DEV_INIT_DATA`/`API_MOCK`; проверка встроена в `build` (`check-bundle.mjs`), а не отдельным скриптом «на память».
- **J5**: `/health` честно различает `db`, `llm` и `astro`; при мёртвом сайдкаре API отвечает 503 за 9 мс, а не висит.
- **Контракт C1/C2**: ответы `ChartResponse`, `Me`, `Invoice`, `SubscriptionState` проходят валидацию по 1.4.0 без единого поля вне схемы.

## Приложение 3: что я изменил в репозитории

Только QA-артефакты (AGENTS.md §0), прод-код не тронут:

- `scripts/qa/init-data.mjs` — подпись `initData` по алгоритму Telegram (воспроизводимость A1–A3, M*, P*);

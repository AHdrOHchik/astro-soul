# QA-14: витрина тарифов как данные сервера (`GET /billing/plans`)

Контракт **1.5.9**. Проверялось на живом стенде: Postgres 5432 (БД
`astro_qa14`), астро-движок 8001, API 8084 с выключенным `PAYMENTS_TEST_PLANS`,
API 8085 с включённым, стаб Bot API 8091.

## Что проверено на стенде (`e2e/qa/iteration-13.mjs`, 93 проверки, 12 сценариев)

| Сценарий | Факт |
|---|---|
| `plans` (флаг выключен) | `200`, ровно шесть тарифов каталога в порядке пейволла; `test: false` у всех; в сыром ответе нет ни `test_1`, ни `test_report_1`; `Cache-Control: no-store`; `one_149` — `one_off`, 149 ⭐, `period_sec: null`; `month_399` — `period_sec: 2592000` |
| `plans` (флаг включён) | `200`, восемь тарифов: шесть каталога без изменений + `test_1`, `test_report_1` в конце, оба `stars: 1`, `test: true`; у тест-разбора `period_sec: null`, у тест-подписки `604800`; `title`/`subtitle`/`includes` непустые |
| `plans` (метрики) | `test_plans_active: true` на 8085 и `false` на 8084 — одним и тем же запросом, без платежей |
| `on`, `pay`, `wrong-amount`, `refund` | прежние сценарии тестовой подписки не изменились |
| `report-off`, `report-on`, `report-pay`, `report-refund` | прежние сценарии тестового разбора не изменились; проверка «в витрине стенда `test_1` есть и помечен `test: true`» заменила прежнюю «в выдаче планов `test_1` нет» (маршрута не было) |
| `prod-guard` | `check.sh --prod` по-прежнему валит запуск с флагом и называет оба тарифа |

Два прогона подряд — одинаковый результат, `ВЫВОД: закрыто.`

## Что проверено тестами (`apps/api/test/billing-plans.spec.ts`, 9 тестов)

- флаг выключен: шесть тарифов каталога, `test: false`, тестовых нет **ни
  планом, ни подстрокой** в сыром JSON, `no-store`, `401` без initData;
- флаг включён: восемь тарифов, тестовые в конце с `test: true`, каталог не
  сдвинулся; `POST /billing/invoice` по коду, который прислала витрина,
  создаёт счёт за 1 ⭐ и без `subscription_period`;
- `test_plans_active` — `false`/`true` в двух контекстах приложения.

## Почему так, а не иначе

- **Тексты на сервере.** Название и подзаголовок приходят в ответе, а не
  берутся клиентом из `ru.ts`: пока их знал клиент, смена названия или состава
  требовала релиза клиента. Формулировки подписок совпадают с согласованными
  владельцем — обещанное названо «появится в ближайшие дни» и там, и там; на
  фронте этот текст станет мёртвым после перехода на витрину.
- **`includes[]` — из прав плана**, а не из текста рядом: в списке только то,
  что сервер действительно выдаёт по этому тарифу.
- **`PlanCode` не расширен.** `test_1`/`test_report_1` приходят как
  `OrderablePlanCode` (строка) в витрине и на денежных путях. Перечисление,
  зависящее от переменной окружения, — не перечисление.
- **`no-store`** — не косметика: кэш пережил бы и включение флага (тестовых не
  видно), и выключение (тестовые видны всем).

## Что не проверено

1. `docker compose up` — Docker в песочнице нет; проброс флага в контейнер
   проверен статически (`apps/api/test/test-plan-plumbing.spec.ts`).
2. Реальный клиент Telegram — оплата и возврат шли через стаб Bot API.
3. Экран пейволла: фронт ещё рисует список из `apps/web/src/lib/plans.ts`,
   поэтому включённый флаг меняет ответ API, но не вид кнопок. Задание фронту
   выполнимо по этому контракту: `GET /billing/plans` → отрисовать `plans[]`,
   `test: true` — отдельным блоком ниже, клиент про флаг не знает.

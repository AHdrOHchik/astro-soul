## LLM

### 2.2 `chart_facts` v1.2 — символы подтверждены, токены не измерены

Независимый замер тем же сериализатором на `test/fixtures/measure-chart.json`:
полный блок **1 247 знаков**, `serializeTopFactors` **464 знака** = **37,2 %** — заявлению соответствует
`docs/qa/reports/chart-facts-v1.2.md` дословно. Тест `chart-facts-budget.spec.ts` (3 кейса) проходит.

**Но это символы.** В самом документе сказано: «Считаются символы; токены **оценены** по 2,8
символа/токен» — и там же: «`usage.prompt_tokens` из реального ответа **не снят**». Мой замер даёт по
тому же коэффициенту **445 → 166** токенов — цифра, которой в задании не было, и она тоже оценка.
Фактических токенов снять нельзя: подставной провайдер (`fake-llm.ts:143`) возвращает
`tokensPerCall ?? 1 000` и делит их 80/20 **независимо от промпта** — в БД `llm_tokens_in = 800` у всех
вызовов. То есть проверка «эффект в токенах» на этом стенде **невыполнима, и это надо сказать прямо**,
а не засчитывать символы за токены. Измерение остаётся за владельцем с `GIGACHAT_AUTH_KEY`.

Качество отбора: в `core` уходят Солнце, Луна, Асцендент и MC, три сильнейших мажорных аспекта
**по орбу**, управитель Асцендента с домом, баланс стихий и крестов. Три главных фактора не теряются.
`rubric_v1.2` на трёх главах не прогонялась (нет живой модели) — подставной провайдер возвращает
фиксированный текст, `reports.validation` пуст.

### 2.3 `based_on` — чисто

`filterBasedOn` оставляет только метки из `chartFactLabels`. Подал 10 позиций, включая `h10`,
`sun|Тельец`, `planet:mars`, «Венера в Раке, 4-й дом» (выдуманный дом), «дом 7», «Сатурн в Рыбах» —

### 2.4 Тизер `core` без терминов — **не реализовано** (находка 1)

Пункт 7 рубрики `rubric_v1.2` записан как требование (`rubric.md:104`): «первые 400 знаков `core`
не содержат астрологических терминов». В коде **валидатора этого нет**. `validateSection` проверяет
объём, формат, «вы», интерфейсные отсылки, запрещённые темы, Хирона, дома при неизвестном времени,
повторы, дисклеймер, абзацы — **но не термины в первых 400 знаках**.

Прогон: глава из 5 абзацев, первый абзац — «Твоё Солнце в Тельце в десятом доме, а Луна в Льве даёт
трин к Узлу: стихия земли усилена крестом. Асцендент в Деве добавляет осторожности». Результат
`validateSection` — **0 провалов, 0 предупреждений**. Та же глава без терминов — тоже 0 провалов.
Разницы между «брак, о котором введён п.7» и «норма» валидатор не видит.

Тизер на стенде (подставной провайдер) терминов не содержит — но это свойство фиксированного текста
`fake-llm`, а не защиты. Регулярка по русским названиям планет, знаков и `дом|аспект|квадрат|трин|
стихия|крест` на реальном тизере чиста; глазами — тоже (в тексте `fake-llm` вообще нет астрологии).
**Ловить «в десятом» без слова «дом» нечем: такой проверки нет.**

### 2.5 Прогноз «про человека» — **подойдёт другому** (находка 2)

`runNightly` собирает `serializeChartFacts(chart)` и передаёт в `forecastPrompt` только `date`.
Эндпоинт транзитов в сайдкаре есть (`POST /transits`, `transitsFor`), клиент в API тоже
(`astro.client.ts:70`), но **никто его не вызывает** — `grep '\.transits('` по `apps/api/src` пуст.

Прямая проверка: `forecastPrompt` на **12 ноября 2026** и на **30 июня 2027** различается **одной
строкой из 24** — `Местная дата: …`. Всё остальное, включая факты карты, идентично. Двум людям с
одинаковой картой (или одному человеку в разные дни) уходит промпт, отличающийся только датой.

Небесная механика на этот день в промпт не попадает вообще — значит прогноз физически не может быть
«про этот день»: модель сочиняет его из натальной карты и числа. Ответ на вопрос задания
«подойдёт ли другому человеку с той же картой» — **да, подойдёт**.

### Расход LLM не виден владельцу (находка 4)

## Находки

**[важное] 1. Пункт 7 рубрики `rubric_v1.2` не проверяется кодом — тизер с терминами проходит.**

Глава, начинающаяся «Солнце в Тельце в десятом доме… трин… стихия… крест», проходит
`validateSection` с 0 провалов. Рубрика требует «нет» по п.7 → перегенерация; код не даёт даже
предупреждения. Пункт введён именно потому, что «тизер начинался перечислением планет и домов,
формально проходя все остальные проверки», — то есть защита от известного брака не работает.
Нужен валидатор на `teaser = body.slice(0, 400)` для `core` (названия планет, знаков, домов, аспектов,
стихий, крестов + конструкции «в десятом», «в 10-м» без слова «дом»), с провалом по п.7 и
перегенерацией, а не предупреждением.

**[важное] 2. Прогноз на день не использует день: транзиты не считаются.**

`POST /transits` в сайдкаре есть и работает, но API его не вызывает. Промпт на 12 ноября и на
30 июня различается только строкой даты. Прогноз подойдёт другому человеку с той же картой —
это ответ на вопрос §2.5 и одновременно объяснение, почему прогноз «общий». Нужно либо считать
транзиты и класть их в промпт (и тогда `serializeTopFactors` для прогноза дополнить транзитными
аспектами), либо честно переименовать продукт: сейчас это не прогноз на день.

**[важное] 3. Эффект `chart_facts v1.2` не измерен в токенах — только в символах.**

1 247 → 464 знака (37,2 %) воспроизведено независимо. Токены нигде не сняты: в документе они
**оценены** коэффициентом 2,8 симв./токен, фактических `input_tokens` нет, а подставной провайдер
отдаёт фиксированные 800 входа независимо от промпта. Засчитывать «1 247 → 464» за токены нельзя.
Плюс арифметика из самого документа: даже при нулевом блоке фактов вход главы остаётся 74 % прежнего —
цель −35 % по главе недостижима без правки `prompts.ts`, и это решение владельца, а не «заодно».

**[важное] 4. Расход на прогнозы и вопросы не виден в `llm_cost_rub_30d`.**

Метрика считается только по `reports`. Прогноз генерируется ежедневно каждому активному
пользователю — основной расход мимо счётчика. Проверено: +12,5 ₽ в `forecasts.llm_cost_rub`
метрику не меняют. Нужно сложить три таблицы (как уже сделано во внутреннем месячном лимите).

**[мелкое] 5. `client-access-audit.mjs` устарел и выдаёт «проверено» за непроверенное.**

Из 4 «разобранных» мест 2 скрипт больше не находит (`ПЕРЕЕХАЛО` — ожидаемые строки не совпадают
с текущим кодом `App.tsx` / `plans.ts`) и честно печатает «проверить вручную заново», но итоговая
строка всё равно «все 4 разобраны, включения нет: true». Руками проверил: клиент решения о доступе
не принимает — `grants()` только подтверждает то, что сказал сервер (`entitlements` из `GET /me`),
`isChartThere` спрашивает сервер. Вердикт верный, инструмент — нет: нужны актуальные якоря или
провал при несовпадении.

**[мелкое] 6. `/admin/payments/search` из задания отсутствует.**

Искать платёж «по дате, сумме и хвосту `charge_id`» можно только SQL-запросом. Для владельца это
означает, что возврат после удаления делает поддержка вручную по базе. Пока `refundStarPayment`
вызывается автоматически при `invoice_invalidated`, это не блокер, но обещанного в задании
инструмента нет.

## ЧТО ДОЛЖНО БЫТЬ ВЕРНО ПЕРЕД ПУБЛИКАЦИЕЙ БОТА

Пять пунктов, проверенных на этом стенде, — и требования к среде для двух агентов, которые
пойдут после (локальный запуск с настоящим Telegram и VPS).

1. **Удаление данных не оставляет ничего, кроме обезличенного платежа.** `DELETE /me` → 204,
   `users`, `profiles`, `charts`, `quotas`, `entitlements`, `reports` по нулю, платёж с
   `user_id = NULL`. Проверено по каждой таблице.
2. **Автопродление отменяется всегда, когда `user_id` ещё жив, и доводится до конца.** Вызов
   `editUserStarSubscription` ровно один раз с `user_id` и **последним** `charge_id`; при 500 —
   `failed` + событие + метрика, ночной джоб добивает до `cancelled`; без подписки — ноль вызовов.
3. **Оплата без товара возвращает звёзды сама.** Оплата после удаления → `rejected` /
   `invoice_invalidated` + `refundStarPayment` с полным `charge_id`, без участия поддержки.
4. **ПДн нет ни в логах, ни в событиях, ни в промптах.** В логе — только хвост `charge_id`;
   в `events.props` — только суммы и флаги; в промпт не уходят место, координаты, имя, `telegram_id`;
   текст вопроса не хранится.
5. **Клиент не решает о платном доступе и не показывает платного текста до оплаты.** 773 фронт-теста
   зелёные, `paywall.qa` проверяет отсутствие платного текста в DOM, цена — из `shared`.

**Требования к среде для следующих агентов.** Локально с настоящим Telegram: реальный
`TELEGRAM_BOT_TOKEN` и `TELEGRAM_API_BASE_URL=https://api.telegram.org` (или переменная не задана —
дефолт тот же). Это первое, что надо проверить `printenv` **внутри процесса**: если там остался
адрес стаба, бот «работает», но ни одно сообщение не уходит человеку, и приёмка врёт.
`GIGACHAT_AUTH_KEY` обязателен, без него `llm_fake_provider` и **никакие токены не измеряются**;
`CONSENT_VERSION` должен совпадать с `legal.md`, иначе все `POST /charts` дают 422; для проверки
прогнозов и пушей держать карту в поясе, где сейчас 03:00 / 08:00, либо вызывать джоб с явным `at`.
На VPS: `PAYMENT_REFUND_WINDOW_DAYS` — **константа в коде**, не переменная (не искать её в env);
проверить, что 20 миграций применены и `legal.md` один; `TELEGRAM_API_BASE_URL` не задавать вовсе,
чтобы дефолт `https://api.telegram.org` взялся сам; перед публикацией прогнать джоб `pdn_retention_cleanup`
один раз вручную и убедиться, что `subscriptions_cancelled_pending_telegram` = 0.

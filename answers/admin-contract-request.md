# Запрос на контракт: серверная часть админ-панели

Готовый текст для раздела PR «Вопросы к контракту» (по решению владельца — сюда,
а не в issue). Формат полей — «что нужно / зачем / ожидаемая форма / дедлайн»:
так запрос к контракту оформляется вообще; здесь он ещё и помечен как вопрос,
потому что ответ меняет форму экранов. Контракт в этом PR **не изменён**: `api.openapi.yaml` остаётся на
1.6.14, панель написана под то, что в нём уже есть, и ничего не додумывает —
ни одного выдуманного поля на экранах нет, а где маршрута нет, экран говорит
«недоступно» и не рисует данные.

Версия контракта, под которую собрана панель: **1.6.14**.

## 1. Сессия админа (блокирует всё остальное)

**Что нужно.** Три маршрута: `POST /api/v1/admin/auth/telegram`,
`GET /api/v1/admin/me`, `POST /api/v1/admin/auth/logout`.

**Зачем.** Сегодня у панели нет способа узнать, кто перед ней, и она не может
поставить `X-Admin-CSRF`. Без них ни один `/admin/*` запрос из браузера не
работает: экран входа честно показывает «Вход недоступен: сервер ещё не
принимает сессии».

**Ожидаемая форма.**

```
POST /api/v1/admin/auth/telegram
  body: { id, first_name?, username?, auth_date, hash }   # как их отдаёт Telegram Login Widget
  200:  Set-Cookie: __Host-admin_session=…; HttpOnly; SameSite=Lax; Secure; Max-Age=43200
        { "ok": true }
  403:  Problem { code: "FORBIDDEN", … }        # tg_id не в ADMIN_TG_ID
  401:  Problem { code: "UNAUTHORIZED", … }     # подпись HMAC не сошлась

GET /api/v1/admin/me
  200: { tg_id: string, name: string, expires_at: ISO8601, csrf_token: string }

POST /api/v1/admin/auth/logout → 200 { "ok": true } + снятие cookie (Max-Age=0)
```

Три вопроса, на которые нужен ответ в контракте, а не в коде панели:

1. `csrf_token` — в теле `GET /admin/me` (так панель и читает), отдельным
   маршрутом, или двойной cookie? Панель берёт токен из тела и хранит только в
   памяти; если выбор в пользу отдельного маршрута — скажите, форма у него
   будет та же.
2. Срок сессии: 12 часов, продления молча нет. Нужен ли в ответе `expires_at`,
   чтобы панель показывала обратный отсчёт, — или она не должна об этом знать?
3. Отзыв сессии: достаточно `Max-Age=0` или нужен серверный список
   отозванных идентификаторов (и тогда — как панель узнаёт, что её разлогинили,
   кроме как по 401)?

**Что делает панель сейчас.** Типы `AdminMe` и `TelegramAuthPayload` в
`apps/admin/src/api/types.ts` помечены как «НЕ В КОНТРАКТЕ» и существуют только
для dev-мокера; гейт `http.assertCallable` не выпускает запрос на путь, которого
нет в `paths:`. Как только маршруты появятся, тест
`src/api/routes.contract.test.ts` перестанет их считать недостающими, и эти два
типа надо удалить, заменив выведенными из `paths`.

**Дедлайн.** Блокирующий: без него итерация 1 не проверяется на живом стенде.

## 2. Аудит действий

**Что нужно.** `GET /api/v1/admin/audit?entity=&entity_id=&limit=&cursor=`.

**Зачем.** Правило панели: каждая мутация обязана показывать, кто и когда
менял значение последний раз. Записи пишет сервер — читать их панель может
только по именованному маршруту. Сейчас в реестре `routes.ts` у колонок
«кто менял» стоит «нет маршрута», и на экране это видно.

**Ожидаемая форма.**

```
200: { items: [{ id, at, actor_tg_id, actor_name, action, entity, entity_id,
                before: object|null, after: object|null, request_id }],
       next_cursor: string|null }
```

`before`/`after` — только изменённые поля, без снимков записи целиком.
Вопрос: `actor_name` берётся из `users` или из снимка, записанного в момент
действия (имя человека меняется, аудит — нет; панель за вторым и придёт).

**Дедлайн.** Нужен до того, как экран «Тарифы» начнут трогать руками: менять
цену без видимой истории last-changed — тот случай, где панель обязана
остановить человека, а не объяснить.

## 3. Поддержка: человек, возврат звёзд, откат разбора, debug push

**Что нужно.**

| Маршрут | Зачем |
| --- | --- |
| `GET /api/v1/admin/users?telegram_id=&alias=&q=` | найти человека; ровно один из трёх параметров, иначе 422 |
| `GET /api/v1/admin/users/{id}` | карточка: доступ, платежи, статус подписки, дата рождения — на одного человека |
| `POST /api/v1/admin/users/{id}/refund` | возврат звёзд; сумма считается на сервере |
| `POST /api/v1/admin/users/{id}/push` | одна тестовая отправка: «почему пуш не пришёл» |
| `GET /api/v1/admin/reports?user_id=&status=&limit=&cursor=` | топ-5 провалов генераций на Обзоре |
| `POST /api/v1/admin/reports/{id}/regenerate` | откатить один разбор |

**Зачем.** Это и есть «работать без разработчика»: сейчас владелец просит
разработчика сделать `SELECT` и ручную выдачу.

**Ожидаемая форма — три вещи, которые панель не имеет права угадывать**
(ответы владельца — в `answers/admin-pr1-review.md`).

1. `refund`: request `{ reason: string }` (обязательный текст основания),
   response `{ charge_id, amount_stars, currency, status }`. Сумма — только с
   сервера; панель вводит её как **подтверждение** (человек повторяет цифру,
   которую вернул сервер), но сама не считает и не хранит.
2. `users/{id}`: дата рождения и время рождения отдаются **только** этим
   маршрутом и только по явному запросу поддержки; список `users` не
   должен уметь их вернуть ни одним фильтром. Запрос карточки с ПДн обязан
   оставить запись в аудите (§2) — это решение сервера, не панели.
3. `regenerate`: response `202 { report_id, state: "queued" }` — не 200 с
   готовым текстом: панель показывает состояние очереди, а не притворяется,
   что разбор уже переписан.

**Дедлайн.** Итерация 2 панели. До этого экраны остаются заглушками — это
нормально, но именно они причина, по которой владелец всё ещё зовёт
разработчика.

## 4. Цены: изменение и история

**Что нужно.** `GET /api/v1/admin/plans`, `PATCH /api/v1/admin/plans/{code}`,
`GET /api/v1/admin/plans/{code}/history`.

**Зачем.** Цена живёт в таблице `plans` (итерация 23), и панель не может ни
показать её, ни изменить через существующие маршруты. Всё, что есть —
`plans:set-price` как CLI-скрипт, то есть разработчик.

**Ожидаемая форма.**

```
GET  /api/v1/admin/plans → { items: [Plan] }     # Plan: code, title, stars_price,
       is_active, is_test, period_days, founder_only — цены только здесь
PATCH /api/v1/admin/plans/{code} body { stars_price: int>0, comment: string }
      → 200 { plan: Plan, effective_from: ISO8601 }
      409 Problem { code: "CONFLICT", details: { reason: "price_changed", current: int } }
GET  /api/v1/admin/plans/{code}/history → { items: [{ at, actor_tg_id, from_stars, to_stars, comment }] }
```

Три вопроса:

1. Смена цены касается новых покупок или и активных подписок тоже? Панель
   обязана написать это на экране подтверждения дословно, по ответу сервера
   (`effective_from`), а не по своей догадке.
2. Нужен ли `comment` обязательным (у нас — да: подтверждение второго шага
   вводит сумму, и «почему» должно оставаться в истории).
3. `409 price_changed` — чтобы панель не писала поверх значения, которое
   кто-то поменял полминуты назад. Согласны?

**Дедлайн.** Итерация 2. В итерации 1 экран «Тарифы» — заглушка: ни кодов, ни
цен он не показывает. Коды планов панель взять неоткуда, кроме контракта
(`PlanCode` в `components['schemas']`), а цены не хранит вовсе: они живут в
таблице `plans` и придут только с `GET /admin/plans`.

## Что нужно от владельца контракта

1. Ответ по §1 (форма CSRF, `expires_at`, отзыв сессии) — он определяет, как
   выглядит экран входа в прод-сборке.
2. Подтверждение, что `GET /admin/grants` и `POST /admin/grants` останутся
   такими, какие они в 1.6.14: на них стоит единственный рабочий экран панели,
   и менять их форму потом — значит менять проверенный код.
3. Срок: §1 до следующей итерации, §2–§5 — единым списком в бэклог, чтобы
   панель не начинала рисовать «полуэкраны» на половину маршрута.

# Changelog

## Итерация 35 — возможность шаринга в `GET /me` (контракт 1.6.10)

Одно аддитивное поле. Проблема была в порядке событий: `share_url` приходит
только в ответе `POST /share/card`, поэтому клиент узнавал, что ссылки нет,
**создав карточку** — первый тап «Поделиться» ничего не открывал, а кнопка
исчезала после ошибки. Плюс `getMe().supports_inline_queries` сервер знал, но
клиенту не отдавал, и клиент гадал по наличию метода в SDK.

- **`Me.share`** (`ShareCapability`): `{link: boolean, inline: "on" | "off" |
  "unknown"}`.
  - `link` — тот же признак, что делает `ShareCard.share_url` не-`null` (имя
    бота в `BOT_USERNAME`). `false` → клиент не рисует кнопку шаринга и не
    зовёт `POST /share/card`: карточку некуда отправить.
  - `inline` — последнее известное `getMe().supports_inline_queries`. `on` →
    клиент предпочитает `switchInlineQuery`; `off` и `unknown` →
    `openTelegramLink(share_url)`. `unknown` — не «выключено»: проверки не было
    или Bot API не ответил.
- **Состояние inline живёт в процессе, а не в кэше.** `TelegramInlineService`
  запоминает результат `checkMode` на время жизни приложения: `/setinline`
  меняет ответ Bot API в любой момент, и следующий старт API его подхватит.
  Кэшировать дольше сессии нельзя — это записано в описании схемы.
- **Отдельного маршрута `/share/capabilities` нет** намеренно: `GET /me` уже
  вызывается на старте, второй запрос только добавил бы точку отказа.
- **`required` не тронут** (ни `Me.share`, ни его поля): первый шаг аддитивный,
  старые клиенты поле игнорируют и работают как раньше.
- **Тесты:** API 54 файла / 652 (было 53 / 644), новый `me-share.spec.ts` (8):
  `link: true` и `false` (пустой `BOT_USERNAME`), `inline` после `checkMode` —
  `on` и `off`, `unknown` до проверки, недоступный Bot API не стирает последнее
  известное состояние, согласованность `link` ⇔ `share_url`, остальные части
  `Me` не сдвинулись.

### Расхождения с заданием (и почему)

1. **`share` не в `required`** — так и в задании («required не обязателен на
   первом шаге»); фиксирую здесь, чтобы это не забылось при следующем бампе.
2. **`inline` при недоступном Bot API остаётся прежним.** Задание говорит
   «последнее известное состояние», поэтому упавшая проверка не сбрасывает
   `on`/`off` в `unknown` — иначе один сетевой сбой на старте выглядел бы как
   «режим выключили». `unknown` отдаётся только когда проверки не было вовсе.

## Итерация 34 — события шеринга разведены (контракт 1.6.9)

Одна цель: метрика «поделились» должна считать отправки, а не создания
карточек. В 1.6.8 имя `share_sent` означало «карточка сгенерирована и
закэширована», а клиенту это имя было недоступно (серверное событие, `422` на
попытку). Метрика считала генерации и называлась отправками.

- **Серверное событие переименовано:** `share_sent` → **`share_card_created`**.
  Смысл — «мы отдали картинку»: `POST /share/card` отдал файл. Свойства
  технические: `kind`, `bytes`, `cached`, а `build_ms` — только когда карточку
  действительно рисовали (у кэш-попадания времени сборки нет, и писать туда
  `0` значило бы врать в метрике «сколько собирается»). Ни получателя, ни
  текста карточки в событии нет.
- **Новое клиентское событие `share_sent`** (`x-analytics-events`, теперь 38
  имён): `props` закрыты — `{kind: day | wheel | insight, channel: inline |
  link}` (`x-event-strict-props`). Человек нажал «Поделиться» и карточка ушла в
  чат: это видит только клиент, сервер отправку не видит вообще. Неизвестное
  значение или отсутствующее поле — `422` с `field_errors[{field:
  "events.props.<ключ>"}]`, лишние ключи вырезаются и в БД не попадают.
- **Список имён остался закрытым.** Тест на `422` для неизвестного клиентского
  события не ослаблен: произвольное имя по-прежнему отклоняет весь батч —
  менялся контракт, а не валидация.
- **`ShareCard.share_url`** — `https://t.me/<bot>?start=sh_<short_id>`.
  Собирается на сервере из `BOT_USERNAME`: `short_id` наружу больше нигде не
  отдаётся, а имя бота на клиенте — это конфиг, который нельзя хардкодить.
  `share_url` — **не** ссылка на файл: подписи (`sig=`) в ней нет, сроком она
  не ограничена (подпись бот выпускает сам при открытии), и файловый `url`
  остаётся приватным. `null` — имя бота на сервере не настроено.
- **Inline-режим бота.** Добавлен обработчик `inline_query`: бот отвечает
  карточкой-картинкой (`InlineQueryResultPhoto` с подписью) или пустым списком,
  если метки в запросе нет. На старте API спрашивает `getMe` про
  `supports_inline_queries` и пишет в лог `telegram_inline_mode`
  (`on | off | unknown`) с подсказкой: включённый inline — настройка BotFather,
  кодом она не включается, но и молчать о ней больше нельзя.
- **Событий продукта на inline нет** намеренно: ответ на inline-запрос — показ
  карточки, а не отправка. «Поделились» считается один раз и по клиенту.
- **Бот на `/start sh_<short_id>`** пишет одно событие — `share_card_opened`
  (`kind`, `channel: link`). Второе (`share_sent`) убрано: переход по ссылке —
  не отправка.
- **Тесты:** API 53 файла / 644 (было 52 / 629): `events.spec.ts` +4,
  `share-cards.spec.ts` +2, новый `telegram-inline.spec.ts` (9). Web 873,
  Python 90, `lint`/`typecheck`/`build` зелёные.

### Расхождения с заданием (и почему)

1. **`share_card_created` несёт `cached`, а `build_ms` — не всегда.** В задании
   «только kind, размер, время сборки». `cached` нужен, чтобы кэш-попадание не
   считалось сборкой, а `build_ms` при кэш-попадании отсутствует: рисования не
   было, и ноль там был бы выдумкой. Остальные поля — ровно те, что в задании.
2. **`share_url` может быть `null`.** `BOT_USERNAME` в конфиге необязателен
   (без него шаринг раньше работал «текстом»). В проде он задан, но пустая
   строка вместо честного `null` сломала бы fallback молча; в схеме поле
   описано как `[string, 'null']` и стоит в `required`.
3. **`share_card_opened` на `POST /share/card` больше не пишется.** Раньше это
   событие означало «запросил карточку в мини-аппе», теперь его место занял
   `share_card_created`, а `share_card_opened` остался про переход по ссылке
   (`channel: link`). Два имени на одно действие — та же путаница, из-за
   которой переименование и понадобилось.
4. **Inline-режим в BotFather кодом не включается** — это ручной шаг. Что
   сделано из кода: обработчик `inline_query`, проверка `supports_inline_queries`
   на старте, инструкция (`docs/qa/reports/share-events-1.6.9.md`). Пока режим
   не включён, основной путь шаринга — `share_url` + `openTelegramLink`; это
   записано в задании фронту, а не оставлено на догадки.
5. **Одна строка вне границ — `apps/web/src/analytics/events.ts`**
   (`share_sent: true,`), разрешена владельцем: bump контракта иначе делает
   `main` красным, а фронт-агент блокируется на `gen:api`. Логики отправки и
   вызовов `track` в этом PR нет — их делает фронт.
6. **Исторические данные не пересчитываются.** События за прошлые сутки,
   записанные как `share_sent` (генерации), под новым именем не появятся:
   счётчик «создано карточек» начинается с этой итерации. Объём данных на
   тестовом этапе ничтожен, а «дописать» старые строки значило бы соврать про
   их смысл.
7. **Новых счётчиков в `/admin/metrics` нет.** Счётчика `share_sent_24h` не
   существовало (событие писалось, но не агрегировалось), поэтому переименовывать
   в `share_cards_created_24h` нечего: аналитика шеринга считается по `events`.
8. **`share_sent` без `props` — `422`.** В задании оговорено только «неизвестный
   `kind`/`channel` → `422`». Событие без вида и канала бесполезно (метрика не
   разложится ни по карточкам, ни по путям), поэтому отсутствие поля считается
   ошибкой контракта, а не «пришло что пришло».
9. **Закрыт пункт 5 расхождений итерации 32** (`share_sent` пишет сервер):
   теперь событие клиентское, как и должно было быть с самого начала.

## Итерация 32 — PDF разбора и карточки шеринга (контракт 1.6.8)

Всё аддитивно: существующие маршруты, поля и статусы не менялись. Две новые
возможности и одна правка списков.

- **PDF разбора собирает Python-сайдкар, а не Node.** `POST /pdf/build` рисует
  документ на reportlab с встроенным DejaVu Sans: обложка (колесо, «Твой
  разбор», дата сборки), оглавление семи глав, главы в серверном порядке,
  финальный блок «Что сделать» и ссылка на бота. Node не умеет набирать текст —
  без встроенного TTF кириллица превратилась бы в квадраты на любом сервере без
  `fonts-*`, а системных шрифтов в образе сайдкара нет (и `cairo`/`pango` тоже).
  В API — только оркестрация: очередь, кэш, права, ссылка.
- **`POST /api/v1/reports/{id}/pdf`** отвечает `202` **всегда** и требует
  `Idempotency-Key`: сборка занимает секунды, а двойной тап не должен ставить
  две сборки. Кэш — по `(report_id, engine_version, prompt_version)` в таблице
  `report_pdfs`, поэтому повтор не пересобирает файл и не зовёт сайдкар.
  `GET` возвращает `{status, url?, expires_at?, error?}` и **свежую** подпись
  каждый раз.
- **Права.** PDF — часть оплаченного разбора, а не отдельный товар: чужой или
  неоплаченный разбор даёт `403 report_not_paid` (тизер тоже — текста в нём
  нет), отсутствующий — `404`, неготовый или без глав — `409
  report_not_ready`. Право проверяется по карте (`entitlements`), а не по
  статусу строки: `ready` бывает и у тизера.
- **Файлы приватные.** Каталог не отдаётся статикой; единственный вход —
  `GET /api/v1/files/{scope}/{name}?sig=…` с HMAC-подписью и сроком 24 часа
  (тот же формат `<expires>.<hmac>`, что у колеса карты). Прямых адресов
  хранилища нет ни в ответах, ни в боте. Ключ проверяется до подписи: `..%2F`
  в пути даёт `404`, а не «файл без подписи».
- **`DELETE /me` стирает файлы.** Ключи читаются до транзакции (строка
  `report_pdfs` уходит каскадом), файлы удаляются из хранилища после коммита —
  порядок «сначала БД, потом диск» оставляет в худшем случае недостижимый
  мусор, а не живую ссылку на удалённые данные.
- **Размер и качество.** `PDF_MAX_BYTES` = 12 МБ. При переполнении понижается
  качество колеса (scale 1 → 0.6 → 0.35 → без картинки), а не падает сборка:
  человеку нужен документ, а не идеальная обложка. Векторное колесо в PDF не
  вставляется — SVG пришлось бы растеризовать, а `cairosvg` в образе нет.
- **`POST /api/v1/share/card {kind}`** → `{url, expires_at, caption}`.
  `day` (1080×1920: знак Луны, фаза, освещённость, строка из `summary`, дата)
  доступна всем, у кого есть карта, включая бесплатный режим — это вирусный
  вход. `wheel` (1080×1920) требует карту. `insight` (1080×1080) — цитата 2–3
  предложений из «Ядра» оплаченного разбора, очищенная от астрономических
  терминов: карточку читает человек, который не знает, что такое асцендент.
  Карточки кэшируются по хешу содержимого, `short_id` выводится из того же
  хеша — ни `user_id`, ни `report_id` в ссылку `t.me/<bot>?start=sh_…` не
  попадают.
- **Совместимость не шарится.** `kind: "compat"` → `404
  share_compat_not_available` с объяснением. Данные партнёра — ПДн третьего
  лица, согласия на публикацию он не давал. Это решение, а не недоделка.
- **Без ПДн.** В карточках нет ни имени, ни даты/времени/места рождения, ни
  координат — ни в тексте, ни в байтах PNG: EXIF и текстовые чанки не пишутся
  вовсе. Проверяется тестом по байтам (Python) и по тому, что уходит в
  рендерер (API).
- **Бот.** `/start sh_<short_id>` отдаёт ту же карточку картинкой со свежей
  подписью и кнопкой «Открыть» — вирусная петля замыкается. `/start
  chart_<uuid>` не изменился.
- **Пагинация списков.** `GET /compatibility` и `GET /questions` получили
  `limit` (1…20) и `offset`, а также **`total`** — количество после фильтра и
  до `LIMIT`. Считается отдельным запросом: оконная функция на пустой
  последней странице вернула бы ноль именно там, где число нужнее всего.
  Мусор в параметрах (`?limit=abc`) не даёт `422` — приводится к умолчанию.
- **Наблюдаемость.** `GET /admin/metrics`: `pdf_generated_24h`,
  `pdf_downloaded_24h`, `pdf_failed_24h`, `pdf_cost_rub_24h`,
  `pdf_build_p95_ms`. События: `pdf_ready` (размер, страницы, длительность),
  `pdf_failed` (код), `pdf_downloaded` (класс клиента, не User-Agent),
  `share_card_opened` (`kind`, канал) и `share_sent` (`kind`, канал) — карточка
  ушла в чат ответом бота на `/start sh_…`: это единственная отправка, которую
  сервер видит своими глазами.
- **Стоимость.** PDF и карточки — CPU, а не модель: `pdf_cost_rub_24h` равен
  нулю по построению, а «цена» измеряется временем сборки
  (`pdf_build_p95_ms`, `report_pdfs.build_ms`). Оценок в рублях здесь нет
  намеренно — нечего оценивать.

### Расхождения с заданием (и почему)

1. **`503 pdf_failed` не отдаётся на провал сборки.** Провал живёт в теле как
   `status: "failed"` + `error` (`PdfStatus`), а повторный `POST` ставит новую
   попытку. Причина: сборка асинхронная, и опрос статуса, отвечающий `503`,
   выглядит как падение сервиса; поле `error` в схеме иначе было бы мёртвым.
   `503` осталось за настоящей недоступностью слоя хранения/очереди.
2. **Векторного колеса в PDF нет** (только растр): в образе нет `cairosvg`,
   `librsvg` и `cairo`, а тянуть системные библиотеки ради обложки — лишние
   200 МБ и новая поверхность отказа.
3. **Строка «сегодня хорошо для…» берётся из готового прогноза дня.** Если
   прогноза на сегодня нет (человек без подписки), карточка собирается из
   фактов сайдкара **без** этой строки: придумывать её в шаблоне значило бы
   выдавать выдумку за текст разбора.
4. **`compat`-карточек нет** — так и задумано (см. выше), это не «пока не
   сделали».
5. **`share_sent` пишет сервер, а не клиент.** В задании событие названо без
   указания стороны, но клиентская отправка (inline-режим Telegram) серверу не
   видна, а клиентский список событий в контракте сверяется с фронтом тестом —
   добавить туда имя, которого фронт не шлёт, значило бы разойтись с
   `apps/web`. Поэтому `share_sent` пишет сервер: карточка отправлена в чат
   ответом бота на `/start sh_<short_id>`. Клиентское событие появится, когда
   фронт начнёт его слать — одним PR с `x-analytics-events` и `apps/web`.
6. **`total`, `limit`, `offset` в схеме необязательны.** Сервер отдаёт их
   всегда (это проверено тестом), но в `required` они сломали бы фронтовые
   фикстуры, которые собирают `{items, quota}` руками, а править `apps/web` в
   этой итерации нельзя. Как только фикстуры обновятся, поля можно перевести в
   `required` — это одна строка в контракте.


## Итерация 30.3 — неудачные вопросы и совместимости не попадают в списки (контракт 1.6.7)

Правка поведения, а не схемы: тела ответов, коды ошибок и статусы прежние,
добавлен один счётчик в метриках. Причина: `failed` в истории читается
человеком как «я заплатил и получил ошибку», хотя право за провал не
списывается, — а проверить это в приложении было нельзя.

- **`GET /api/v1/compatibility` отдаёт только `ready` и собственные `pending`.**
  `failed` и `refunded` в списке нет никогда: неудачная попытка — внутренняя
  история, а не товар. Фильтр в SQL **до** `LIMIT`, поэтому счётчики и будущая
  пагинация считаются от того же набора, что и список (отдельного `total` в
  схеме нет — его добавление было бы изменением схемы, а схемы в 1.6.7 не
  меняются). `pending` оставлен: по нему витрина восстанавливает экран после
  закрытия мини-аппа.
- **`GET /api/v1/compatibility/{id}` не изменился** и возвращает запись в любом
  статусе, включая `failed` с `error_code`. Это нужно воркеру, QA и разбору
  инцидентов: провал скрыт из истории, но не из системы.
- **`GET /api/v1/questions` отдаёт `ready`, `refused` и `pending`**, `failed` —
  нет. `refused` остаётся намеренно: это настоящий ответ карты («про здоровье не
  отвечаю»), а не сбой. `pending` нужен и для восстановления экрана, и чтобы
  отличать `409 question_in_progress` от «вопроса не было».
  `GET /questions/{id}` по-прежнему возвращает любой статус.
- **Провал вопроса больше не тратит попытку.** Квота списывается на приёме (иначе
  гонка съедала бы две из трёх), а при сбое генерации возвращается тем же
  `refundQuota`, что и при `409`/дубле. Правило «списываем только на `ready`» у
  совместимости подтверждено тестом: провал не трогает ни разовую покупку, ни
  окно подписки.
- **Наблюдаемость.** `GET /admin/metrics` получил `compat_failed_24h` (по
  `updated_at`, как `compat_failed_30d`); `questions_failed_24h` на месте. События

## Итерация 30 — прогноз дня и «спроси карту» (контракт 1.6.6)

Только бэкенд. Обе функции — платный контент подписки; модель вызывается
**один раз в сутки на человека** (прогноз) и **один раз на вопрос**, а всё, что
можно посчитать без модели, считает Python-сайдкар.

- **Факты дня считает движок, а не модель.** Новый маршрут сайдкара
  `POST /forecast/facts` отдаёт на местную дату: знак Луны и градус на полдень,
  фазу с освещённостью, ретро-планеты, транзиты к Солнцу/Луне/Асценденту/MC
  (орб ≤ 3°, максимум 8, по силе), управителя дня по дню недели и 2–3 окна
  времени. Одинаковый вход — побайтово одинаковый JSON (тест). Правила школы

  `daily_forecasts` вставляется через `insert … on conflict do nothing`, поэтому
  два одновременных запроса дают **один** вызов модели, а второй читает готовый
  текст (тест на single-flight). Дата — местная дата **места рождения**
  (`profiles.place_tz`); ограничение «пояс рождения, а не текущего города»

## Итерация 29 — отмена подписки из приложения (контракт 1.6.5)

- **Автопродление можно отключить, не удаляя аккаунт.** `POST /api/v1/subscription/cancel`
  гасит только продление: доступ и права остаются до конца оплаченного периода
  (отмена ≠ возврат). До этого единственным способом не продлевать было удалить
  всё (`DELETE /me`), а кнопка «открыть подписки в Telegram» вела на
  `tg://settings/star_subscriptions` — адрес, которого в Telegram нет.
- **Повтор — `409`, а не `200`.** После успеха клиент получает
  `409 already_cancelled`, если подписки нет — `409 no_active_subscription`.
  Иначе экран не может отличить «отменно сейчас» от «уже было отменено».
- **`auto_renew` меняется только после подтверждения Bot API.** Вызов
  `editUserStarSubscription(is_canceled: true)` идёт с `charge_id` последнего
  успешного платежа подписки (`payments.telegram_payment_charge_id` в строке,
  иначе последний платёж пользователя). При `ok:false`/таймауте — `502` с
  `details.reason` (`telegram_error`, `timeout`, `no_charge_id`), состояние
  `failed`, повтор ночным джобом (тот же, что у `DELETE /me`: окно 30 дней, до
  5 попыток, не чаще раза в час). `no_charge_id` — наш дефект данных, у него
  отдельный счётчик.
- **`GET /me`** отдаёт `subscription.cancelled_at` (и уже существовавший
  `auto_renew`, который теперь наше записываемое состояние, а не «только для
  чтения из настроек Telegram»). Поля меняются только у отменённой подписки.
- **`DELETE /me` не изменился**: данные удаляются, доступ закрывается,
  автопродление гасится тем же вызовом. Если отмена уже была — второго вызова
  в Bot API нет.
- **Метрики**: `subscription_cancel_total_24h`, `subscription_cancel_failed_24h`,
  `subscription_cancel_no_charge_id_24h`, `subscriptions_auto_renew_off`;
  события `subscription_cancelled` (новое) и `subscription_cancel_failed`
  (с `props.source`).
- **Живой прогон на стабе Bot API** воспроизводит путь целиком для тестовой
  подписки `test_1`: оплата → отмена → `409` на повтор, параметры вызова видны
  в `GET /__config` (`e2e/qa/iteration-29.mjs`).

## Итерация 28 — `steps` собирается из пунктов, а не режется поперёк (контракт 1.6.4)

- **Обрезка больше не убивает список.** Второй живой прогон (`46d8b893`, 3,90 ₽)
  упал на `steps`: общий триммер порезал список по предложению (`from=651
  to=474`), потом по слову (`from=799 to=539`) — третий пункт исчез, раздел
  выброшен, покупка ушла в `failed`. Теперь для `steps` общего триммера нет
  вовсе: каждый пункт ограничивается отдельно (`trimStepsItem`, ≤140 знаков, по
  границе слова, с точкой), текст собирается заново из **всех** пунктов, а
  подпись-дисклеймер всегда прикрепляется последним абзацем и в обрезке не
  участвует.
- **`steps` не выбрасывается из-за формы.** Два или четыре пункта — принимаем с
  пометкой `steps_count`: «ровно три» — требование промпта, а не условие
  выдачи. `ui_reference` и битая разметка в `steps` — тоже пометки. Раздел
  теряется только на пустом или нераспарсенном ответе (ни одного пункта «—»)
  либо на запрещённом содержании (вердикт о паре, процент совместимости,
  запрещённые темы) — такой текст нельзя показывать ни за какие деньги.
- **Длина `steps` — мягкий ориентир.** Если после поштучной обрезки объём вне
  400–550 (например, два пункта), текст уходит человеку с `length_off`, а не в
  `failed`. Проверка длины при этом не ослаблена: у `clicks`/`friction`/
  `scenario` границы остаются условием выдачи.
- **`chars` в логе — это длина отданного текста.** Живой лог показывал
  `trimmed to=474`, а следом `chars=553`: обрезали один текст, проверяли другой
  (с подписью), писали в БД третий. Появилась `finalizeSection(text) →
  {text, chars, volumeChars}`: одна строка на валидацию, хранение и лог,
  `chars` = её длина, `volume_chars` = без подписи.
- **`validation` — перечень проверок с вердиктами.** Вместо противоречивого
  `code: "format"` + `verdict: "ok"` + `failures: ["steps_count"]` в записи
  теперь `checks: [{rule, status, detail, matched}]`: видно, что длина в
  порядке, а сломан список.
- **`ui_reference` описан и понижен для `steps`.** Правило ищет «нажм…»,
  «свайп…», «тап…», «экран…», «кнопк…» — отсылку к интерфейсу вместо жизни.
  Найденное слово уходит в лог (`matched`), у `steps` это пометка, у абзацных
  разделов — по-прежнему провал.
- **Светила не теряются, когда блок `luminaries` пуст.** Живая пара пришла с
  `present: false` во всех четырёх парах, хотя в `cross_aspects` светила были —
  семейство `luminary` оказывалось пустым ровно в разделе «Что совпадает».
  Теперь кросс-аспект с `luminary: true` попадает в семейство `luminary`
  (`luminary:aspect:<пара>`), а пары из блока не дублируются.
- **`compat:dry-run --long --steps=651|799`** воспроизводит этот лог: три
  пункта, подпись, `status: ready`.

## Итерация 27 — длинный раздел совместимости обрезается, а не выбрасывается (контракт 1.6.3)

- **`too_short` больше не значит «слишком длинно».** В живом прогоне
  `541d56a4` раздел «Как вы разговариваете» на 1 180 знаках при границах
  600–800 получил код `too_short`, вторая попытка дала 1 423 знака и тот же
  код, раздел был выброшен, а заказ ушёл в `failed` за 3,19 ₽. Причина —
  двухшаговая проверка (`<300 → too_short`, затем `length`), где `codeOf()`
  сводил оба кода к `too_short`. Теперь одна функция `classifyLength(chars,
  range)` с тремя явными ветвями и границами из `COMPAT_RANGES`:
  `too_short` — только `chars < min`, `too_long` — только `chars > max`.
- **`too_long` лечится обрезкой, а не отказом.** Текст режется по границе
  абзаца (у `steps` — внутри пунктов, чтобы все три остались), затем
  предложения, затем слова; результат всегда в `[min, max]`, в
  `normalization` пишется `trimmed`, в лог — `compat_section_trimmed
  {section, from, to, boundary, min, max}`. Повторного вызова модели на длину
  нет: она уже написала больше, чем просили, и второй раз напишет столько же.
- **Повтор остался только для `too_short` и неразобранного ответа** — один
  раз. Второй подряд короткий текст отдаётся как есть (`compat_section_short_accepted`,
  предупреждение `length_off direction=below`): отсутствие раздела хуже, чем
  короткий раздел. Раздел выбрасывается только на пустом ответе.
- **Диагностика содержит границы:** `compat_section_rejected` пишет `chars`,
  `min`, `max`, `verdict` и список предупреждений. Без `max` в живом прогоне
  нельзя было понять, что 1 423 — это перебор, а не недобор.
- **Терминология разведена:** `length_off` — предупреждение контракта с
  `direction: above|below`; `too_short`/`too_long`/`ok` — вердикт длины.
  Нормализация пробелов пишет `whitespace`, а не `trimmed` (иначе в
  `normalization` нельзя отличить «убрали пробелы» от «сократили текст»).
- **`/admin/metrics`:** `compat_sections_trimmed_24h`,
  `compat_sections_dropped_24h` — сколько разделов сокращено и сколько
  выброшено за сутки. Второе обязано быть близко к нулю.
- **`pnpm compat:dry-run --long`** воспроизводит живой прогон: модель отвечает
  на 1 084–1 433 знака, печатается `trimmed` по разделам и итоговый статус
  `ready`.

Первое подтверждение говорит это до нажатия словами `SPEC.md`: «Подписка при этом отменяется, доступ закрывается сразу, оплаченный период не возвращается». С экрана «Данные удалены» убрана строка «Подписка сохраняется до конца оплаченного периода»; на её месте — фраза про обезличенную историю платежей. Мок после `DELETE /me` не помнит ни подписки, ни покупок, ни прогноза.
- Мок API отдаёт `Me.entitlements.full_report_chart_id` в каждом ответе, как сервер с контракта 1.5.4: карта, за которую куплен разбор, или `null`. Приложение поле по-прежнему не читает (находки B и E отчёта QA-003/004).
- `POST /engagement/ask` клиент API не повторяет ни при 5xx, ни при обрыве сети.

## Фронт, итерация 7 — разбор для карты, удаление на другом устройстве, подписки по умолчанию выключены (контракт 1.5.5)

### Изменено
- **Разбор куплен для карты, а не для пользователя.** Приложение читает `Me.entitlements.full_report_chart_id`. Оплачен ли разбор карты, решается в одном месте — `hasReportFor(me, chartId)` в `apps/web/src/lib/plans.ts`: только когда сервер назвал именно эту карту. `full_report: true` сам по себе ничего не открывает: у того, кто купил разбор одной карты и построил вторую, на второй — цена, а не «Получить разбор». Платёж за разбор подтверждается тоже по карте (`grants(me, plan, chartId)`): разбор другой карты его не подтверждает. Это находки B и E отчёта QA-003/004.
- **`VITE_SUBSCRIPTIONS`: подписки продаются только при значении `enabled`.** Переменная не задана, пуста или равна `off` — сборка подписки не продаёт (было наоборот: продавала, пока не сказано `off`). Значение, которое нельзя прочитать (`of`, `0`, `yes`), по-прежнему останавливает и сборку, и dev-сервер.
- **Сборка говорит, с чем она сделана, первым делом** — до проверки типов и до Vite, четыре строки в одном виде: `subscriptions: OFF (set VITE_SUBSCRIPTIONS=enabled to sell)` или `ON SALE`; `support:` и `bot:` — значение или `NOT SET → …` с тем, что из этого выйдет; `consent:` — версия текстов согласия. Строки собирает `readBuildSettings` (`apps/web/scripts/buildSettings.ts`), её же зовёт `vite.config.ts`.
- **Данные удалены на другом устройстве: любое действие ведёт на Welcome.** К прежним путям (вопрос, заказ разбора, счёт за разбор, прогноз) добавлены: `404` на `GET /reports/{id}` — на карте, на экране разбора (в том числе пока разбор пишется) и при обновлении ссылки на PDF; настройки, открытые с карты; проверка платежа за разбор, который сервер не подтвердил («Проверить ещё раз» на пейволле и на карте). Приложение спрашивает `GET /me`: карты нет — Welcome с пустой анкетой, без текста сервера, без блока ошибки и без `error_shown`; карта на месте — как раньше. Разбор, на который сервер ответил `404`, приложение больше не берёт из `Me`: иначе запросы шли по кругу. `401` — отдельный случай: «Сессия устарела» и «Закрыть»; после удаления сервер так не отвечает.
- **Удаление данных, второе подтверждение** («Точно удалить?»): «Удаляются профиль, карты, разборы, прогнозы и вопросы — в том числе купленный разбор. **Подписка отменяется сразу, оплаченный период не возвращается.** Восстановить данные не получится.» Три абзаца, средний — полужирным, обычным размером.
- **Экран «Данные удалены»:** «Подписка отменена. Если захочешь вернуться — начнёшь с чистого листа.», мелким шрифтом — «Обезличенная история платежей сохранится для бухгалтерского учёта и возвратов.», ссылка «Управлять подписками в Telegram» (`tg://settings/star_subscriptions`; автопродление сервер сам не выключает, issue #29).
- **«Сегодняшний прогноз готовится»:** под «Загляни после 08:00» — «Время считается по месту рождения.»
- **Кнопка поддержки без контакта** называется «Контакт поддержки ещё не задан» (было «Поддержка скоро появится»).
- **Юридические тексты** приведены к `legal-texts-2026-11-10.md` в редакции от 2026-11-14 (пункт согласия об удалении, абзацы политики и соглашения: удаление отменяет подписку сразу и без возврата). Версия согласия прежняя, `2026-11-10`, — по правилу `legal.md` §6; хэш версии в `tests/legal-texts.test.ts` заменён (issue #30).
- **Фокус прогноза.** Код контракта `health` клиент API отдаёт приложению как `wellbeing`; на экране по-прежнему «самочувствие».
